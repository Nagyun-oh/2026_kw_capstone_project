# WAF 비교 실험실

같은 요청 샘플을 같은 백엔드 앞의 여러 WAF에 보내 요청 단계 탐지율·오탐률을 비교한다. 메인 스택(`compose.yaml`)의 WAF는 `DetectionOnly`로 감사 로그를 남기지만, WAF마다 로그 형식이 달라 그대로 비교할 수 없다. 그래서 실험실의 WAF는 모두 **차단 모드**로 두고 **차단 응답(403)** 으로 판정한다.

```text
run_pipeline_test.py --waf-mode status
  ├─> ModSecurity + CRS (127.0.0.1:8090) ─┐
  └─> Coraza + CRS      (127.0.0.1:8091) ─┴─> 더미 백엔드 (모든 요청에 200)
AI 판정: 실험 전용 AI(127.0.0.1:8101~)의 /predict/batch를 직접 호출
```

메인 스택과 네트워크·로그 수집이 분리돼 있어 Kafka·백엔드·DB에 기록이 남지 않고 블랙리스트 자동 등록도 일어나지 않는다.

## 구성

| 서비스 | 이미지 | 설정 |
| --- | --- | --- |
| `backend` | `nginx:alpine` (digest 고정) | 어떤 요청에도 200을 준다(`backend.conf`, 조건부 헤더가 있으면 nginx가 412·304를 줄 수 있음). 차단은 요청 단계에서만 일어나므로 판정은 백엔드와 무관하다 |
| `modsecurity` | `owasp/modsecurity-crs:nginx` (메인 WAF와 같은 digest) | 엔진 `On`, CRS 4.25.1 |
| `coraza` | `ghcr.io/coreruleset/coraza-crs:4.25.1-nginx-202609260209` (digest 고정) | 엔진 `On`, CRS 4.25.1 |

두 WAF의 설정은 메인 WAF와 같게 맞추고, 기동 후 생성된 `crs-setup.conf`에서 값이 같은지 확인했다.

- CRS: 차단 PL1, 탐지 PL2, 요청 임계값 5
- **응답 단계 차단은 끈다**(응답 임계값 10000). AI는 요청만 보므로 WAF도 요청 단계 탐지만 비교한다.
- 메인 WAF 커스텀 룰(`waf/rules/CUSTOM-001-ai-align.conf`) 중 **앱 호환 설정만** 같게 맞춘다: 허용 메서드에 PUT·PATCH·DELETE 추가(10004, `ALLOWED_METHODS`). 탐지 룰(10001~10003)은 넣지 않는다(CRS만 비교). 10005(Socket.IO 경로 예외)는 샘플에 해당 경로가 없어 넣지 않았다.

환경변수 이름은 같아도 의미가 달라 주의한다.

| 설정 | ModSecurity 이미지 | Coraza 이미지 |
| --- | --- | --- |
| 탐지 범위 PL | `PARANOIA` | `DETECTION_PARANOIA` |
| 차단 PL | `BLOCKING_PARANOIA` | `BLOCKING_PARANOIA` |
| `BACKEND` | `http://backend:8080` (스킴 포함) | `backend:8080` (nginx upstream이라 스킴 없음) |

## 실행

```bash
# 1) 샘플: 공격은 중복 제거 후 전부, 정상은 출처별 최대 18,000건 (원본 구성은 .meta.json에 남는다)
python3 dev_tools/scripts/sample_test_requests.py --mode census --benign-cap 18000 --seed 42 \
    --output dev_tools/datasets/sample-census.jsonl

# 2) 실험실과 실험 전용 AI(Kafka 없음). 메인 AI는 스레드 설정 때문에 느려질 수 있어(아래 참고) 따로 띄운다.
docker compose -f wafs/docker-compose.yml up -d
for n in 1 2; do docker run -d --rm --name ai-exp-$n -p 127.0.0.1:810$n:8000 -e OMP_NUM_THREADS=4 security-ai:local; done

# 3) WAF별 측정. AI 판정은 캐시에 저장해 두 번째 WAF부터 재사용한다.
python3 dev_tools/scripts/run_pipeline_test.py --input dev_tools/datasets/sample-census.jsonl \
    --waf-mode status --waf-port 8090 --label modsecurity-crs --workers 16 \
    --ai-url http://127.0.0.1:8101,http://127.0.0.1:8102 --ai-cache dev_tools/datasets/ai-cache.jsonl \
    --out-dir dev_tools/datasets/census-modsecurity
python3 dev_tools/scripts/run_pipeline_test.py ... --waf-port 8091 --label coraza-crs --out-dir dev_tools/datasets/census-coraza

# 4) 정리
docker stop ai-exp-1 ai-exp-2
docker compose -f wafs/docker-compose.yml down
```

`status` 모드 판정: WAF 응답이 403이면 탐지, 아니면 미탐지다. 더미 백엔드는 403을 주지 않으므로 기준선 비교(`--baseline-port`)는 쓰지 않는다. 실제 앱 앞에서 측정할 때는 `--baseline-port`로 앱에 직접 보낸 응답도 받아, 앱 자체가 403을 준 요청을 판정 불가(미탐지로 집계)로 따로 센다.

리포트의 "원본 구성으로 환산" 표는 층별 비율을 원본 건수로 가중 평균한 탐지율·오탐률, 라벨이 의심되는 출처(기본 `ecml`)를 뺀 오탐률, 실제 공격 비율(10%, 1%)을 가정한 정밀도다.

## 판정 방식 검증

실험실 ModSecurity(`status`)와 메인 WAF 감사 로그 판정(`audit`, 2026-10-20 실행)을 같은 샘플 1,000건으로 비교해 **1000/1000건 일치**를 확인했다(2026-10-22). 처음에는 975/1000건이었고, 차이 25건의 원인은 두 가지였다.

1. **감사 로그 판정 버그(24건)**: 기존 `audit` 판정이 "Total Score"를 하나만 저장해, 요청 이상 점수(949110)가 나중에 기록된 응답 점수(959100)로 덮어써졌다. 요청 점수가 10~15여도 응답 점수 4로 바뀌어 미탐지로 집계됐다. 요청·응답 점수를 따로 읽도록 고쳤다.
2. **허용 메서드 차이(1건)**: 메인 WAF는 CUSTOM-001(10004)로 PUT을 허용하지만 실험실은 CRS 기본값이라 PUT을 911100으로 차단했다. 실험실에 같은 설정을 넣었다.

1번 버그로 이전 결과의 WAF 탐지가 적게 집계됐다. 남아 있는 감사 로그로 다시 판정한 값은 다음과 같다(요청은 다시 보내지 않음). 수정 전 탐지가 수정 후 미탐지로 바뀐 경우는 없다.

| 실행 (3,000건) | WAF 탐지율 / 오탐률 | WAF+AI OR | WAF+AI AND |
| --- | --- | --- | --- |
| 2026-10-11 수정 전 | 80.3% / 29.8% | 93.5% / 42.5% | 60.8% / 1.1% |
| 2026-10-11 수정 후 | 82.4% / 31.0% | 95.4% / 43.8% | 61.1% / 1.1% |
| 2026-10-20 수정 전 | 76.8% / 29.7% | 92.7% / 56.5% | 52.2% / 1.4% |
| 2026-10-20 수정 후 | 80.7% / 30.9% | 95.9% / 57.8% | 52.9% / 1.4% |

## 결과: census 샘플 86,067건 (2026-10-22)

공격 45,663건(중복·라벨 충돌 제외 후 전부)과 정상 40,404건(출처별 최대 18,000건)을 보냈다. 전송 오류 0건, AI 판정은 캐시 공유로 한 번만 계산했다. 결과 파일: `dev_tools/datasets/census-{modsecurity,coraza}/`(Git 제외).

| 방식 | 탐지율 (원본 구성) | 오탐률 (원본 구성) | 탐지율 (출처 균등) | 오탐률 (출처 균등) |
| --- | --- | --- | --- | --- |
| ModSecurity + CRS | 43.0% | 19.6% | 58.7% | 31.9% |
| Coraza + CRS | 42.5% | 19.6% | 58.3% | 31.9% |
| AI | 86.3% | 4.4% | 72.2% | 16.5% |
| ModSecurity + AI (AND) | 39.1% | 1.4% | 45.9% | 1.6% |
| ModSecurity + AI (OR) | 90.1% | 22.5% | 85.0% | 46.8% |

- **원본 구성**은 층별 비율을 원본 건수로 가중한 값(±0.3~0.5%p), **출처 균등**은 출처 4개(capec·csic·ecml·wcp)를 같은 비중으로 평균한 값이다. 공격의 59%가 capec sqli(27,083건)라 원본 구성 값은 이 층이 좌우한다. 결과는 출처별 표와 함께 보고한다.
- **WAF는 URL 경로 안의 SQL 인젝션에 약하다.** capec sqli 중 SQL 구문이 경로에 있는 16,732건은 WAF 25.8%·AI 98.8%, 쿼리·본문에 있는 670건은 WAF 83.5~98.7%였다.
- **라벨 의심**: capec sqli 중 9,681건은 요청에 SQL 흔적이 없다(공격 세션 전체에 라벨이 붙은 것으로 보임). WAF 2.2%·AI 68.4% 탐지로, AI가 공격 구문이 아닌 데이터셋 특징(사이트 경로 등)을 학습했을 가능성이 있다. capec 정상 요청의 AI 오탐률도 15.4%다. 이 9,681건을 빼면 출처 균등 탐지율은 WAF 61.2%·AI 74.4%다. ecml 정상 요청은 WAF 오탐률 98.8%로 라벨이 의심된다(기존과 같음).
- **엔진 차이**: 같은 요청에서 ModSecurity만 탐지 194건, Coraza만 탐지 0건(맥니마 p≈8×10⁻⁵⁹). 194건 중 191건은 잘못된(overlong) UTF-8 인코딩으로 숨긴 경로 조작 공격이다(모두 wcp). 정상 요청 판정은 두 엔진이 같았다.
- AI 평가 데이터(`test.jsonl`)는 AI 학습 데이터와 같은 출처에서 나왔으므로, 처음 보는 사이트에서의 성능은 T2(다른 웹사이트)로 따로 확인해야 한다.

## 결과: ModSecurity PL1~4 (2026-10-22)

같은 census 샘플로 차단·탐지 PL을 같은 값(N)으로 바꿔 측정했다. 요청 임계값 5, 응답 단계 차단은 끈 상태다. PL1 재측정은 기존 측정과 86,067/86,067건 같았다(결정성 확인).

python3 dev_tools/scripts/run_pipeline_test.py --input dev_tools/datasets/sample-census.jsonl \
    --waf-mode status --waf-port 8090 --label modsecurity-crs-pl3 --workers 16 \

    --out-dir dev_tools/datasets/census-modsecurity-pl3

| PL | WAF 탐지율 / 오탐률 | WAF+AI AND | WAF+AI OR | WAF 정밀도(공격 10%) |
| --- | --- | --- | --- | --- |
| 1 | 43.0% / 19.6% | 39.1% / 1.4% | 90.1% / 22.5% | 19.6% |
| 2 | 74.5% / 38.9% | 67.1% / 3.7% | 93.6% / 39.6% | 17.5% |
| 3 | 78.3% / 46.3% | 70.6% / 3.9% | 94.0% / 46.8% | 15.8% |

원본 구성 환산값이다. AI 단독은 PL과 무관하게 86.3% / 4.4%(정밀도 68.7%)다. PL4에서도 WAF가 놓친 공격 9,689건 중 7,029건(72.5%)을 AI가 탐지했다.

- PL을 올리면 탐지율은 PL3부터 거의 늘지 않고 오탐률만 계속 오른다. 실제 공격 비율 10%를 가정한 WAF 정밀도는 PL1이 가장 높다.
- PL2부터 csic 요청은 공격·정상 모두 100% 차단된다. 모든 csic 요청에 있는 `Accept-Charset` 헤더가 920451(제한 헤더)에 걸리기 때문이다. 이 착시를 빼려고 csic를 제외한 출처 균등 탐지율을 보면 PL1 70.2% → PL2 85.3%다.
- PL을 한 단계 올릴 때 새로 생긴 오탐의 주요 룰(정상 요청 400건 표본): PL2는 920451·931130(외부 링크 RFI)·934120(SSRF), PL3는 932350(유닉스 명령 단어)·920300(`Accept` 헤더 없음, capec 데이터 특성), PL4는 942421(쿠키 특수문자 수)·920274·920273(엄격한 문자 검사).

| 1 | 43.0% / 19.6% | 26.9% / 2.6% | 20.7% / 0.7% | 15.9% / 0.3% |

- nginx가 ModSecurity에 넘기기 전에 거부한 요청은 모든 조합에서 같고 CRS 탐지로 세지 않았다: 400 1,248건(루트 위로 올라가는 경로 `/%2F..`, 잘못된 `%` 인코딩, 공격 935건 포함), 405 73건(`TRACE`). 412·304는 WAF를 통과한 요청에 더미 백엔드가 조건부 헤더를 보고 준 응답이다.

## AI 처리 속도

AI 서버는 요청을 하나씩 처리한다(모델 잠금). 새로 띄운 AI는 묶음 호출로 초당 약 75건이지만, 메인 스택 AI는 초당 약 5건으로 느려진 상태가 자주 보였고 재시작하면 회복됐다.

원인은 실행 시간이 아니라 스레드 설정이었다(2026-10-22, `dev_tools/load-test/README.md`).

- 기본 설정(스레드 수 지정 없음)은 한 건을 처리할 때도 여러 CPU 스레드를 쓴다. 여러 스레드(HTTP 요청 처리, Kafka 처리)에서 모델을 호출한 뒤에는 계속 느려진다.
- 메인 AI는 재시작 직후에도 Kafka 경로로는 초당 약 5.4건(1.4코어)이었다.
- `OMP_NUM_THREADS=1`이면 같은 Kafka 경로에서 초당 84건(0.93코어)이었고, 느려지지 않았다. 프로세스 스레드 수가 늘거나 Kafka 연결에 문제가 있던 것은 아니었다.

큰 실행은 실험 전용 AI를 띄우고, 여러 개면 `--ai-url`에 쉼표로 나눠 준다. census 측정은 `OMP_NUM_THREADS=4` 2개로 초당 약 125건이었다. 판정 결과는 어느 인스턴스든 같았다.

## 주의

- 2만 건처럼 많이 보낼 때 속도 제한·봇 차단 기능이 있는 WAF는 그 기능을 끄거나 전송 속도를 낮춘다. 속도 때문에 막힌 요청이 탐지로 집계된다.
- 처음에는 JuiceShop을 백엔드로 썼지만, census 샘플을 보내자 약 64초 만에 Node.js 힙이 4GB를 넘어 종료됐다(`JavaScript heap out of memory`). 이후 WAF 응답이 모두 502가 됐다. 메인 스택의 JuiceShop도 대량 공격 요청을 받으면 같은 일이 생길 수 있다. 리포트는 WAF 응답 5xx 건수를 표시하고, 1%를 넘으면 실행 중에 경고한다.
- 백엔드를 JuiceShop에서 더미 nginx로 바꿔도 같은 1,000건의 판정이 1000/1000건 같았다.
- AI 캐시는 `/health`의 모델 정보(버전·가중치·임계값)가 다르면 쓰지 않는다. 모델을 바꾸면 새 캐시 파일을 지정한다.
- WAF 주소는 `--waf-host localhost`(기본값)로 둔다. `127.0.0.1`로 보내면 Host 헤더가 숫자 IP라 920350이 모든 요청에 걸려 점수가 3점씩 더해진다.
- PL을 바꿀 때 탐지 PL은 차단 PL 이상이어야 한다. 낮으면 CRS 901500이 모든 요청을 500으로 거부한다(리포트의 5xx 경고로 드러난다).

### 공격 탐지 일반화 (공격 75건)

같은 DVWA 엔드포인트에 표준 점검 페이로드로 **공격 75건**(페이로드 68 + 비페이로드 7)을 만들어

| 묶음 | 건수 | ModSec PL1 | ModSec PL2 | Coraza PL2 | AI | OR(PL2∨AI) |
| --- | --- | --- | --- | --- | --- | --- |
| 페이로드 공격 | 68 | 85% | 94% | 94% | **62%** | 94% |
| 비페이로드(CSRF·무차별·리다이렉트) | 7 | 0% | 14% | 14% | 0% | 14% |

  새 사이트 공격 탐지는 WAF가 우수 → 두 계층 병행 근거가 양방향으로 성립. 전체 분석은
  `dev_tools/datasets/t2-dvwa/report.md`.

## WAF 추가하기

1. `wafs/docker-compose.yml`에 서비스를 추가하고 `127.0.0.1:809x`로 노출한다. 백엔드는 `backend:8080`.
2. 차단 모드로 켜고, 요청 단계만 차단하도록(응답 검사 차단 끔) 설정한다. 허용 메서드도 위와 같게 맞춘다.
3. 차단 응답 코드를 확인한다. 403이 아니면 `--block-status`로 지정한다(예: `--block-status 403,406`).
4. 이미지는 digest로 고정하고, 설정값을 이 문서의 구성 표에 적는다.
