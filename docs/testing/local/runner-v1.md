# 로컬 초기 실행기와 계측 이력

정리일: **2026/11/05**

이 문서는 2026/10/31~2026/11/01의 v1 실행 규칙과 구현 이력이다. 아래의 다음 작업·미실행 표현은 작성 당시 상태다. 최신 진행은 [로컬 목차](README.md), 현재 E2E 실행은 [v2 가이드](e2e-runner.md)를 따른다.

### 로컬 정상 요청 실행기의 판정 기준

새 실행의 판정 기준 버전은 `arrival-smoke-v3`이며 `manifest.json`에 저장한다. `constant-arrival-rate`는 기간 동안 반복 시작률을 설정하는 방식이다. `요청률 × 기간`을 계획 참고 건수로 남기고, 실제 HTTP 건수와의 차이를 `metrics.json`의 `request_count_delta`에 기록한다. 이 차이만으로 실패시키거나 임의의 ±1 허용 범위를 두지 않는다.

- `PASS`: 실제 HTTP 요청과 완료 반복(`iterations`)이 각각 1건 이상이며 두 건수가 같고, 모든 응답이 200, `dropped_iterations`가 0, 평균·p95·p99·최대 응답 시간이 확보됨. 실행 완료·k6 종료 코드 0, Docker 표본과 Kafka 전후 결과 등 필수 증거 확보도 필요하다. 현재 시나리오는 반복당 HTTP 요청이 한 건이다.
- `FAIL`: 요청·완료 반복이 0, 완료된 실행의 요청 수와 반복 수 불일치, 200 외 응답, 실행하지 못한 반복 발생 또는 k6 임계값 위반(종료 코드 99)이 확인됨.
- `INCONCLUSIVE`: 확인된 기준 위반은 없지만 실행 중단·실행 오류·필수 지표나 수집 결과 누락으로 판단할 수 없음. 확인된 위반이 함께 있으면 `FAIL`로 두고 증거 부족도 기록한다.
- 판정 이유는 `metrics.json`의 `verdict_reasons`와 보고서에 남긴다. 수집 예외가 없어도 HTTP·k6 기준 위반 사유를 확인할 수 있다.

이 판정은 작은 예비 실험의 실행·수집 확인용이다. 정확한 목표 요청률 달성, DB 처리 완료, 탐지 정확도나 차단 성공을 보장하지 않는다. 정상으로 의도한 요청에서 탐지가 발생했다면 위협 저장·알림도 발생한 부하로 기록한다. 정식 부하 테스트에서는 요청률 달성·지연 상한·최종 처리 등 별도 기준을 실행 전에 확정해야 한다.

기준 변경 전의 보고서·원본·판정은 수정하지 않는다. 이전 실행이 정확 건수 조건 때문에 실패했더라도 원래 결과를 보존하고, 새 기준으로 새 ID·회차를 실행해 비교한다.

## 8. 진행 현황 — 2026/10/31

실험을 재개할 때는 [로컬 진행 목차](README.md)와 관련 회차·증거를 확인한다. 아래 표는 2026/10/31의 진행 기록이다. 이후 조사할 문제는 실제 관측에서 선택하고 진행 상태는 환경별 목차에 기록한다.

## 9. p99 지원 구현·검증 — 2026/11/01

위 2026/10/31 진행 표의 p99 구현 대기 항목을 완료했다. 평균·p95·p99·최대값의 정규화·저장·보고와 `arrival-smoke-v3`의 필수 지표 판정을 연결했고, 모의 테스트 26개와 실제 설치된 k6의 `inspect` 검사를 통과했다. 이 구현 검증 당시에는 실제 HTTP 부하를 실행하지 않았다. 이후의 r07 실측과 다음 작업 범위는 아래 10절과 환경별 목차를 따른다.

## 10. 서버 검증 우선순위 확정 — 2026/11/01

r07에서 HTTP 60건 모두 200, 평균 6.22ms·p95 9.62ms·p99 29.25ms·최대 29.70ms와 Kafka 전후 lag 0을 확인했다. 사용자 SQL에서도 로그·고유 requestId·AI 탐지·연결된 원본 로그가 각각 60건이었다. 이 결과로 기본 요청·저장 경로 확인을 마쳤으며, 장애 안전성·최대 처리량 검증을 완료한 것은 아니다.

앞서 계획했던 탐지 조합별 전체 기능 E2E는 현재 서버 실험의 필수 선행 단계에서 제외한다. 자동 등록·알림 정합성 등 백엔드 기능 검증은 유지하고, 고정 데이터 정책 테스트와 변경 영향에 따른 통합 검증으로 범위를 정한다. 탐지 품질 검증은 보안 팀원과 분담한다.

이후 구현한 선택 계측 옵션과 현재 다음 작업은 아래 11절을 따른다. 모델·탐지 정책이 바뀌면 성능 비교 조건에도 반영한다. 원본 실험 보고서·판정은 수정하지 않고 현재 상태는 환경별 목차에서 갱신한다.

## 11. 로컬 서버 계측 옵션 — 2026/11/01

`--observe-pipeline`을 추가해 실험 URL의 DB 로그·requestId·탐지 건수, 서비스 반환 후 AI 완료 로그, 부하 중·종료 후 Kafka lag, 관측 구간별 비동기 지연을 대조한다. 기존 옵션 없는 스모크와 과거 판정은 유지한다. r08의 DB 시각 해석 모순을 진단하고, `--db-time-offset`을 필수로 명시하는 `local-pipeline-v2`로 보완했다. 모의 테스트 총 47개와 r09의 실제 계측 검증을 통과했다.

구체적인 범위·읽기 전용 DB 조회·시간 해석·r08 실패 근거·r09 결과·실행 기준은 [로컬 서버 계측 준비·검증](server-observation.md)을 따른다. 실패·정책상 제외·DLT·알림의 요청별 집계와 정확한 요청 시작→커밋 지연은 미측정으로 유지한다. 이후 목표 확정·판정·자동 중단 구현은 아래 12절을 따른다. 짧은 계측 연결 확인을 서버 최대 성능·장애 검증 완료로 표현하지 않는다.

## 12. 로컬 1차 기준 확정·판정·자동 중단 — 2026/11/01

사용자가 초안을 확정해 [기계 실행용 기존 기준](../../../scripts/testing/profiles/local-load-v1.json)을 기록했다. `--profile local-load-v1`은 1·3·5회/초 중 하나, 120초, 최종 관측 60초, HTTP p95/p99 200/500ms와 DB 행 생성→AI 완료 p95/p99 2000/5000ms를 적용한다. 각 부하는 3회 계획이며 한 명령은 한 회차만 실행한다. 별도의 이전 기준 문서는 제거했고 현재 사람이 읽는 측정 계약은 아래 v2로 모은다.

예상 밖 403, 10초 오류율, 필수 컨테이너 종료·OOM·재시작, 호스트 여유 메모리, 연속 수집 실패를 감시하고 k6만 중단한다. 서비스·DB·기존 보고서는 변경하지 않는다. 중단 사유·부분 원본·판정·기준 해시를 기록하며 증거 부족을 성공으로 채우지 않는다.

모의 테스트 74개와 k6 설정 검사·dry-run을 통과했다. 이 구현 작업에서 실제 HTTP 부하·장애 주입은 수행하지 않았다. 서버 범위 v1 도구 준비는 완료했다. 이후 측정 범위를 구체화한 현재 다음 작업은 아래 13절을 따른다. 이전 스모크·r01~r09 원본과 판정은 유지한다.

## 13. AI·WAF→대시보드 E2E 기준 v2 — 2026/11/01

[측정 계약](e2e-plan-v2.md)과 [기계 명세](e2e-plan-v2.json)를 추가했다. 이번 작업은 기준 문서 작성이며 새 실행 프로필·앱 계측·실험 결과를 생성한 것은 아니다. 기존 v1의 기준·판정과 r01~r09 원본은 보존한다.

- AI: HTTP→access 수집→Kafka→AI 처리 완료→브라우저의 AI 출처 수신·표시.
- WAF: HTTP→audit 이벤트→Kafka→WAF 탐지 저장→브라우저의 WAF 출처 수신·표시.
- 총 1·3·5회/초에 10초당 양성 probe 1개를 포함한다. 각 120초·3회, 회차마다 워밍업 30초를 제외한다. detector fixture는 보안 팀원이 확인한 입력으로 고정한다.
- run·phase·요청 순번→서버 requestId→alertId·revision을 연결한다. 첫 알림에 두 출처가 함께 있어도 두 경로의 완료를 각각 기록하며 팝업은 하나로 유지한다.
- 서버 시각과 브라우저 수신·DOM 표시를 분리한다. 현재 초 단위 access 시각, DB 행 생성 시각, 발송 메서드 반환을 정밀 커밋·실제 브라우저 수신의 대용으로 쓰지 않는다.
- 초기 지연 목표는 명세에 고정한다. 낮은 부하의 p99는 참고값이며 단계는 3회 모두 PASS여야 통과한다. lag·완료 누적 수를 부하 중에도 기록하고 종료 후 필수 4개 경로의 lag 0을 최소 10초 간격으로 2회 확인한다.

다음은 요청 추적·정밀 시각·실제 관리자 브라우저 관측과 v2 판정·중단 연결 구현이다. 짧은 연결 검증 후 fixture·차단 정책·시계·관측 비용을 확인하고 첫 기준 측정을 진행한다. 현재 v1 명령으로 v2 전체 E2E를 측정했다고 기록하지 않는다.

## 14. 기준 문서 통합·p50 연결 — 2026/11/01

이전 기준 문서를 제거하고 참조를 v2 또는 보존한 v1 JSON으로 정리했다. HTTP·비동기 지연의 p50 수집값을 결과 JSON·Markdown 보고서에 연결하고, 중앙값·누락·잘못된 값·0·기존 판정 유지의 회귀 테스트를 추가했다. 모의 테스트 총 79개 통과. 기본 임시 폴더에 대한 실행 환경의 권한 오류가 있어 검증 프로세스에서만 `tempfile.tempdir`를 작업 폴더의 `build`로 지정했다. 기존 실험 보고서·원본·합격 기준은 보존한다. v2 전체 E2E 계측 구현과 새 부하·장애 실험은 아직 별도 작업이다.

## 15. v2 실행기·브라우저 계측 구현 — 2026/11/01

별도 `scripts/testing/run_e2e.py`와 원본 표본 합산기를 추가했다. WAF 응답 ID·시각, 실험 표식, 백엔드 trace·DB 연결, 실제 프론트 수신·DOM 관측을 연결한다. 현재 다음 작업은 [실행 가이드](e2e-runner.md)의 실제 반영·로그인·소량 검증이다. 기존 v1·과거 결과는 보존하며 실제 부하를 실행한 것으로 표시하지 않는다.
