## 1. 목표와 종료 지점

같은 HTTP 요청을 기준으로 AI·WAF 두 분기의 처리 지연과 대시보드 전달·표시 지연을 구분한다. 탐지율·오탐률·공격 유형별 판정은 보안 팀원의 범위다. 이 실험은 해당 탐지가 발생했을 때 서버·알림·화면이 처리하는 성능과 정합성을 확인한다.

```text
AI: HTTP → WAF access.log → Fluent Bit → log-topic → 백엔드·로그 DB
         → ai-request-topic → AI → ai-result-topic → 백엔드 결과 처리

WAF: HTTP → WAF audit.log → Fluent Bit → waf-detection-topic → WAF 탐지 DB

공통: 탐지·알림 대기 정보 커밋 → 전송기 → WebSocket → 브라우저 수신
      → 알림 표시 / 목록 API 재조회 → 테이블 반영
```

브라우저 수신, 알림이 실제로 보이는 시점, 목록 행이 보이는 시점은 서로 다른 지표다. 주 E2E 종료 지점은 **상관관계를 확인한 알림에 기대한 출처가 보이는 시점**으로 잡는다. 페이지·검색 조건에 영향을 받는 테이블 반영은 별도 대표 표본으로 확인하며, 모든 요청이 현재 10행 목록에 동시에 나타날 것을 요구하지 않는다.

## 2. 고정할 부하와 워밍업

총 부하는 1→3→5회/초, 각 120초·3회다. 각 회차 시작 전 30초 동안 총 1회/초로 같은 모델·브라우저·수집 경로를 워밍업한다. 워밍업에도 중단 감시를 적용하고, 종료 후 처리·알림 대조와 필수 lag 0을 확인한 뒤 측정을 시작한다. 워밍업은 성능 통계·본 실험 건수에서 제외한다. 준비 완료를 확인하지 못하면 본 측정을 시작하지 않는다.

| 총 목표 요청률 | 10초당 일반 요청 | 10초당 E2E probe | 120초 계획 참고 총량 |
| --- | --- | --- | --- |
| 1회/초 | 9 | 1 | 120 |
| 3회/초 | 29 | 1 | 360 |
| 5회/초 | 49 | 1 | 600 |

probe는 총 부하에 포함한다. 일반 요청의 경로·구성은 고정하고, probe는 보안 팀원이 검증한 입력을 사용해 동일 요청에서 AI·WAF 출처를 관측하는 것을 기본으로 한다. 실제 발생 건수를 기록하며 도착률 기반 실행의 끝 경계 때문에 계획 건수와 다르다는 이유만으로 실패시키지 않는다.

probe의 요청·기대 상태 200·기대 출처·모델·WAF 규칙·fixture 해시를 워밍업 전에 고정한다. 두 탐지가 확인된 fixture가 없으면 별도 검증된 probe 군으로 설계를 개정하고 새 버전을 사용한다. 특정 조합을 만들기 위해 본 실험 중 모델·탐지 기준을 조정하지 않는다. AI 단독·WAF 단독 등 모든 기능 조합을 이 부하 실험의 선행 과제로 확대하지 않는다.

같은 요청의 이중 탐지가 자동 블랙리스트 등록으로 이어질 수 있으므로 전용 클라이언트 IP·차단 제외·기존 등록 여부를 사전에 확인하고 기록한다. 필요 시 합의한 격리된 로컬 측정 조건을 준비하며 실행기가 임의로 화이트리스트·정책·DB를 바꾸지 않는다. 조건이 미확정이면 실행 대기다. 실제 403 차단·해제는 별도 시나리오다.

모델·정책·데이터·이미지·자원 제한·브라우저 수·백그라운드 트래픽·UI 초기 상태·계측 옵션을 회차마다 기록한다. 일반 요청에서 실제 발생한 탐지·알림량도 기록해 모델 변경으로 처리 부하가 달라지는 것을 구분한다.

## 3. 실행·요청·알림 식별

| 키 | 역할 |
| --- | --- |
| `runId` | 실험 회차 식별. 인증·IP 신뢰·보안 정책의 근거로 사용하지 않음 |
| `phase` | `warmup` / `measurement` 분리 |
| `kind`·`sequence` | `background` / `probe`와 회차 안 요청 순번. 요청 키는 runId·phase·kind·sequence 조합 |
| `requestId` | WAF가 생성한 공통 ID. 대소문자를 보존하고 클라이언트가 보낸 ID로 대체하지 않음 |
| `alertId`·`revision`·`sources` | 통합 알림 식별·중복 처리·출처 최초 확인 |

v2는 실험 표식을 전용 헤더 `X-DualGuard-Test-Run/Phase/Kind/Seq`로 보낸다. 표식과 보안 payload를 분리하고 실제 access 로그까지 보존되는지 검증한다. 기존 v1의 정확한 `test_run` URL 필터는 유효하지만 v2의 헤더 방식과 혼합하지 않는다. 시간 구간만으로 실험 요청을 선택하지 않는다.

WAF에서 생성한 ID를 응답 `X-Request-ID`로 돌려주는 설정과 클라이언트 연결을 추가했다. 응답 ID가 access·audit의 ID와 일치하고 입력 헤더로 위조·중복되지 않는지 실제 기동 후 확인한다. 실행기는 응답 헤더·저장된 ID·실험 표식을 대조하고 누락되면 성공으로 처리하지 않는다.

WAF Lua 이벤트는 query·headers를 제거하므로 헤더를 붙인 것만으로 WAF 분기를 필터링할 수 없다. 클라이언트가 확보한 서버 requestId 집합으로 WAF 이벤트를 대조하고, 원본 로그가 아직 없어도 WAF 이벤트를 추적한다. 현재 알림 DTO에 requestId가 없으므로 `request_alerts.alert_key`를 통한 alertId 매핑 또는 호환 가능한 메시지 계측이 필요하다. 알림이 매핑보다 먼저 도착해도 최초 관측 시각을 버리지 않는다.

## 4. 시각과 지표 정의

| 시각 | 출처·의미 |
| --- | --- |
| C0 | E2E probe 송신 직전, 측정 제어기 단조 시계 |
| C1(AI/WAF) | 실제 로그인된 브라우저의 STOMP 수신 처리에서 유효 revision·해당 출처를 처음 확인해 같은 제어기에 전달한 시각 |
| C2(AI/WAF) | 동일 알림에서 해당 출처가 보이는 DOM을 같은 제어기가 확인한 시각 |
| S0 | WAF의 `$msec - $request_time`으로 계산한 요청 시작 UTC epoch. 밀리초 해상도이며 초 단위 access `time`으로 대체하지 않음 |
| S1 | 해당 access 로그 저장 트랜잭션의 커밋 완료 후 UTC 시각 |
| SAI | AI 결과 처리 성공·트랜잭션 반환 후 UTC 시각. 정상·위협 결과 구분 |
| SWAF | WAF 탐지·알림 대기 정보 트랜잭션의 커밋 완료 후 UTC 시각 |
| SPUB | 알림 전송 호출 시각. 브라우저 수신 확인은 아님 |

| 지표 | 계산·대상 |
| --- | --- |
| HTTP 요청 경로 응답 | 일반 요청의 HTTP 전송·대기·수신 시간. 대시보드 API 응답성과 구분 |
| 로그 수집 구간 | S1−S0 |
| AI 처리 구간 | SAI−S1 |
| AI 서버 E2E | SAI−S0, AI 분석 대상 요청 전체 |
| WAF 서버 E2E | SWAF−S0, WAF 탐지 발생이 확인된 요청 |
| 출처별 알림 E2E | C1(AI/WAF)−C0, 기대 출처를 확인할 probe |
| 출처별 화면 E2E | C2(AI/WAF)−C0, 대응 알림이 실제로 보이는 probe |
| 공통 전달 구간 | 출처 커밋→전송 호출→브라우저 관측→DOM. 시계 연결이 검증된 구간만 계산 |

C0~C2는 같은 측정 제어기의 시계를 사용한다. 브라우저와 제어기 사이 보고·DOM 관측 비용을 포함하는 관측 지연임을 명시하고 브라우저 원시 시각도 보조 증거로 남긴다. 서로 다른 `performance.now()` 기준점을 직접 빼지 않는다. k6 일반 요청의 송신 표본과 서버 UTC를 연결할 때는 같은 OS 시계·동기화·정밀도·측정 오차를 확인한다. EC2는 별도 시계 검증이 필요하다.

S0 산출과 `DG_TRACE` 커밋 후 표식을 구현했다. 저부하 사전 요청의 송신·응답 시각과 WAF 시각을 대조하고 왕복 100ms를 넘으면 시작하지 않는다. 이는 밀리초 단위 관측 범위 확인이며 정밀한 시계 동기화를 보장하지 않는다. DB `created_at`, WAF의 초 단위 `time`, 알림 DTO의 `time`을 요청 시작·커밋·브라우저 수신 시각으로 치환하지 않는다. v2는 DB DATETIME을 지연 계산에 사용하지 않으며 기존 DB 값·시간 설정을 바꾸지 않는다. 시각 모순·오차 미확인은 해당 구간 INCONCLUSIVE다.

## 5. 알림 통합과 UI 관측

현재 전송기는 기본 1초 주기로 pending 알림을 보내고, 두 출처가 먼저 도착하면 첫 CREATED부터 AI·WAF를 함께 포함할 수 있다. 같은 메시지로 두 출처의 최초 관측을 충족해도 정상이다. UPDATED에서 나중 출처가 추가되면 그 출처를 처음 확인한 시각을 사용한다. 같은 requestId에 팝업 두 개를 요구하지 않는다.

정상 AI 결과에는 탐지·알림이 없을 수 있다. 모든 요청의 AI 처리 완료를 대조하되, 알림 기대치는 실제 발생한 탐지의 요청별 출처 집합과 검증된 probe 기대 출처로 정한다. 실제 탐지가 없는데 알림을 기다려 전송 유실이라고 판정하지 않는다.

실제 로그인·세션·CSRF·STOMP 구독이 완료된 브라우저 한 개를 사용한다. 인증 준비 실패를 해결하려고 보호 설정을 해제하지 않는다. 단순 WebSocket 클라이언트 수신을 실제 UI 수신·표시로 대체하지 않는다. 프론트가 알림 후 목록을 비동기로 재조회하는 동작을 고려해 알림 가시성과 목록 반영을 분리한다. 기대 출처 확인 전에 probe 알림을 닫지 않으며, 워밍업 알림 정리와 화면 조건을 고정한다.

테이블 반영은 회차별 대표 probe 한 건을 추적 가능한 기존 검색·페이지 조건에서 따로 확인한다. 검색·페이지 범위를 벗어나 보이지 않는 행을 전송 누락으로 세지 않는다. 실제 대시보드 API 응답은 브라우저의 기존 재조회 요청을 관측해 endpoint별 진단 지표로 남기며 JuiceShop HTTP 목표를 적용하지 않는다.

## 6. v2 초기 합격 기준·통계

아래 시간 상한은 v2를 위해 정한 초기 엔지니어링 목표이며 운영 SLA가 아니다. 새 계측의 저부하 검증에서 시간 출처·관측 비용·fixture를 먼저 확인한다. 기준을 변경해야 하면 본 실험 전에 새 버전으로 남긴다. 실행한 회차의 목표를 결과에 맞춰 바꾸지 않는다.

| 항목 | 초기 기준 |
| --- | --- |
| 일반·probe HTTP | 고정 fixture의 기대 200 응답 100%, dropped_iterations 0. 실제 송신·응답·완료 대조 |
| 일반 HTTP 요청 경로 | p95 ≤ 200ms. 대시보드 응답성·DualGuard 추가 오버헤드로 설명하지 않음 |
| AI 서버 E2E | SAI−S0의 p95 ≤ 3000ms, eligible 전체 처리·표본 수 대조 |
| WAF 서버 probe | 탐지 발생이 확인된 각 probe의 SWAF−S0 ≤ 2000ms |
| AI·WAF 브라우저 수신 | 기대한 각 출처를 각 probe의 C0부터 5000ms 이내에 관측 |
| AI·WAF 알림 표시 | 기대한 각 출처를 대응 알림 DOM에서 C0부터 7000ms 이내에 확인 |
| 최종 정합성 | 측정 phase의 실제 송신·서버 requestId·로그·AI 처리 결과 대조. WAF는 실제 발생 이벤트·기대 probe 대조. 알림은 요청별 기대 sources·최신 revision·실제 관측 대조 |
| 결과 중복 | 불필요한 DB 중복 결과 0, 같은 알림·revision의 중복 팝업 0. Kafka 재전달 자체는 별도 집계 |
| 적체 해소 | 최종 관측 60초 + 진행 중 명령 시간 안에서 처리·알림 대조와 함께 필수 lag 0 두 번 확인 |

요청·처리 지연은 표본 수·평균·p50·p95·p99·최대값·미확인·기한 초과를 함께 남긴다. 현재 1/3/5회·초 단계에서는 **p99를 참고 지표로 기록하며 단독 합격 기준으로 사용하지 않는다.** 120초당 기본 probe는 약 12개이므로 probe의 백분위도 참고값이며 각 probe의 기한과 정합성을 판정한다. 이를 WAF 처리량 한계 시험으로 설명하지 않는다.

p50은 중앙값으로 평소 요청의 응답 수준을 보여주는 참고 지표다. 별도 지연 합격 상한을 추가하지 않는다. HTTP는 k6 `med`를 `http_p50_ms`로 저장하고, 비동기 구간별 원본 표본은 `p50_ms`로 집계한다. 누락값은 미측정으로 남기며 과거 보고서를 소급 수정하지 않는다.

3회 합산 백분위가 필요하면 동일 환경·모델·rate·fixture·경로·구간·phase의 원본 지연 표본을 합쳐 다시 계산한다. 회차별 p99를 평균내지 않는다. 도착하지 않은 표본을 0ms로 넣거나 제외한 채 전체 성공으로 표시하지 않는다. 실제 관측한 표본의 조건부 통계와 누락·기한 초과 비율을 함께 기록하고, 중단·불완전 회차의 관측 범위를 표시한다.

v2의 원본 표본 집계는 정렬한 n개 값의 인덱스 `(n−1)×p`에서 이웃 값 사이를 선형 보간한다. 사용한 계산법·도구 버전도 저장하고, k6 요약값과 자체 재집계값의 출처를 구분한다. 표본이 없으면 백분위는 미측정이다.

**3회 모두 PASS일 때 단계 PASS**다. 확인된 FAIL이 하나라도 있으면 단계 FAIL, FAIL 없이 INCONCLUSIVE나 미실행 회차가 있으면 단계 INCONCLUSIVE다. 중앙값·다수결로 실패 회차를 덮지 않는다. 1단계가 통과하지 못하면 원인 확인 전 높은 부하로 확대하지 않는다.

fixture가 기대한 탐지를 만들지 않은 경우, 원본 WAF audit·AI 결과 발생 근거부터 확인한다. 발생 이벤트가 확인됐는데 저장·전달이 기한을 넘으면 해당 파이프라인 위반으로 기록한다. 탐지 자체가 발생했는지 알 수 없으면 fixture·관측 문제로 구분하고 손실·미탐 원인을 단정하지 않는다.

## 7. 부하 중 추이·중단·멱등성

10초 간격으로 필수 group·partition lag와 runId·phase별 누적 송신·로그 커밋·AI 완료·WAF 저장·출처별 브라우저 관측 건수를 함께 기록한다. 명령 소요 시간이 더해지는 실제 시작·종료 시각을 남긴다. 필수 경로는 `log-group/log-topic`, `ai-service-group/ai-request-topic`, `ai-result-group/ai-result-topic`, `waf-detection-group/waf-detection-topic`이다.

최종 lag 0 두 번의 확인 간격은 **직전 수집 완료 후 최소 10초 + 명령 시간**이다. lag 0 자체는 처리·브라우저 완료를 뜻하지 않는다. AI 정상·위협·실패·정책상 제외·미처리를 구분하고 단순 탐지 건수를 완료 건수로 쓰지 않는다.

각 수집·조회·브라우저 관측에는 유한한 타임아웃을 두고 실행 전에 값을 기록한다. 최종 대기 시간에 진행 중 명령 시간이 더해지더라도 해당 타임아웃을 넘겨 무한 대기하지 않는다.

완료 처리량은 실제 표본 시각 간 완료 건수 증가량/경과 초로 계산한다. lag·요청별 미완료 수의 기울기와 완료 처리량·자원을 함께 보고 포화 후보를 찾는다. Kafka lag는 group 전체, 업무 건수는 run·phase 필터임을 표시해 다른 트래픽에 의한 증가를 혼동하지 않는다. 관측 구간만으로 장기 포화를 확정하지 않는다.

v2의 중단 기준은 예상 밖 403, 최근 10초·완료 10건 이상·오류율 10% 이상, 필수 컨테이너 종료·OOM·재시작·교체, 여유 메모리 1GiB 미만 15초, 같은 필수 수집 연속 2회 실패다. 수치는 기존 실행기 기준에서 유지하며 이 문서와 기계 명세에 직접 기록한다. v2의 브라우저·trace·건수 수집도 필수 관측에 포함한다. 워밍업에도 적용한다. 중단 대상은 실행기가 소유한 부하·probe 작업이며 앱·DB·차단 정책을 자동 변경하지 않는다.

DB 중복 결과 0의 근거는 실제 DB 제약과 동시성·재전달 검증을 함께 확인한다. `network_logs.request_id`, WAF requestId·threatId, `request_alerts` 키의 실제 제약을 조회한다. AI 탐지는 현재 요청별 잠금과 존재 조회를 사용하므로 모든 탐지에 DB UNIQUE가 있다고 단정하지 않는다. 이 기준 작성 과정에서 제약·스키마를 변경하지 않는다. WebSocket을 종단 간 exactly-once로 표현하지 않는다.
