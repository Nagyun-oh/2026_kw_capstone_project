# 2026/11/03 — 1건/초 기준 측정 중간 결과·정합성 문제

[로컬 목차](README.md) · [구조화된 진단 증거](evidence/20261103-ai-result-commit-race.json)

## S — Situation

v2 소량 연결 r13 PASS 후 실제 로컬 스택에서 1건/초·120초·3회 기준 측정을 시작했다. 회차마다 30초 워밍업을 제외하고 실제 관리자 브라우저의 수신·DOM·대표 테이블과 DB·UTC 커밋 trace·Kafka lag를 대조했다. 탐지 품질 평가나 장애 주입 실험은 아니다.

## T — Task·Target

- 같은 코드·이미지·도구·fixture·측정 계약으로 3회 모두 PASS인지 확인한다.
- 평균·p50·p95·p99·최대·실제 표본 수를 기록하고 요청·저장·AI 완료·알림 연결을 대조한다.
- 실패·미확인이 발생하면 다음 회차와 부하 증가를 보류한다. 판정 기준을 소급 완화하거나 DB·오프셋을 초기화하지 않는다.

## A — Action

| 회차 | 자동 판정 | 측정 HTTP / DB / AI 완료 | 탐지 probe | HTTP p95 | 비고 |
| --- | --- | --- | --- | --- | --- |
| [r14](runs/20261103T141850+0900-local-e2e-rps1-r14.md) | PASS | 121 / 121 / 121 | 12 | 5.521ms, 일반 요청 109개 | 요청→AI 완료 p95 573.380ms, 두 출처 수신·DOM·대표 행 확인 |

| r16 | 미실행 | 미측정 | 미측정 | 미측정 | r15의 정합성 문제 조사로 보류 |

요청률은 설정값이며 실제 송신 수를 따로 보존한다. 이번 두 회차는 k6 일반 요청 109개와 probe 12개로 총 121개를 보냈다. HTTP 통계는 일반 요청에 대한 값이며 probe·브라우저 지연과 섞지 않는다.

두 회차의 요청률·기간·워밍업·계약/fixture/실행기/앱 소스 해시·도구·이미지는 같았다. 시작 시 DB 로그/탐지 수는 r14가 4,750/365, r15가 4,902/395로 자연 증가했다. DB를 비우지 않았으며 이를 완전히 동일한 데이터 상태로 표현하지 않는다.

## R — Result

**3회 단계 통과는 미완료다.** r14의 단일 PASS를 전체 단계 PASS로 표시하지 않는다. r15의 자동 INCONCLUSIVE와 원본을 보존하고, 별도 로그·코드 검토에서 AI 결과 처리 오류를 확인했다. 지연이 빠르더라도 처리 정합성을 충족했다고 판단할 수 없다.

두 누락 ID에 대해 AI 서비스는 `result sent`를 기록했지만, 결과 Consumer에는 같은 시간대 `LogEntry not found` 오류가 두 건 발생했다. Consumer가 업무 예외를 로그로만 남기고 반환하므로 오류 처리기까지 예외가 전달되지 않는다.

로그 ID 5000의 관측 순서는 다음과 같다. 시각은 원본 증거의 UTC다.

```text
05:24:52.188Z        AI 요청 발행 로그
05:24:52.213Z        결과 Consumer: LogEntry not found
05:24:52.343333149Z  원본 로그 커밋 후 trace
```

`LogService`는 원본 로그 저장 트랜잭션이 끝나기 전에 AI 요청을 발행하고, `ThreatService`는 결과 수신 시 READ_COMMITTED에서 원본 행을 조회한다. 빠른 AI 결과가 커밋을 앞지르는 순서 경쟁이 원인으로 강하게 지지된다. 예외 로그 자체에는 logId가 없으므로 시간 순서·미완료 ID·AI 전송 로그·코드를 함께 근거로 사용한다. 4968의 오류 로그는 커밋 후 trace보다 약 2ms 늦어 SELECT의 정확한 시작 시각은 직접 증명하지 못했다.

**Kafka lag 0은 처리 완료를 보장하지 않았다.** r15의 최종 표본들은 lag 0이었지만 AI 완료는 119건이었다. 자동 보고서의 ‘종료 후 lag 0 두 번 확인 부족’ 문구는 실행기의 `final_lag`가 AI 완료·DOM까지 포함한 복합 조건인 데서 나온다. 실제 lag가 계속 남았다고 해석하지 않는다.

## T — Trouble·다음 작업

- 이번 발견은 처리량 포화가 아니라 커밋·결과 도착 순서 및 오류 처리의 정합성 문제다. 브로커 메시지 소실이나 AI 모델 미실행으로 단정하지 않는다.
- 백엔드 앱·DB·Consumer 오프셋은 수정하지 않았다. 로컬 서비스는 기동 상태로 유지했다.
- 다음은 AI 요청 발행의 커밋 경계와 결과 Consumer의 재시도·복구 방식을 설계하고 회귀 테스트로 재현·검증하는 작업이다.
- 단순 커밋 후 콜백은 선행 조회 경쟁을 줄여도 DB 커밋과 Kafka 발행 사이의 프로세스 종료를 보장하지 않는다. 재시도·전송 확인 또는 outbox의 적용 범위를 함께 판단한다.
- 수정 후 새 회차 3개를 같은 부하·fixture·계약으로 측정하고, 이번 회차는 개선 전 결함 재현 증거로 연결한다. 서로 다른 코드의 회차를 같은 3회 단계 집계로 합치지 않는다.
- 장애 주입·중복 전달·재시작 시나리오와 최대 처리량 조사는 여전히 미실행이다.
