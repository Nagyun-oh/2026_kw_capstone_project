# 실험 진행과 기록 가이드

## 1. 목적과 현재 준비 범위

DualGuard의 성능·장애 복구·데이터 정합성·보안·차단 정책을 같은 조건에서 재현하고, 결과와 한계를 포트폴리오 근거로 남긴다.

진행 절차·기록 틀과 기존 서버 실행기를 유지하고 [v2 측정 계약](local/e2e-plan-v2.md)에 맞춘 별도 실행기·WAF·브라우저 계측을 구현했다. r15에서 확인한 [결과 처리 정합성 문제](local/20261103-rps1-baseline-review.md)를 보완한 뒤 2026/11/03 로컬 1건/초 120초·3회 단계와 추가 3·5건/초 각 1회 예비 확인이 PASS했다. 다음은 EC2 실행·계측 준비다. 모의 검증, 격리 복구, 실제 브라우저 E2E와 부하 한계를 구분한다.

**현재 담당 범위는 서버의 처리량·HTTP/API/비동기 지연·자원·적체·장애 복구·데이터/알림 정합성이다.** WAF·AI 탐지율·오탐률·공격 유형별 판정은 보안 팀원이 검증한다. 조사할 병목이나 포트폴리오 사례를 미리 정하지 않는다. DB 조회·집계·페이지 처리·저장·락·커넥션, AI·Kafka·WAF·알림 등 실측에서 드러난 구간을 추가 계측·재현으로 좁히고 개선한다. 최신 결과·가설·다음 작업은 환경별 목차에 기록한다.

v2는 탐지 품질 평가를 추가하지 않고 AI·WAF 분기의 서버 처리·실제 브라우저 수신·알림 DOM 표시를 분리한다. JuiceShop HTTP를 대시보드 응답 시간으로 설명하지 않는다. 기존 v1과 별도 run_e2e.py를 구분하며 실제 v2 소량 연결 PASS를 본 부하·장애 검증 완료로 표현하지 않는다.

```text
공통 계측·기록 준비
  ├─ 로컬: 예비 확인 → 기준 측정·장애 검증 → 병목·결함 개선 → 동일 조건 재측정
  └─ EC2: 환경 준비·예비 측정 → 기준 측정·장애 검증 → 병목·결함 개선 → 동일 조건 재측정
```

실험 자료는 아래 두 환경별 목차에서 찾아본다. 로컬에서 절차·복구와 계측을 검증한 뒤 EC2 측정을 준비한다. 각 환경에서 병목·결함이 관측됐을 때 개선과 재측정을 연결하며, 문제가 발견되지 않았다면 관측 범위와 한계를 기록한다.

| 환경별 목차 | 목적 | 현재 상태 |
| --- | --- | --- |
| [로컬 테스트 · 병목 개선 · 동일 조건 재측정](local/README.md) | 계측·실험 절차 검증, 로컬 기준 측정·장애 복구·개선 비교 | 격리 복구 r02·1건/초 3회 단계·3·5건/초 각 1회 예비 확인 PASS. 로컬 추가 부하 마무리 |
| [EC2 테스트 · 병목 개선 · 동일 조건 재측정](ec2/README.md) | 배포 환경에서 별도 기준선을 측정하고 장애·개선 효과 검증 | 시작 전. 환경·부하 발생기·실행 도구·목표 준비 필요 |

공통 절차는 이 문서, 진행 상태·관측한 문제·회차·전후 비교 연결은 환경별 목차에서 관리한다. 관측 → 원인 가설 → 추가 계측·재현 → 개선 선택 → 동일 조건 재측정을 기본 흐름으로 삼는다. 문제가 없거나 원인이 미확정이면 그 상태를 기록한다. **로컬 결과와 EC2 결과를 직접 비교해 개선율로 발표하지 않는다.** 개선 전후 비교는 같은 환경의 기준선을 사용한다.

| 진행 원칙 | 적용 방법 |
| --- | --- |
| 환경 | 로컬에서 절차·복구를 검증하고 EC2에서 배포 성능을 측정한다. 부하 발생기는 가능하면 대상 서버와 분리한다. |
| 시간 | 팀원 사용 시간과 겹치지 않는 실행 구간을 실험 전에 기록한다. 특정 시각은 아직 확정하지 않았다. |
| 부하 | 저부하 예비 측정 후 정식 상한·목표·중단 기준을 정한다. |
| 데이터 | 정상 부하와 라벨이 있는 공격·차단 실험을 구분한다. 데이터 파일·버전·정답 기준은 실험별로 확정한다. |

환경 구성은 [로컬 인프라](../operations/local_compose.md), [AWS 배포](../operations/aws_deployment.md), WAF 보고 의미는 [동기화 계약](../design/05_waf_sync.md)을 참고한다.

## 2. 기록 위치와 실험 ID

[기록 템플릿](experiment-template.md)을 복사해 실험별 보고서를 만든다. 실행기 구현 전에는 같은 양식을 직접 작성한다. 에이전트가 실험을 수행할 때도 관측한 사실과 증거를 이 양식에 기록한다.

```text
docs/testing/
  README.md
  experiment-template.md
  claude-handoff.md              # 현재 상태·다음 작업 전달문
  local/
    README.md                   # 로컬 단계·실험·개선 전후 비교 목차
    runs/<실험-ID>.md            # 로컬 회차 보고서·단계 집계
    evidence/                   # 로컬 공유 증거 JSON
    preliminary-summary.md      # 초기 예비 실험 정리
    runner-v1.md                # 초기 실행기와 구현 이력
    path-migration-20261105.json # 기존 경로·이동 경로·해시 대조표
  ec2/
    README.md                   # EC2 단계·실험·개선 전후 비교 목차
    runs/                       # EC2 실행 후 생성할 보고서
    evidence/                   # EC2 실행 후 생성할 공유 증거
build/test-runs/<실험-ID>/       # 실행 시 생성할 원본 결과; 기존 build/ ignore 규칙 적용
  manifest.json                 # 환경·목표·실행 조건
  metrics.json                  # 측정값·단위·측정 구간·자료 출처
  events.jsonl                  # 장애 주입·복구·예외 시각
  raw/                          # 필요한 원본 결과
```

위 환경별 `runs/`와 결과 파일은 실제 실행 시 생성하며, 시작 조건 미충족으로 중단된 실행도 기록한다. 파일 생성만으로 실험 성공을 판단하지 않는다. 세 JSON 파일 이름은 공통 실행기의 저장 규약이다.

환경별 구분은 폴더·목차와 실험 ID의 `local`·`ec2`로 한다. 2026/11/05 사용자 요청으로 기존 로컬 보고서·공유 증거·초기 정리를 `local/`로 모았고, 이후 로컬 실행기도 `local/runs/`에 보고서를 생성한다. 기존 `build/test-runs/` 원본·증거 JSON의 내용과 해시는 보존했다. 과거 JSON 안의 경로는 [이동 대조표](local/path-migration-20261105.json)로 확인한다. 실행·분석 후 해당 환경 목차에 회차·판정·관측한 문제·기준선·다음 작업을 갱신한다. 이 목차 갱신은 현재 실행기가 자동 처리하지 않으므로 문서 작업으로 수행한다.

- ID 형식: `YYYYMMDDTHHMMSS+0900-<환경>-<시나리오>-rNN`. 예: `20261031T140000+0900-local-normal-smoke-r01`은 설명용이며 실제 실행 기록이 아니다.
- 사람이 읽는 보고서의 제목·본문 날짜는 `YYYY/MM/DD`(예: `2026/10/31`), 시각은 한국 시간의 `YYYY/MM/DD HH:MM:SS +09:00`으로 표시한다. 제목은 `실험 기록: YYYY/MM/DD — 실험 제목`으로 작성하고 실험 ID는 실행 정보에 남긴다. 실행 준비 시각과 실제 부하 시작·종료 시각은 구분한다.
- 원본 JSON·JSONL의 관측·수집 시각은 UTC 또는 오프셋 포함 ISO 8601로 보존한다. 보고서에서만 표시 형식을 변환하며, 시간대 없는 값에 임의로 9시간을 더하지 않는다. 시간대 없는 DB 값의 해석 기준도 남긴다.
- 실험 ID·파일명은 `/`가 경로 구분자로 해석되므로 기존 `YYYYMMDDTHHMMSS+0900` 형식을 유지한다.
- 실행 전에 같은 ID의 보고서·원본 디렉터리가 없는지 확인한다. 재시도는 새 ID와 회차를 사용하고 이전 ID를 연결한다.
- 이전 보고서를 성공 결과로 덮어쓰지 않는다. 같은 실행의 진행 사항은 종료까지 이어서 기록하되, 목표 변경이 필요하면 이유를 남기고 새 실험으로 분리한다.
- `build/` 결과는 Git에서 제외되고 정리 시 사라질 수 있다. 보고서에는 수치도 남기며, 보존할 증거는 비밀값 제거 후 별도 보관 위치·파일 해시·보관 기한을 기록한다. 경로만 남긴 뒤 원본을 삭제하지 않는다.
- 보고서·공유 증거에는 토큰·쿠키·비밀번호·개인정보를 남기지 않는다. 실 IP는 식별용 별칭으로 치환하되 같은 대상의 대응 관계를 유지한다. 자동 커밋·push·외부 업로드는 하지 않는다.

## 3. STAR-T 작성 규칙

이 프로젝트에서는 Task·Target·Trouble을 명시적으로 분리한다. 아래 여섯 항목을 사용하는 프로젝트 기록 양식이며, 명칭을 다른 STAR-T 해석으로 바꾸지 않는다.

| 항목 | 내용 | 작성 시점 |
| --- | --- | --- |
| Situation | 현재 구조·상태, 실험 배경, 가설 | 실행 전 |
| Task | 이번에 확인하거나 해결할 한 가지 과제 | 실행 전 |
| Target | 측정 항목·합격 기준·중단 기준·복구 완료 기준 | 실행 전 |
| Action | 실제 명령·조건·장애 주입·복구·변경 내역 | 실행 중 |
| Result | 실측값·판정·근거·미측정 항목·비교 결과 | 실행 후 |
| Trouble | 예상 밖의 문제·관측 근거·원인 가설·대응·미해결 사항 | 발견 시 |

의도적으로 중단한 AI 서비스는 Action의 장애 주입이다. 중단 중 예상하지 않은 DB 저장 실패가 생겼다면 Trouble에 별도로 기록한다. 원인을 검증하지 못했으면 가설로 남긴다.

## 4. 실행 전 체크리스트

- [ ] 고유 ID와 보고서를 만들고 Situation·Task·Target을 작성했다.
- [ ] 대상 환경·주소·실행 구간·부하 발생기·담당자를 확정했다. 이번에 요청받은 실험 범위에 서버 중단·설정 변경이 포함되는지 확인했다.
- [ ] 대상 서버의 실제 앱 SHA·이미지 태그/가능한 digest·WAF 설정 버전을 확인했다. 실행기 저장소 SHA와 로컬 변경 파일도 별도로 기록했다.
- [ ] 서버 사양, Docker 제한, 모델 lock/실제 파일 검증 여부, 데이터 버전·라벨·건수, DB 시작 건수를 기록했다. T3 사용 시 CPU 크레딧 모드·잔량도 기록한다.
- [ ] DB 구조·컨테이너 상태·모델 로딩·기본 요청 처리를 확인했다. 모델 준비 요청은 본 측정과 구분한다.
- [ ] 테스트 IP의 현재 블랙리스트 등록·차단 제외 상태와 요청 경로를 확인했다. 임의의 전달 헤더로 소스 IP를 위조하지 않는다.
- [ ] 수집 방법·간격·시계 기준·집계 구간·최종 대기 시간을 정했다. 지연·오류율·자원·복구 시간 중단 기준을 숫자로 정하거나 미정이면 본 실험을 시작하지 않는다.
- [ ] 중단 서비스·변경 설정·테스트 IP의 시작 상태와 원상복구 절차를 기록했다. DB·볼륨 삭제나 전체 초기화를 일반 복구 절차로 사용하지 않는다.
- [ ] 다른 실험·배포·팀원 요청이 측정 구간에 섞이지 않도록 조정했다.

예비 실험의 예시는 로컬 정상 요청 1회/초, 60초다. 계획 참고 건수 60회와 실제 전송 수를 따로 기록한다. 이 예시는 성능 보장이나 확정된 본 실험 목표가 아니다. 기록 검증의 합격 기준은 필요한 결과 파일·관측값이 누락 없이 남고 실제 처리 결과와 대조되는지로 정한다.

## 5. 무엇을 어떻게 구분해 측정할까

| 항목 | 정의·주의사항 |
| --- | --- |
| HTTP | 목표/실제 전송률, 완료·시간 초과·미전송 수, 응답 시간 평균·p50·p95·p99·최대값(ms), 예상 밖의 오류율. 요청 건수·측정 기간·반복 회차를 함께 남기고, 정상 요청의 403과 차단 시나리오의 예상한 403을 구분한다. |
| 비동기 지연 | 요청 발생 → 로그 저장 / 탐지 저장 / 알림 발송 / 브라우저 수신을 별도 구간으로 정의한다. 수집할 수 없는 구간은 미측정으로 둔다. |
| Kafka | 실제 group·topic·partition별 lag와 수집 시각, 장애 복구 후 적체 해소 시간. 다른 consumer group이나 topic 수치를 합쳐 처리 건수로 단정하지 않는다. |
| 서버 | 컨테이너별 CPU·메모리와 호스트·Docker 자원 한도, 디스크 여유. 도구 단위와 샘플링 간격을 남긴다. |
| 정합성 | 이번 실행의 수집·분석 대상, 정상 처리·정책상 제외·미처리·DLT·중복을 구분한다. 이전 데이터나 전체 누적 건수만으로 성공 판정하지 않는다. |
| WAF | 목록 변경 → 보고된 적용 확인 → 실제 HTTP 차단·해제 확인을 분리한다. 보고가 끊겼다고 차단 해제로 판단하지 않는다. |
| 탐지 품질 | 라벨이 있는 데이터의 WAF·AI·OR 탐지 결과와 AND 자동 차단 결과를 구분한다. 성능 테스트 결과를 탐지 정확도로 설명하지 않는다. |

기본 도구는 k6, 주기적인 Docker stats, Kafka CLI, SQL·관리자 API다. 현재 실행기는 읽기 전용 SQL·AI 완료 로그 대조와 연속 lag 관측도 지원한다. v2의 실제 브라우저·출처별 알림·DOM 계측은 로컬 회차에서 확인했다. 일반 API 수집은 기존 세션·CSRF 인증을 사용하며, 메트릭을 얻으려고 보호를 해제하지 않는다.

- 실행 식별값으로 요청을 추적하고, 탐지 연결에는 서버가 생성한 `requestId`를 사용한다. 클라이언트의 실험 식별값이 서버 요청 ID를 대체하지 않는다.
- HTTP 요청 수, WAF·AI 개별 탐지 수, 통합 위협 그룹 수, 알림 ID·revision 수는 서로 다를 수 있다. 알림 발송과 브라우저 수신도 같은 사건으로 세지 않는다.
- WAF OR AI는 기록·통합 알림, 같은 요청의 WAF AND AI 및 IP 일치는 자동 등록의 현재 기준이다. 서로 다른 요청의 결과를 같은 IP라는 이유로 합쳐 자동 차단 성공으로 처리하지 않는다.
- 측정값 0, 미측정, 해당 없음은 구분한다. 근거가 없는 값과 예시 수치를 실측 칸에 넣지 않는다. 자동 차단으로 부하 IP가 막히면 정상 부하 결과의 유효성을 다시 판단한다.
- 기존 `dev_tools/scripts/e2e_test.py`는 현재 인증·메시지 형식·실험별 식별과의 호환성을 먼저 확인해야 한다. 그대로 현재 파이프라인의 검증기로 간주하지 않는다.

### p50·p95·p99 수집·기록 기준

앞으로의 성능·부하 실험에서는 HTTP 응답 시간의 평균·p50·p95·p99·최대값을 함께 수집·보고한다. p50은 중앙값으로 평소 응답 수준을 보여준다. 비동기 지연을 측정할 때도 HTTP와 분리된 구간·자료로 기록한다. 적은 표본의 p99는 가장 느린 소수 요청의 영향을 크게 받으므로 요청 수·측정 기간·반복 회차를 함께 해석하고, 한 번의 예비 측정으로 성능을 보장하지 않는다.

2026/11/01에 p99 자동 수집·저장·보고를 구현했다. 새 실행은 k6 summary에서 평균·p95·p99·최대값을 읽어 `metrics.json`의 `http_avg_ms`, `http_p95_ms`, `http_p99_ms`, `http_max_ms`와 Markdown 보고서에 ms 단위로 기록한다. 이후 r07·r09에서 저부하 실측도 확인했다. v2는 현재 요청률의 p99를 참고값으로 보존하고 합격 상한과 구분한다.

- [x] `normal-smoke.js`의 `summaryTrendStats`에 `p(99)` 추가.
- [x] `metrics.py`에서 p99를 `http_p99_ms`로 정규화하고, 누락은 0이 아닌 미측정으로 보존.
- [x] `run_experiment.py`의 결과·보고서에 평균·p95·p99·최대값과 단위(ms)를 반영하고 판정 기준을 `arrival-smoke-v3`로 갱신.
- [x] 구형·신형 summary, p99 누락·비정상 값, 보고서 출력을 모의 테스트로 검증.

p99 수집과 성능 합격 상한 설정은 구분한다. 상한을 판정하는 실험은 실행 전에 p95·p99 기준을 정한다. 새 실행의 `arrival-smoke-v3`는 평균·p95·p99·최대값 확보를 필수로 확인하며 지연 상한을 임의로 적용하지 않는다. 누락·null·문자열·불리언·음수·비유한 수치는 미측정으로 보존하고, 확인된 다른 기준 위반이 없으면 `INCONCLUSIVE`로 판정한다. 숫자 0은 유효한 측정값으로 보존한다.

기존 `arrival-smoke-v2` 등으로 생성한 r01~r05 보고서·원본·판정은 그대로 유지한다. 과거 p99는 미측정이며 기존 평균·p95·최대값으로 복원하지 않는다. 과거 summary를 새 코드로 읽는 경우에도 없는 p99를 채워 넣지 않는다.

이후 p50도 결과 저장·보고에 연결했다. k6의 `med`를 `metrics.json`의 `http_p50_ms`로 보존하며 비동기 구간은 원본 지연 표본에서 `p50_ms`를 계산한다. p50은 합격 상한을 추가하지 않는 참고 지표다. 누락·잘못된 값은 null/미측정으로 남기고 기존 `arrival-smoke-v3`와 `local-load-v1`의 판정은 유지한다. 과거 보고서·원본은 소급 수정하지 않는다.

## 6. 실행·종료·복구

1. 시작 상태를 확인하고 실행 상태를 `RUNNING`으로 바꾼다.
2. 실제 명령·도구 버전·시작 시각과 측정 구간을 기록한다. 비밀 인수와 요청 본문은 제거한다.
3. 장애는 한 번에 한 종류씩 주입한다. 예정 시각과 실제 시각·결과를 각각 남기고 예상 밖의 사건은 Trouble에 기록한다.
4. 중단 기준에 도달하면 부하를 멈추고 중단 이유·관측값을 보존한다. 반복 실행으로 실패 기록을 지우지 않는다.
5. 성공·실패·중단과 관계없이 종료와 복구 확인을 진행한다. 어떤 서비스를 중단했는지 확인하고 시작 상태에 맞춰 복구한다.
6. 기본 health·요청 처리, 관련 Kafka 처리·lag, WAF 보고·실제 접근 상태를 시나리오에 맞게 재확인한다. 명령 종료 코드만으로 복구 완료를 단정하지 않는다.
7. 최종 대기 시간까지 처리·미처리·DLT·중복을 집계하고 Result·복구 결과를 작성한다. 복구 실패·미확인이면 이를 그대로 남긴다.

현재 정상 요청 실행기는 예외·중단 시 가능한 범위에서 증거를 저장하고 자신이 실행한 부하 프로세스를 종료한다. 서비스 중단·재시작 기능은 없다. 장애 시나리오를 확장할 때 복구를 구현·검증하며, 강제 종료 등으로 완료하지 못하면 다음 실행 전에 수동으로 확인한다. 복구를 무조건 보장한다고 표현하지 않는다.

| 구분 | 값과 의미 |
| --- | --- |
| 실행 상태 | `PLANNED`: 계획 / `RUNNING`: 실행 중 / `COMPLETED`: 실행 종료 / `ABORTED`: 시작 후 중단 / `BLOCKED`: 시작 조건 미충족 |
| 판정 | `NOT_EVALUATED`: 미평가 / `PASS`: 사전 기준 충족·필수 증거 확보·필요한 복구 확인 / `FAIL`: 기준 위반 확인 / `INCONCLUSIVE`: 기준 미정·증거 부족·실험 오염 등으로 결론 불가 |

`COMPLETED`는 성공 판정이 아니다. 장애 테스트의 예상한 서비스 오류는 그 자체로 실패가 아니며, 사전에 정한 처리·복구 기준으로 판정한다. 실제 기준 위반은 다른 지표의 미측정 때문에 숨기지 않고 기록한다.

## 7. 비교와 보고

- 로컬 개선 전↔로컬 개선 후, EC2 개선 전↔EC2 개선 후를 각각 비교한다. 로컬에서 적용한 개선이 포함된 상태로 EC2를 시작했다면 그 상태가 EC2의 첫 기준선이며, 로컬 결과를 EC2 개선 전 수치로 대신 쓰지 않는다.
- 개선 전 실행 ID를 연결하고 코드 변경 외에 장비·모델·DB 규모·입력·준비 요청·수집 방식·집계 구간이 같은지 확인한다.
- 단계적·순간·지속 부하, 장애·정합성·보안·WAF 검증은 서로 다른 시나리오로 기록한다. 반복 횟수와 실행 순서도 남긴다.
- 조건이 다르면 비교 제한을 명시한다. 비교 가능한 실행만 개선율을 계산하고, 이전 값이 0이거나 증거가 없으면 백분율을 만들지 않는다.
- 한 번의 결과를 일반적인 처리 한계나 안정성 보장으로 확대하지 않는다. 관측한 병목, 검증한 원인, 아직 검증하지 못한 가설을 구분한다.
- 보고서는 조건·목표·핵심 수치·Trouble·판정·미측정·복구 결과·증거 위치를 포함한다. 전체 원본 로그를 보고서나 대화에 붙이지 않는다.
- 정리·커밋 대상은 비밀값 없는 문서와 필요한 작은 증거로 한정하고, 원본·데이터·모델·비밀값의 Git 제외 여부를 확인한다.


로컬 초기 실행기의 판정·명령·구현 이력은 [로컬 v1 안내](local/runner-v1.md), 현재 E2E는 [v2 실행 가이드](local/e2e-runner.md)를 따른다.
