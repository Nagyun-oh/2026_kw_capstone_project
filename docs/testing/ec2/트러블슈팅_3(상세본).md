## 1. S — Situation: 실제로 어떤 문제가 보였는가

트러블슈팅_2의 남은 지연을 DB 쪽에서 줄일 수 있는지 보려고 r14~r16의 DB 관측을 다시 읽었다. outbox 관련 SQL은 문장 평균 1ms 미만이라 원인이 아니었다. 대신 DB 시간 상위에 파이프라인이 아닌 **대시보드 조회**가 있었다.

- 입력·요청·트래픽 조건: 5 RPS 측정 중 실행기의 브라우저가 대시보드를 열어 둔 상태. 대시보드는 10초 자동 갱신과 WebSocket 알림 수신 때마다 로그·위협·블랙리스트 목록을 다시 조회한다. [자동 갱신·알림 갱신](../../../frontend/src/Dashboard.js#L70) · [목록 조회](../../../frontend/src/hooks/useSecurityData.js#L368)
- 관측한 증상: 검색 조건 없는 로그 목록 10건 조회가 회차당 68~75회 실행됐고 평균 116.5~140.3ms였다. 호출마다 1.6만~1.8만 행을 검사했고 모든 호출이 인덱스를 쓰지 않았다.
- 사용자·업무 영향: 관리자 화면의 갱신마다 DB가 테이블 전체를 읽는다. 검사 행 수가 회차마다 약 600씩, 즉 새로 쌓인 로그 수만큼 늘었다. 로그가 쌓일수록 조회가 느려지는 구조다.
- 재현 방법·재현 여부: 부하 없는 시점의 `EXPLAIN ANALYZE`로 재현했다. 18,199행 전체 스캔 후 정렬, 30.1ms.

### 3-3. 확인한 원인과 증상의 연결

```text
created_at 인덱스 없음 → ORDER BY created_at DESC LIMIT 10도 전체 행을 읽고 상위 10건을 정렬
  → 갱신마다 약 26MB 스캔 → 로그 수에 비례해 느려짐(회차당 +600행, 부하 중 평균 128ms)
```

- 확인한 원인: 정렬 컬럼에 인덱스가 없다. 엔티티는 `ddl-auto: validate`라 인덱스를 만들거나 검사하지 않고, 초기 스키마에도 없었다.
- 아직 검증하지 못한 부분: EC2 운영 DB에서의 적용 후 효과와 부하 중 수치. 단순 비례 추정으로는 로그 100만 건이면 부하 없이도 1초 이상이지만 측정하지 않았다.

### 5-2. 핵심 변경

1. **역할·호출 순서:** API·서비스·리포지토리 코드는 바꾸지 않았다. Hibernate가 만드는 SQL은 그대로이고 MySQL 옵티마이저가 새 인덱스를 선택한다.
2. **변경 전후 핵심 코드:**

```sql
-- 기존 DB용 (docs/db/add-network-logs-created-at-index.sql)
SET SESSION lock_wait_timeout = 5;
ALTER TABLE network_logs
    ADD INDEX idx_network_logs_created_at (created_at),
    ALGORITHM = INPLACE,
    LOCK = NONE;
```

```java
@Table(
        name = "network_logs",
        indexes = @Index(name = "idx_network_logs_created_at", columnList = "created_at")
)
```

3. **동작 원리:** B-tree 인덱스는 `created_at` 순서로 정렬돼 있다. `ORDER BY created_at DESC LIMIT 10`은 인덱스 끝에서부터 10개를 읽고 멈춘다. InnoDB 보조 인덱스는 PK를 포함하므로 10번의 PK 조회로 나머지 컬럼을 가져온다.
4. **설계 근거:** 전체 스캔·정렬이라는 확인된 원인을 정렬 순서가 이미 갖춰진 접근 경로로 바꾼다.
5. **경계·실패 처리:** `ALGORITHM=INPLACE, LOCK=NONE`이라 인덱스를 만드는 동안 로그 저장을 막지 않는다. 시작·종료 시 짧은 메타데이터 잠금이 필요하며, 5초 안에 얻지 못하면 실패하고 변경 없이 끝난다. 같은 SQL을 다시 실행하면 1061 오류가 나므로 적용 전 존재 여부를 확인한다. `ddl-auto: validate`는 인덱스를 검사하지 않으므로 앱 배포 순서와 무관하다.
6. **트레이드오프:** 로그 저장마다 보조 인덱스 항목 하나(약 수십 바이트)를 추가로 기록한다. 검색 조건이 드문 IP라면 인덱스 역순으로 많은 행을 거르며 읽을 수 있다. 현재 기본 화면은 조건이 없다.

## 8. 학습 정리·다음 작업

- **핵심 개념:** `ORDER BY ... LIMIT`은 정렬 순서를 가진 인덱스가 있으면 앞에서 N건만 읽고 멈출 수 있다. 없으면 전체를 읽고 정렬한다. InnoDB 보조 인덱스에는 PK가 들어 있어 나머지 컬럼을 PK로 조회한다.
- **실제 코드 연결:** JPA `Sort`와 Specification이 만든 SQL은 그대로 두고 DB 접근 경로만 바꿨다. `ddl-auto: validate`는 인덱스를 만들지 않으므로 엔티티 선언과 SQL 파일을 함께 관리해야 한다.
- **다른 방식이 필요한 조건:** 자주 쓰는 검색 조건(IP 등)이 생기면 `(ip_address, created_at)` 같은 복합 인덱스를 검토한다. 깊은 페이지 이동이 많아지면 OFFSET 대신 커서 방식을 검토한다.
- **사용자가 설명할 수 있어야 할 부분:** 실행 계획의 `Table scan`과 `Index scan (reverse)` 차이, 온라인 DDL과 메타데이터 잠금, 커밋 내구성 설정(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`)을 낮추지 않은 이유.
- **다음 작업:** 저장소 변경(엔티티·스키마·기존 DB용 SQL)을 문서와 함께 커밋·PR로 반영한다. 인덱스 효과에는 앱 배포가 필요 없다. 남은 후보는 매 갱신마다 전체 행 수를 세는 건수 조회(평균 약 21ms, 행 수에 비례)와 조회 때마다 탐지 전체를 집계하는 그룹 위협 조회다. AI 경로 p95 감소와 대시보드 부하의 관계는 별도 실험(대시보드 열림·닫힘 비교)이 있어야 말할 수 있다. 그룹 위협 조회(조회 때마다 전체 집계)와 총 건수 조회는 후속 후보로 남긴다.
