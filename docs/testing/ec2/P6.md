## 전후 비교 원칙

구간의 평균 실행 시간은 다음처럼 계산한다. Performance Schema 시간은 picosecond이며 ms 변환에는 10억으로 나눈다.

```text
구간 실행 수 = 이후 COUNT_STAR − 이전 COUNT_STAR
구간 누적 실행 시간(ms) = (이후 SUM_TIMER_WAIT − 이전 SUM_TIMER_WAIT) / 1,000,000,000
구간 평균(ms) = 구간 누적 실행 시간 / 구간 실행 수
```

구간 실행 수가 0이면 평균은 null이다. 전체 기간 평균끼리 빼거나 lifetime 최대값을 구간 최대·p95·p99로 사용하지 않는다. 서버 식별값·uptime 변화, 계수 감소·first_seen 변경·digest 행 소실, 2,000행 상한·overflow bucket을 확인하며 불완전한 차이를 성공으로 처리하지 않는다. [MySQL statement summary](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-statement-summary-tables.html), [시간 단위](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-timing.html).

digest·전역 상태는 **DB 전체의 관측 구간**이다. 앱의 배경 polling·다른 트래픽·관측기 자체의 쿼리도 포함한다. `observer_candidate`는 JSON_OBJECT·Performance/Information Schema 관련 형태를 서버에서 분류한 참고 표식이며 완벽한 출처 판정은 아니다. 표시가 false인 BEGIN·COMMIT·ROLLBACK·SET 등에도 관측 비용이 섞일 수 있다. 이 차이를 실험 요청만의 쿼리 수라고 주장하지 않는다.

락·트랜잭션은 수집 순간의 변하는 표본이며, 두 표본이 0이어도 전체 구간에 경합이 없었다고 증명하지 않는다. [MySQL 잠금 정보의 일관성](https://dev.mysql.com/doc/refman/8.0/en/innodb-information-schema-internal-data.html).

outbox 저장소는 created_at·available_at·published_at을 직접 `UTC_TIMESTAMP(6)`로 기록한다. 따라서 대기 시간은 DB의 UTC 시각끼리, 발행 지연은 같은 행의 created_at→published_at으로 계산한다. 다른 테이블 시간대나 JDBC 설정을 바꾸지 않는다. 집계가 감소하거나 잘못된 시각이 있으면 비교를 미확인으로 남긴다. 구간 내 신규 발행이 없으면 지연 평균도 null이며, 기존 보존 행의 467ms를 이번 회차 결과로 복사하지 않는다.

## 읽기 전용·인증

모든 조회는 SELECT당 3초 제한과 `START TRANSACTION READ ONLY`·`ROLLBACK`을 사용한다. 조회 프로세스는 12초, 전체 SSH 호출은 최악의 순차 실패를 고려해 200초 제한이다. 실제 호출은 별도 프로세스로 제한 시간을 적용하며 수집 비용을 기록한다. 실패 시 자신의 조회만 종료한다.

기본은 앱 계정이다. 접근 실패 시 컨테이너의 기존 root 인증으로 읽기 전용 재시도하며 `--app-only`로 재시도를 끌 수 있다. timeout·출력 상한·구문/컬럼/테이블 오류는 root로 반복하지 않는다. 실패 메시지 대신 MySQL 오류 번호·SQLSTATE만 남긴다.

이번 실제 환경에서는 앱 계정이 일부 통계 SELECT 권한이 없었고(1142) PROCESS 권한도 없었다(1227). 컨테이너 root 환경값 인증도 실패했다(1045). 사용자가 기존 비밀번호로 직접 root 로그인 가능한 것을 확인한 뒤 **숨김 입력으로 1회 수집 프로세스 안에서만 사용**해 해결했다. 비밀번호나 권한을 변경한 것은 아니다.

숨김 입력은 직접 열린 로컬 터미널에서만 지원한다. 비밀번호를 SSH와 컨테이너 프로세스의 표준 입력으로 전달하며 argv·파일·manifest·보고서에 기록하지 않는다. 다음 실행에서 필요하면 다시 입력해야 한다. 이미 로그인한 MySQL 세션은 수집기가 공유하지 않는다.

## 실행과 E2E 연결

프로젝트 루트 PowerShell에서 계획만 확인:

```powershell
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_db.py --dry-run
```

현재 환경에서 사용한 숨김 입력 방식:

```powershell
$ec2Host = '<현재 EC2 주소>'
$ec2Key = '<기존 개인 키 파일 경로>'
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_db.py --collect-only --ssh-host $ec2Host --identity-file $ec2Key --prompt-db-root --round 4
```

검증된 기존 호스트 키 별칭이 필요한 경우 P4 방식을 따른다. 실제 run ID로 outbox를 좁히려면 `--run-id <ID>`를 추가한다. `--interval`은 앞 스냅샷이 끝난 뒤 기다리는 시간이며 실제 스냅샷 사이 시간에는 조회 비용이 더해진다.

E2E 실행기의 EC2 전용 전후 hook은 **워밍업 정리 후·측정 시작 전**과 **측정·최종 drain 후·대표 테이블 조회 전**에 연결했다. 자격 증명을 메모리에만 가진 `db_observer` 수집 함수를 주입한다. 로컬 실행은 원격 DB hook을 호출하지 않는다. 실제 부하가 포함된 전체 연결은 P7~P8에서 확인한다.
