# EC2 단계 부하 · 한계 RPS와 병목 개선 계획

**2026/11/07 · 계획(미실행)** · [EC2 진행 목차](README.md) · [P8 측정 계약](P8.md)

트러블슈팅_5 배포·재측정 다음 작업이다. 같은 t3.large 사양에서 부하를 단계적으로 올려 처리 한계와 병목 근거를 찾는다. 이후 애플리케이션·아키텍처 쪽 변경으로 개선하고 같은 사양에서 다시 잰다. 아래 병목·개선 후보는 현재 근거로 세운 가설이다. 실제 측정에서 드러난 문제를 따라가며, 미리 정한 해결책에 맞추지 않는다.

## 1. 목표와 범위

- **포트폴리오 주제:** 부하 테스트 기반 병목 개선. 같은 자원에서 병목을 찾고 구조로 해결한 사례를 보인다.
- **사양 고정:** 인스턴스 확장은 개선으로 내세우지 않는다. 필요하면 참고 측정으로만 기록한다.
- **AI 코드 제약:** `AI_new/` 코드는 AI 담당 팀원 영역이라 수정하지 않는 것을 전제로 한다. 개선은 백엔드·Kafka·배포 구성에서 찾는다. AI 코드에서 확인한 문제는 근거와 함께 담당자에게 제안한다.
- **지표:** 입력 RPS 대비 처리 완료 EPS, 토픽별 lag 추이, 구간별 p50·p95·p99, 컨테이너·호스트 자원, 회차별 정합성.

## 2. 현재 근거 (5 RPS 관측)

정식 PASS 회차 r14~r23 중 r20을 뺀 9회의 `metrics.json` `resource_peaks`·`lag_maxima` 값이다. 컨테이너 CPU는 `docker stats` 기준이며 100%가 vCPU 1개다.

| 관측 | 값 | 의미 |
| --- | --- | --- |
| AI 컨테이너 CPU 최대 | 54.7~105.9% | 5 RPS에서 이미 vCPU 1개에 가까움 |
| AI 컨테이너 메모리 최대 | 호스트 대비 10.2~10.4% | 복제 시 메모리 여유는 별도 확인 |
| 백엔드 컨테이너 CPU 최대 | 10.9~95.9% | 95.9%는 백엔드 재생성 32초 뒤 시작한 r14 한 회차. 나머지 8회는 10.9~61.6%. 짧은 순간의 표본 최대값이다 |
| `ai-service-group` lag 최대 | 19~28 | 측정 중 0~27에서 오르내리고 증가 추세는 없다. 부하가 끝나면 0으로 돌아온다. AI 소비자의 자동 커밋 주기(kafka-python 기본 5초) × 5 RPS ≈ 25와 같은 규모라, 실제 적체보다 크게 보이는 값으로 본다 |
| 호스트 CPU 사용률(2 vCPU) | 측정 구간 평균 62.8~73.7%, 표본 최대 90.2~97.4%, steal 0.5~7.4% | r17~r19·r21~r23 `/proc/stat` 차분. 아래 측정 도구 부담이 포함된 값이다 |
| Kafka 컨테이너 CPU | 측정 구간 평균 24.5~78.9%, 순간 최대 145.9~188.4% | r22 대조 결과, 실행기의 lag 조회 CLI(`kafka-consumer-groups`, 120초에 7회·회당 약 6초)가 도는 동안 45~142%, 그 외에는 3.4~5.4%였다. 브로커 자체 부하는 작다. 급등은 같은 컨테이너에서 JVM을 띄우는 CLI 두 가지(측정용 lag 조회, 15초 healthcheck `kafka-topics --list`)에서 온다. lag 조회를 줄인 개정 3 재측정에서 호스트 CPU가 약 0.21 vCPU 줄었다. [트러블슈팅_6](<트러블슈팅_6(상세본).md>) |
| 발생기 PC CPU | 측정 구간 평균 9~11% | 5 RPS에서는 여유가 있다 |
| DB 컨테이너 CPU 최대 | 43.2~77.9% | COMMIT 평균 약 5ms(부하 중) |
| 측정 후 최종 처리 대기 | r14~r16 21.5~37.2초 | 측정이 끝난 뒤 적체 해소에 걸린 시간 |
| AI 처리 추정 | 평균 약 87ms 이하 | r21~r23 로그 커밋 → AI 결과 커밋 평균 239.0ms에서 outbox 발행 평균 152.0ms를 뺀 값. AI 전달·추론·결과 저장이 모두 들어 있다. 직접 측정 아님 |

코드·설정에서 확인한 사실:

- `AI_new/main.py`의 Kafka 소비는 스레드 하나에서 메시지를 한 건씩 처리한다. 한 건마다 모델 3개로 예측하고, transformer 예측은 `RLock`으로 직렬화된다. 결과 전송마다 `producer.flush()`로 완료를 기다린다.
- AI 소비자는 `enable_auto_commit=True`다. 처리 도중 프로세스가 종료되면 결과가 빠질 수 있다. 처리량과 별개인 정합성 후보다.
- Compose에 토픽 파티션 설정이 없어 브로커 기본값(1개)을 쓴다. 측정의 lag 기록에도 partition 0만 나온다.
- AI 서비스는 호스트 포트 `127.0.0.1:8000`을 고정으로 연다. `--scale`로 바로 복제할 수 없다.

**현재 판단:** 5 RPS는 처리가 밀리지 않는 구간이다. 모든 회차가 600건 저장·AI 완료였고, lag는 증가 추세 없이 0으로 돌아왔다. 서버 p95도 3초 목표보다 훨씬 낮다. 한계 RPS는 아직 측정하지 않았다.

**예상 한계 (추정, 미측정, 2026/11/07 개정 3 기준선으로 갱신):** 개정 3 기준선 r30~r32에서 5 RPS 호스트 CPU 평균은 61.3~66.0%(약 1.28 vCPU)였다. 이 안에는 부하와 무관한 기본 부하가 들어 있다. healthcheck CLI, 대기 중인 JVM, 실행기의 원격 수집이 그 예다. 기본 부하 B를 따로 재지 않았기 때문에, 선형 가정에서 2 vCPU 중 약 1.9 vCPU를 쓸 수 있다고 보고 범위로 계산한다.

| 기본 부하 B 가정 | CPU 포화 추정 |
| --- | ---: |
| 0 (모든 CPU가 부하에 비례) | 약 7.4 RPS |
| 0.4 vCPU | 약 8.6 RPS |
| 0.6 vCPU | 약 9.6 RPS |

지연은 포화 전부터 늘기 시작한다. 이전 판의 "측정 도구 부담을 줄이면 약 11~12 RPS"는 healthcheck 같은 기본 부하를 빠뜨린 낙관적 추정이었다.

**기본 부하 측정 결과 (2026/11/08):** 부하 없이 3분 동안 잰 호스트 CPU는 약 0.42 vCPU였다. 그중 Kafka healthcheck(`kafka-topics --list`, 15초 간격)가 약 0.22 vCPU다. B ≈ 0.42로 계산하면 **CPU 포화는 약 8.7 RPS**로 추정한다. healthcheck 부담을 없애면 약 9.9 RPS다. 지연은 그보다 앞서 늘기 시작할 것이다. [유휴 기준 증거](evidence/20261108-idle-baseline-kafka-healthcheck.json) · [트러블슈팅_6 6-3](<트러블슈팅_6(상세본).md>)

AI 컨테이너는 5 RPS에서 평균 약 0.3~0.43 vCPU를 쓴다. 단일 스레드라도 한 코어를 온전히 쓰면 초당 12건 이상 처리할 수 있어, 호스트 CPU가 먼저 포화될 가능성이 크다. 선형 가정, 회차당 약 13개 표본, 유휴 기본 부하를 작게 본 가정이 들어간 추정이므로 단계 부하로 확인한다.

## 3. 선행 조건

1. 완료(2026/11/07): `d45960f2` 배포 후 트러블슈팅_5 재측정 r24~r29를 마쳤다. 다만 이 계획의 기준선은 6번의 측정 방식 개선 뒤 같은 이미지에서 다시 잰다.
2. **예열:** backend를 재생성하면 기록하지 않는 준비 회차를 한 번 돌린 뒤 측정한다. r24·r27처럼 재생성 직후 첫 회차는 180초를 기다려도 느렸다.
3. 아래 한계 판정·안전 중단 기준을 실행 전에 확정한다. 실행 후 소급 변경하지 않는다.
4. 현재 실행기 계약은 1·3·5 RPS로 고정돼 있다. 5 RPS를 넘는 부하는 새 계약 개정·프로필이 필요하다. CLAUDE.md의 "10 RPS 이상은 별도 상한·안전 조건 확인 후 진행"을 따른다.
5. 발생기 PC(k6 + Chrome)의 CPU·메모리·네트워크가 먼저 한계에 닿지 않는지 함께 감시한다.
6. **측정 도구 부담을 먼저 줄인다.** 지금 lag 조회 CLI가 측정 구간의 약 1/3 동안 vCPU 1개 가까이를 쓴다. 그대로 두면 한계가 2~3 RPS 낮게 보일 수 있다. 조회 주기를 늘리거나 가벼운 방식으로 바꾸고, 바꾼 방식으로 5 RPS 기준선을 다시 잰다. 2026/11/07 실행기 개선(계약 개정 3, 부하 중 60초 간격) 적용과 새 기준선 r30~r32 측정을 마쳤다. 호스트 CPU가 약 0.21 vCPU 줄었다.
7. **기본 부하 측정:** 완료(2026/11/08). 유휴 호스트 CPU 약 0.42 vCPU, 그중 Kafka healthcheck 약 0.22 vCPU. healthcheck 경량화는 [트러블슈팅_7](<트러블슈팅_7(상세본).md>)에서 진행한다. 운영 설정이 바뀌므로 배포 뒤 유휴 측정과 5 RPS 기준선을 다시 잰다.
8. 팀원이 쓰지 않는 시간에 측정한다. CPU 크레딧은 unlimited 모드라 고부하가 길면 추가 과금이 생길 수 있다. 측정 전후 크레딧을 기록한다.

## 4. 단계 부하 설계 (초안)

| 항목 | 초안 |
| --- | --- |
| 단계 | 5 → 7 → 9 → 11 → 13 RPS. 예상 한계가 7~12 RPS라 2 RPS 간격으로 올린다. 한계 판정이 나오면 다음 단계로 가지 않는다 |
| 회차 | 단계마다 120초 예비 1회. 기준선, 한계 직전, 한계 단계는 정식 3회 |
| 한계 판정 | 측정 중 처리 완료 EPS가 입력의 95% 미만으로 유지, lag 지속 증가, 서버 p95 3초 초과, 종료 후 해소 60초 초과 중 하나. AI 그룹 lag는 5초 자동 커밋 때문에 톱니 모양이 생긴다. 그래서 순간값이 아니라 구간별 최저값의 증가 추세로 판단한다 |
| 안전 중단 | 기존 P8 중단 조건 + 호스트 가용 메모리 1GiB 미만, 컨테이너 재시작, 해소 300초 초과, HTTP 오류율 1% 초과 |
| 관측 | `progress.jsonl` 처리 완료 EPS·lag, 컨테이너·호스트 자원, 발생기 자원, 구간별 백분위, DB 문장·COMMIT, outbox·알림 발행 |

## 5. 개선 후보 (측정 후 선택)

| 순서 | 후보 | 변경 위치 | 확인할 점 |
| --- | --- | --- | --- |
| 1 | AI 체류 시간 외부 계측: 백엔드가 `ai-result-topic` 레코드 생성 시각을 기록 | 백엔드 | AI 코드 변경 없이 요청 발행 ACK → 결과 생성 시간을 분리한다. 같은 EC2 호스트 시계를 쓴다 |
| 2 | `ai-request-topic` 파티션 확장 + AI 컨테이너 복제(같은 consumer group) | Kafka·Compose | AI 코드 변경 없음. 포트를 열지 않는 두 번째 서비스 정의가 필요하다. 2 vCPU에서 CPU 경쟁으로 효과가 작을 수 있다. 리밸런스 시 auto-commit 중복·누락과 백엔드 결과 저장 멱등성을 확인한다. 파티션은 늘리기만 가능하고 줄일 수 없다 |
| 2-1 | AI 추론 계층을 별도 인스턴스로 분리 + 파티션·AI 컨테이너 확장 | 인프라·Compose·배포 | 같은 호스트의 CPU 경쟁이 병목으로 확인될 때 검토한다. AI 코드는 `KAFKA_BOOTSTRAP_SERVERS`만 바꾼다. Kafka 외부 리스너·보안 그룹 제한, 배포 워크플로·수집 실행기의 다중 호스트 지원, 추가 비용이 필요하다. 자원이 늘어나므로 "같은 사양" 비교가 아니다. 비교하려면 같은 비용 조건(예: 큰 인스턴스 1대 vs 작은 인스턴스 2대)으로 맞추고 버스트 기준선 차이를 기록한다. 소비자 한 개의 직렬 처리 한계는 분리만으로는 그대로다 |
| 3 | 부하에서 드러나는 백엔드 구간: 로그 소비, outbox 발행의 메시지별 ACK 대기, 알림 발행 | 백엔드 | 측정에서 해당 구간 지연·적체가 확인될 때만 진행한다 |
| 선행 | 측정 도구 부담 축소: lag 조회 주기·방식 | 실행기 | Kafka CPU의 대부분은 lag 조회 CLI였다. 브로커 자체는 5 RPS에서 3~7% 수준이다. 축소 전후 5 RPS 기준선을 같은 방식으로 다시 잰다. [트러블슈팅_6](<트러블슈팅_6(상세본).md>) |
| 제외 | COMMIT 내구성 설정 완화, 인스턴스 확장 | — | 장애 시 탐지 기록 유실 위험, 같은 사양 비교 원칙과 맞지 않음 |

AI 담당자에게 전달할 제안(근거 첨부): 여러 건 묶음 추론, 결과 전송 `flush()` 묶기, 처리 완료 후 오프셋 커밋.
