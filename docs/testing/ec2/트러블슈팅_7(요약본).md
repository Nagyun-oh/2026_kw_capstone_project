# EC2 Kafka healthcheck 상시 CPU 부담 · 핵심 요약

**2026/11/08 · 배포·재측정 완료 · 목표 4개·참고 지표 충족** · [상세 해결 과정](<트러블슈팅_7(상세본).md>)

## 문제 상황 흐름

```mermaid
flowchart LR
    A["dockerd: 15초마다 healthcheck"] --> B["kafka 컨테이너에서 kafka-topics --list"]
    B --> C["JVM 기동, 회당 약 2.9초·3.8 CPU초"]
    C --> D["부하가 없어도 상시 약 0.22 vCPU 사용"]
    D --> E["처리 한계 추정 약 1.2 RPS 감소"]
```

## 문제 상황

- 측정 도구의 lag 조회를 줄였는데도(트러블슈팅_6) Kafka 컨테이너 CPU가 기대만큼 줄지 않았다. lag 조회가 없는 시점에도 CPU가 튀었다.
- 원인은 Kafka의 Docker healthcheck였다. 15초마다 `kafka-topics --list`(JVM을 새로 띄우는 Java CLI)를 실행했다.
- 부하 없이 3분 동안 cgroup 누적값으로 재 보니, 유휴 서버 CPU 0.42 vCPU 중 약 0.22 vCPU가 이 healthcheck였다. 2 vCPU 서버 용량의 약 11%다. [유휴 기준 증거](evidence/20261108-idle-baseline-kafka-healthcheck.json)

## 해결 과정

- healthcheck 결과가 어디에 쓰이는지 확인했다. backend·ai·fluent-bit이 기동할 때 Kafka가 준비될 때까지 기다리는 용도뿐이고, unhealthy가 돼도 자동으로 재시작하는 장치는 없다.
- 확인 방식(`kafka-topics --list`, 브로커가 실제로 응답하는지)은 그대로 두고 간격만 15초에서 60초로 늘렸다. 기동 직후 120초 동안만 5초 간격(`start_interval`)으로 확인해 의존 서비스의 대기 시간은 유지했다.
- 연속 실패 횟수를 12회에서 3회로 줄여 unhealthy 판정까지 걸리는 시간은 이전과 같은 약 3분으로 맞췄다.

## 결과

2026/11/08 PR #112(`1b6d818c`)로 배포한 뒤 같은 3분 유휴 측정으로 확인했다. 배포 전에 정한 목표 4개를 모두 충족했다. [재측정 증거](evidence/20261108-idle-after-kafka-healthcheck.json)

| 지표 | 배포 전 | 배포 후 | 목표 |
| --- | ---: | ---: | --- |
| Kafka 컨테이너 유휴 평균 CPU | 23.75% | **9.68%** | 10% 이하 충족 |
| 유휴 서버 CPU | 0.42 vCPU | **0.28 vCPU** | 0.30 이하 충족 |
| healthcheck 실행 (3분) | 12회 | 3회 | 약 60초 간격, 실패 0 충족 |
| 기동 순서 | — | Kafka healthy 직후 backend·ai·frontend 기동 | 충족 |

- 회당 비용(약 2.7초·3.8 CPU초)은 그대로이고 실행 횟수만 1/4이 됐다. 서버 CPU 감소분 0.143 vCPU가 Kafka 컨테이너 감소분과 같아, 다른 원인이 섞이지 않았다.
- 5 RPS 기준선 r33~r35(준비 회차 포함, 3회 PASS)에서도 부하 중 서버 CPU가 평균 63.8% → 58.0%로 낮아졌다. 지연 지표도 대부분 좋아졌지만 측정 시각·재시작 차이가 있어 healthcheck 효과로 주장하지 않는다. [기준선 비교 증거](evidence/20261108-healthcheck-5rps-baseline-comparison.json)
- CPU 포화 추정은 약 8.7 RPS에서 약 9.2 RPS로 늘었다(선형 가정). 실제 한계는 단계 부하로 확인한다.

## 해결과정에 쓴 방법을 써야만 했던 이유

- **포트 확인(`nc -z`)으로 바꾸지 않음:** 가장 가볍지만 "포트가 열림"과 "요청을 처리할 수 있음"은 다를 수 있다. 기동 순서 보장이라는 healthcheck의 목적을 약하게 만든다.
- **간격만 늘리고 기동 중에는 짧게:** 결과가 기동 순서에만 쓰이므로 운영 중에는 자주 확인할 이유가 없다. 그렇다고 간격만 늘리면 기동 대기가 길어져서 `start_interval`로 기동 구간만 짧게 확인했다.
- **수치로 고른 대안:** 회당 CPU를 실측했기 때문에 간격을 4배로 늘리면 상시 부담이 약 1/4이 된다는 효과를 미리 계산하고 고를 수 있었다.
