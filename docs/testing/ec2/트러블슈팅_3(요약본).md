# EC2 대시보드 로그 목록 전체 스캔 · 핵심 요약

**2026/11/07 · EC2 인덱스 적용 및 같은 부하 재측정 완료(PASS)** · [상세 해결 과정](<트러블슈팅_3(상세본).md>)

## 문제 상황 흐름

```mermaid
flowchart LR
    A["대시보드 10초 갱신·알림 수신"] --> B["GET /api/v1/logs (최신 10건)"]
    B --> C["ORDER BY created_at DESC LIMIT 10"]
    C --> D["created_at 인덱스 없음"]
    D --> E["매번 전체 행 스캔 + 정렬"]
    E --> F["로그가 쌓일수록 조회 지연 증가"]
```

## 문제 상황

- AI outbox 개선 뒤 남은 지연을 DB에서 줄일 수 있는지 보려고 5 RPS 세 회차의 DB 관측을 다시 분석했다. 파이프라인 SQL은 문장 평균 1ms 미만이었고, DB 시간 상위는 **관리자 대시보드의 로그 목록 조회**였다. [트러블슈팅_2](<트러블슈팅_2(상세본).md>)
- 최신 10건만 보여 주는 조회가 회차당 68~75회 실행됐고 평균 **127.7ms**였다. 호출마다 **1.6만~1.8만 행 전체**를 검사했다. 검사 행 수는 회차마다 새로 쌓인 로그 수(약 600)만큼 늘었다.
- 대시보드는 10초마다, 그리고 알림을 받을 때마다 목록을 다시 조회한다. 로그가 쌓일수록 갱신마다 DB 비용이 커지는 구조였다.

## 해결 과정

- EC2 DB에서 읽기 전용으로 인덱스·쿼리 원문·실행 계획을 확인했다. `network_logs` 인덱스는 PK와 `request_id`뿐이었다. 실행 계획은 **18,199행 전체 스캔 → 정렬 → 10건**이었다(부하 없음 30.1ms). [실행 계획·쿼리 원문](evidence/20261107-dashboard-query-explain.json)
- 정렬 컬럼에 인덱스가 없는 것이 원인이었다. 엔티티는 `ddl-auto: validate`라 인덱스를 만들지 않고, 초기 스키마에도 빠져 있었다.
- 의미를 바꾸지 않는 최소 변경으로 **`network_logs(created_at)` 인덱스**를 선택했다. 엔티티 선언, 새 DB 스키마, 기존 DB용 온라인 DDL을 함께 맞췄다.
- 운영 DB에 적용하기 전에, EC2와 같은 MySQL 8.0.46 임시 컨테이너에서 새 DB 초기화와 기존 DB 이전을 모두 재현했다. 적용 스크립트의 판정 로직도 같은 방식으로 시험했다. [격리 검증](evidence/20261107-network-logs-index-preapply-verification.json)

- 세 회차 모두 600건 저장·AI 완료, 확인 요청 12건 두 출처 알림, lag 0, 원복을 확인했다. 앱 이미지·실행기·부하 조건·브라우저 버전은 기준선과 같았고, 재측정 직전 외부 로그 유입은 0건/초였다.
- AI 경로 p95도 세 회차 모두 낮아졌다(로그 커밋 → AI 결과 커밋 526.3 → 432.8ms). 다만 WAF 쪽은 소폭 늘었고 측정 시각·DB 규모가 달라, **인덱스 효과로 주장하지 않는다.**
- 로그 목록 쿼리 자체의 p99는 측정하지 않았다. DB 관측은 구간별 평균만 비교할 수 있다. 파이프라인 p99도 낮아졌지만(요청 → AI 결과 커밋 1,204.4 → 946.0ms) 같은 이유로 원인 미확인이다. [단계별 p99 추이](runs/20261107-ec2-p99-trend-ts1-ts4.md)
- **격리 검증 (합성 18,000행, EC2 결과 아님):** 18,000행 전체 스캔 17.6~34.0ms → 인덱스 역순 10행 **0.06~0.08ms**. 상위 10건 결과 동일, 새 DB 초기화 성공, 적용 스크립트는 적용·재실행 생략을 정확히 판정했다.
- 백엔드 컴파일과 로그 관련 테스트 7개가 통과했다.
- **EC2 적용 (2026/11/07 16:26 +09:00):** 온라인 DDL 552.7ms, 오류 없음. 같은 조회가 적용 직전 **18,562행 전체 스캔 45.7ms**에서 직후 **인덱스 역순 10행 0.095ms**로 바뀌었다(부하 없음, 각 1회). 같은 스냅샷에서 인덱스 사용·미사용 결과가 같았다. 앱 배포·설정 변경은 없었다. [EC2 적용 증거](evidence/20261107-network-logs-index-operating.json)
- 판정 기준(부하 중 호출당 검사 행 100 이하, 결과 동일, 파이프라인 P8 기준 유지)은 EC2 적용 전에 정했고 모두 충족했다.

## 해결과정에 쓴 방법을 써야만 했던 이유

- **인덱스 vs 정렬을 `id`로 변경:** 둘 다 전체 스캔을 없앤다. 정렬을 바꾸면 DDL은 필요 없지만 API의 정렬 의미가 바뀐다. 인덱스는 코드·의미를 그대로 두고 원인인 접근 경로만 고친다.
- **조회 빈도 줄이기는 보류:** 호출 수는 줄어도 호출당 비용이 행 수에 비례하는 문제는 남는다.
- **커밋 내구성 설정은 바꾸지 않음:** `COMMIT`도 DB 시간 합계가 컸지만(평균 3ms), 설정을 낮추면 장애 시 탐지 기록을 잃을 수 있다.
- **온라인 DDL + 짧은 잠금 대기:** 운영 중 로그 저장을 막지 않는다. 잠금을 못 얻으면 변경 없이 실패하게 했다.
