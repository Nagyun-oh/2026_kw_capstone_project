## 1. S — Situation: 실제로 어떤 문제가 보였는가

## 3. A — Action: 원인을 좁힌 과정

### 3-1. 수집 흐름

```text
WAF Nginx 요청 종료 → access.log 한 줄 기록(버퍼 없음)
  → Fluent Bit tail 입력이 읽어 청크에 저장
  → [SERVICE] Flush 주기(0.5초)마다 출력 플러그인으로 전달      ← 의심 구간
  → Kafka(log-topic / waf-detection-topic) → 백엔드 Consumer → DB 커밋
```

| 순서 | 실제 파일·설정 | 역할 | 경계 |
| --- | --- | --- | --- |
| 1 | [`nginx-logging.conf.template`](../../../waf/nginx-logging.conf.template) | `access_log`를 `buffer`·`flush` 옵션 없이 바로 기록 | WAF 컨테이너 |
| 2 | [`fluent-bit.conf` `[INPUT] tail`](../../../waf/fluent-bit.conf) | 읽기 위치는 `DB`, 버퍼는 `storage.type filesystem`으로 named volume에 보관 | 수집기 |
| 3 | [`fluent-bit.conf` `[SERVICE] Flush`](../../../waf/fluent-bit.conf#L4) (변경 전 0.5) | 엔진이 Flush 주기마다 쌓인 레코드를 출력으로 넘김 | 수집기 |
| 4 | `[OUTPUT] kafka` | 모든 복제 ACK(`acks -1`)로 전송 | Kafka |

## 5. A — Action: 적용 방법·복구

변경은 설정 한 줄이다.

```ini
[SERVICE]
    Flush        0.1   # 기존 0.5
```

EC2에는 저장소 파일을 직접 고치지 않는다. 작업 트리를 깨끗하게 유지하고 다음 배포의 checkout과 충돌하지 않기 위해서다.

1. 보조 스크립트가 EC2 HEAD와 `compose.aws.yaml`·`waf/fluent-bit.conf` 무변경을 확인한다.
2. 저장소 설정에서 `Flush` 줄만 바꾼 사본을 `/home/ubuntu/.config/dualguard/fluent-bit.conf`에 만들고, 다른 줄이 같은지 대조한다.
3. 기존 운영 오버라이드(`compose.alerts.override.yaml`)에 수집기 설정 파일 연결만 추가하고, 같은 이미지로 `fluent-bit`만 다시 만든다.
4. 연결된 설정, 이미지, 12초 뒤 재시작·오류 로그를 확인한다. 실패하면 이전 오버라이드로 되돌려 다시 만든다. 이어서 WAF 상태, 필수 lag 0, 서비스 9개 실행을 확인한다.

## 8. 학습 정리·다음 작업

- 로그 수집기도 배치 주기를 가진다. Flush는 처리량과 지연 사이의 설정값이며, 저부하에서는 대기 시간이 그대로 지연이 된다.
- 대기 주기를 줄이면 평균은 주기 차이의 절반만큼, 최대 지연은 주기 차이만큼 줄어든다. 이번에 평균 210ms(확인 요청 구간 200ms), p95 356ms가 줄어 분포 모양과 일치했다. 비용은 수집기 CPU 최대치 약 1%p 증가였다.
- 운영: EC2는 호스트 사본 + 운영 오버라이드로 0.1을 유지한다. 저장소 `waf/fluent-bit.conf`도 0.1로 바꿨으니 다음 배포 PR에 포함한다. 배포 뒤에는 호스트 오버라이드의 수집기 항목을 정리할 수 있다.
- 다음 후보(AI 알림 p95 1초 미만): 커밋 직후 발행기 깨우기(outbox·알림 조회 대기 제거, ②·③), 요청 구간 210ms 꼬리 위치 확인(④), AI 처리 구간 계측(②), AI 팝업 갱신 약 90ms(⑤).
