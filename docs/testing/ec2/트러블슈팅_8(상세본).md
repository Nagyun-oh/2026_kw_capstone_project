## 1. S — Situation: 실제로 어떤 문제가 보였는가

트러블슈팅_7까지 측정 도구와 Kafka healthcheck 부담을 줄인 뒤, 처리 한계(knee)를 찾으려고 계약 개정 4로 단계 부하 모드를 만들었다.

- **입력 조건:** 7 → 9 → 11 → 13 RPS, 단계마다 120초 1회. 한계 신호는 처리 완료 비율 < 0.95, 미처리 기울기 > 입력 RPS × 0.05건/초, 서버 p95 > 3초, 측정 후 60초 내 미해소 중 하나다.
- **처음 관측:** 7·9·11 RPS는 PASS였다. 13 RPS(r01)에서 서버 p95 3,128.8ms로 첫 한계 신호가 나왔다.
- **이상한 점:**
  - 13 RPS에서도 처리량은 입력을 따라갔다(완료 비율 1.014, 송신 종료 6.5초 뒤 미처리 0).
  - 지연이 계속 높은 게 아니라 5초 구간별로 약 200ms와 2~3.4초를 오가는 "혹" 모양이었다.
  - 그 회차에서 DB 수집 명령 1회가 실패했다.
- **재현 시도:** 실패 원인 기록을 보완한 뒤 같은 11 RPS를 다시 쟀다(r02). p95가 586ms → 2,030ms로 바뀌었고, DB 수집이 다시 실패해 INCONCLUSIVE가 됐다.
- **영향:** 같은 조건에서 결과가 재현되지 않으면 한계 RPS를 정할 수 없다. 측정 도구가 대상 서버를 흔들면 한계가 실제보다 낮게 보이고, 그 정도가 실험할수록 커진다.

| --- | --- | --- | --- |
| 13 RPS 서버 p95 3,128.8ms, 호스트 CPU 평균 89.5%(최대 99.1%) | 측정 120초 | step-rps13-r01 | 1회 |


변경 전 쿼리의 핵심(요지):

```sql
SELECT JSON_OBJECT(... 'wafRows',(SELECT COUNT(*) FROM waf_detections w
                      WHERE BINARY w.request_id=BINARY n.request_id))
FROM network_logs n LEFT JOIN request_alerts a
  ON BINARY a.alert_key=BINARY CONCAT('request:',n.request_id)
WHERE BINARY JSON_UNQUOTE(JSON_EXTRACT(IF(JSON_VALID(n.raw_log),n.raw_log,'{}'),'$.test_run')) = <회차 ID>
ORDER BY n.id;
```

### 3-2. 가설과 검증

| 원인 가설 | 지지·반박 근거 | 확인 결과 | 상태 |
| --- | --- | --- | --- |
| 13 RPS는 실제 처리 한계 | 처리 완료 비율 1.014·미처리 기울기 음수. 지연이 연속이 아니라 혹 모양 | 처리량은 유지. 교란 시점에 대기열이 생기는 모양 | 보류 → 기각(4-5 재측정) |
| lag CLI가 교란 | 13 RPS에서 회당 8.9초(5 RPS 부하 중 4.8~5.8초). 가장 큰 혹이 두 번의 CLI와 겹침 | 상관 확인. 수집 실패 뒤 시각 미갱신으로 25초 만에 재실행되는 실행기 결함 확인 | 확인(부분 원인) |
| DB 수집 실패는 연결 지연(3초 연결 제한) | 실패 명령이 3,232ms에 끝나 `--connect-timeout=3`과 비슷 | 보완 후 오류 코드 `3024/HY000`(실행 시간 초과) | 기각·정정 |
| 수집 쿼리 자체가 무겁고 데이터와 함께 커짐 | 측정 중 쿼리 중앙값 1.0초 → 2.0~2.2초, 오늘 테이블 +28% | `EXPLAIN ANALYZE`로 두 비용 확인(아래) | 확인 |

**EC2 읽기 전용 실행 계획(r02 회차 기준, 유휴, 2026/11/08 13:12 KST):**

| 단계 | 기존 쿼리 | 비고 |
| --- | --- | --- |
| 회차 행 찾기 | `network_logs` 전체 37,152행 테이블 스캔 + JSON 해석 → 1,352행, 약 586ms | 테이블 전체 크기에 비례 |
| `wafRows` 부분쿼리 | 행마다 `waf_detections` 인덱스 851행 전체 탐색, 0.649ms × 1,352회 ≈ 877ms | `BINARY` 캐스트로 동등 조회 불가. 회차 행 수 × 탐지 건수에 비례 |
| 알림 조인 | 해시 조인(851행) | 작음 |
| 합계 | 약 1,644ms(클라이언트 포함 1,343ms 측정 시점 별도) | 부하 중에는 2~3초 |

- **컬럼 확인:** `request_id`·`alert_key`는 이미 `utf8mb4_0900_bin`(이진 정렬)이라 `BINARY` 캐스트가 정확성에 기여하지 않으면서 인덱스만 막고 있었다.
- **`created_at` 저장 시각대:** `datetime(6)`에 KST 벽시계로 저장됨을 확인했다(log 36476 `12:53:39.646` vs DG_TRACE 커밋 `03:53:39.655Z`). DB `time_zone`은 SYSTEM(UTC)이다.
- **같은 5 RPS의 도구 부담:** 측정 120초 안의 명령 실행 시간 합계(벽시계)는 DB 쿼리 약 10초, lag CLI 약 8초, `docker stats` 약 30초였다.

### 3-3. 확인한 원인과 증상의 연결

```text
실험마다 network_logs가 1,000건 넘게 쌓임
  → 수집 쿼리(8~10초마다)가 전체 행 JSON 해석 + 행마다 탐지 테이블 재탐색
  → DB CPU를 수 초씩 사용(부하가 클수록 더 느려짐) + 60초마다 lag CLI(JVM, 수 초)
  → 남는 CPU가 적은 11~13 RPS에서 AI 소비가 밀려 대기열이 수 초짜리 혹이 됨
  → 서버 p95 급등, 회차마다 결과가 달라짐
  → 쿼리가 3초 제한을 넘으면 수집 실패 → 판정 불가, lag 시각 미갱신으로 CLI가 겹쳐 교란 증폭
```

- **확인한 원인:** 측정 실행기의 DB 수집 쿼리 비용(데이터 누적에 비례)과 부하 중 lag CLI가 측정 대상 CPU를 썼다. 수집 실패 시 lag 조회 시각을 갱신하지 않는 결함이 교란을 키웠다.
- **아직 검증하지 못한 부분:** 13 RPS r01의 지연 혹 중 측정 구간 시작 직후(0~5초) 혹은 9~13 RPS 모두에서 보였고 원인을 확정하지 않았다.

## 2-2. A — 구조와 원인 가설

**AI 서비스 처리 구조** ([`AI_new/main.py`](../../../AI_new/main.py) `kafka_worker`, 읽기만 함):

해석:

1. **비교에 배포 직후 예열이 섞였다.** 배포로 backend가 15:07에 재시작됐고, 준비 회차(1 RPS·90건) 뒤 바로 측정했다. backend CPU가 49 → 30 → 24%로 회차마다 줄었다(개선 전 약 14%). r05는 호스트 CPU 97.9%로 포화돼 처음부터 끝까지 수 초짜리 지연 혹이 이어졌다. 트러블슈팅_5에서 본 "재생성 직후 첫 회차가 느림"과 같은 모양이다. 그래서 개선 전후가 완전히 같은 조건은 아니다.
2. **예열 영향이 작은 회차만 봐도 개선이 없다.** r06·r07의 AI 구간 p95는 1,782ms로 개선 전 1,881ms와 거의 같다(목표 −50%). AI 구간 p50(133 → 211ms)과 로그 수집 p95(204 → 344ms)는 오히려 늘었다.
3. **AI가 쓰는 CPU는 그대로였다.** AI 컨테이너 CPU는 개선 전후 모두 약 66%다. 메시지당 약 50ms CPU라는 일의 양이 같다. 소비자를 둘로 나눠도 서버 전체가 2 vCPU에 묶여 있어 새로 쓸 수 있는 CPU가 거의 없었다. 개선 전에도 호스트 CPU가 평균 81%(약 1.6 vCPU)였다.
4. **가설 기각:** 대기열은 "소비자가 하나라서" 생긴 것이 아니다. "호스트 CPU가 순간 포화될 때 AI 처리가 밀려서" 생긴다. 직렬 소비자는 코어 하나의 약 65%만 쓰고 있어 자체 상한(초당 약 20건)에 닿지 않았다. 병렬화는 CPU 여유가 있을 때만 처리량을 늘린다. 이 서버에서 지연을 줄이려면 요청당 총 CPU를 줄이거나(AI 묶음 추론 — AI 코드 변경 필요, 측정 도구의 `docker stats` 등) CPU를 늘려야 한다(같은 사양 비교 밖).

남은 확인:

- backend가 충분히 예열된 상태에서 13 RPS 3회를 다시 재면, A가 효과 없음(중립)인지 손해인지 가를 수 있다. 미실행.
- **되돌리기(2026/11/08 사용자 결정·배포 완료):** 효과가 없고 메모리를 약 600MiB 더 쓰므로 저장소 기본값을 `AI_UVICORN_WORKERS=1`로 되돌렸다(커밋 `8c5e4780`, 배포 `b56b5cab`, 15:58 KST). 프로세스 수 설정은 다시 실험할 수 있게 남겼다. 배포 후 읽기 전용 확인 결과는 다음과 같다([증거](evidence/20261108-ai-workers-rollback-check.json)).
  - AI 프로세스 1개, AI 메모리 1.215GiB → 610MiB, 서버 가용 4.78GB
  - 파티션 2개를 소비자 1개가 모두 배정받음(lag 0)
- **병렬 소비 자체는 동작했다:** A 기간 파티션 오프셋은 파티션 0이 48,049 → 50,431(2,382건), 파티션 1이 0 → 2,486건이었다. 메시지 4,868건이 49:51로 고르게 나뉘어 두 소비자가 실제로 나눠 처리했다. 그런데도 지연이 줄지 않았으므로, 병목은 소비자 수가 아니라 CPU라는 결론을 뒷받침한다.
- **파티션 2개는 유지한다.**
  - 파티션은 줄일 수 없다. 줄이려면 토픽을 지우고 다시 만들어야 해서 남은 메시지와 오프셋을 잃는다.
  - 소비자 하나가 두 파티션을 모두 받아 읽으므로 동작에 문제가 없다.
  - 메시지 키가 logId라 요청 간 순서가 필요 없어서, 파티션이 둘이어도 처리 결과가 같다.
  - 파티션 하나가 늘어 생기는 부담(로그 파일·조회 대상 하나 추가)은 무시할 수준이다.
  - backend 선언(`AiRequestTopicConfig`)도 실제 토픽과 같은 2로 둔다. 1로 바꾸면 기동할 때마다 KafkaAdmin이 파티션 수 불일치를 기록한다.
  - 나중에 AI를 별도 인스턴스로 옮기거나 CPU가 늘면, 프로세스 수만 2로 올려 바로 나눠 소비할 수 있다.
