# EC2 테스트 · 병목 개선 · 동일 조건 재측정

최종 갱신: **2026/11/05**

[공통 가이드](../README.md) · [로컬 테스트](../local/README.md) · [AWS 배포](../../06_aws_deployment.md)

EC2에서는 실제 배포 환경의 별도 기준선을 측정하고, 확인된 병목·결함 개선 후 같은 EC2 조건에서 다시 측정한다. **현재 EC2 실험은 시작 전이며 측정·개선 결과는 없다.** 기존 로컬 실행기는 로컬 HTTP 80만 허용하므로 이 문서 추가만으로 EC2 실행이 지원되지는 않는다.

조사할 문제·계층·해결책은 실제 관측에서 정한다. DB 조회·집계·페이지 처리·락·커넥션, AI 처리, Kafka·수집·알림 등 어떤 구간이든 근거가 있으면 조사하며 정해진 사례 수를 채우지 않는다. API 조회를 측정한다면 해당 API의 응답·쿼리·자원·정확성을, 파이프라인을 측정한다면 처리 완료·적체·알림 등 그 범위에 맞는 지표를 선택한다.

회차별 기록은 공통 실험 양식으로 남기고, 발견한 문제를 깊이 이해할 때 `보고서양식2(자세한 해결과정)`을 사용한다. 원인 미확정·개선 효과 없음도 결과로 보존한다.

## 진행 단계

| 순서 | 작업 | 상태 | 완료 기준·다음 작업 |
| --- | --- | --- | --- |
| 1 | EC2 측정 환경·실행 도구 준비 | 준비 중 — 로컬 저장소 기준 상태 확인·계획 수립(2026/11/05). EC2 접속·배포·DB 적용은 미확인 | 로컬 절차·계측 검증 후 대상 SHA·이미지·인스턴스·발생기·관측 경로와 사용 시간 확정. 아래 [준비 상태 확인](#준비-상태-확인-20261105)의 P0~P8 |
| 2 | EC2 저부하 예비 측정·목표 확정 | 시작 전 | 실제 요청 경로·정상 처리·수집 완전성을 확인하고 본 실험 목표·부하 상한·중단·복구 기준 확정 |
| 3 | EC2 기준 측정·단계적 부하 | 시작 전 | 고정한 환경·데이터·입력·부하 조건과 기준선 ID 기록 |
| 4 | 장애·정합성 검증 | 시작 전 | 영향 범위를 정하고 한 종류씩 장애를 검증. 복구·누락·중복·DLT·알림 상태 대조 |
| 5 | 확인된 병목·결함 개선 | 시작 전 | 원인 근거와 변경 SHA·설정 기록. 발견되지 않은 개선 효과를 만들지 않음 |
| 6 | 동일 조건 재측정·비교 | 시작 전 | 같은 EC2 기준선·조건에서 재측정하고 편차·비교 제한·복구 결과 보고 |

부하 측정과 장애 주입은 서로 다른 회차로 분리한다. 로컬에서 검증한 복구 절차를 EC2 환경에 맞게 확인하며, 운영 서비스의 중단·변경을 문서 작업의 일부로 수행하지 않는다.

## EC2에서 별도로 고정할 조건

| 조건 | 기록할 내용 |
| --- | --- |
| 대상 | 배포 앱 SHA·이미지 digest, WAF 설정, 모델·탐지 정책, DB 규모·초기 lag |
| 서버 자원 | 인스턴스 유형·vCPU·메모리·스토리지, Docker 한도, T3 계열이면 CPU 크레딧 잔량·모드 |
| 부하 발생기·경로 | 가능하면 대상 서버와 분리한 발생기, 사양·위치, HTTPS→EC2 Nginx→WAF→JuiceShop 경로 |
| 처리·차단 조건 | 테스트 IP 등록·차단 제외 여부, 정상 부하와 예상한 403의 집계 구분, 발생한 위협 저장·알림 부하 |
| 수집·복구 | HTTP 평균·p50·p95·p99·최대값과 건수·기간, 비동기 지연·연속 lag·자원, 최종 대기·중단·복구 기준. p50은 참고 지표 |
| 비교 조건 | 입력·요청률·시간·준비 요청·캐시·반복 수·수집 방식, 동시 사용·배포 여부 |

계측과 목표를 먼저 확정하고 실행 도구의 EC2 지원을 별도로 구현·검증한다. 임의로 로컬 주소 제한만 해제해 실행하지 않는다. 준비 상태와 실제 실행 여부는 구분해서 기록한다.

## 준비 상태 확인 (2026/11/05)

로컬 저장소·코드·로컬에 저장된 원격 참조만 확인했다. **EC2 접속, 배포 SHA·이미지·`.env.aws`·DB 구조 조회, HTTP 요청은 수행하지 않았다.** 아래 위험은 코드에서 확인한 사실이고, EC2 실제 상태는 P0에서 확인한다.

| 구분 | 확인한 사실 | 의미 |
| --- | --- | --- |
| 코드 위치 | outbox·결과 Consumer 보완, `DG_TRACE`, WAF 응답 계측 헤더는 커밋되지 않은 작업 트리에만 있다. 로컬의 `HEAD`·`origin/develop`(39de94d8)·`origin/main`(7d57d145, 마지막 fetch 2026/10/30)에는 없다. 실행기 `scripts/testing/`과 `docs/testing/` 전체도 미추적이다 | CI 배포 이미지에 포함됐을 가능성은 낮지만 실제 배포 SHA는 미확인 |
| 스테이징 | 신규 파일 12개가 staged 상태이고, 그중 11개는 작업 파일과 내용이 다르다(AM) | 커밋 시 다시 스테이징하지 않으면 이전 내용이 들어갈 수 있음 |
| DB 순서 | `LogService`는 `AI_OUTBOX_ENABLED`와 무관하게 로그 저장 트랜잭션에서 outbox를 저장한다. outbox는 JdbcTemplate이라 `ddl-auto: validate`가 테이블 누락을 시작 시점에 잡지 않는다 | 새 backend 배포 전에 운영 DB에 `add-ai-request-outbox.sql` 적용이 필요. 누락 시 health는 UP이어도 로그 저장이 실패할 수 있음 |
| WAF 반영 | WAF 템플릿·njs는 이미지가 아니라 EC2 체크아웃 파일 bind mount다. `deploy.sh`는 app 3개 이미지만 교체한다 | 계측 헤더 반영에는 WAF 재생성·`nginx -t`·응답 헤더 확인이 별도로 필요 |
| 환경 변수 | Compose 기본값이 `WAF_CONSUMER_ENABLED=false`, `PIPELINE_TRACE_ENABLED=false`다 | `.env.aws`의 실제 값 확인 필요. 값 변경은 backend 재생성을 동반 |
| 차단 정책 | 기존 probe는 같은 요청에서 WAF·AI가 모두 탐지되는 입력이다. EC2에서는 발생기 공인 IP가 실제 IP로 복원된다 | 제외 설정 없이 실행하면 자동 등록 후 약 10초 주기 동기화로 이후 요청이 403이 될 수 있음. 정책 결정 필요 |
| 시계 | 기존 실행기는 발생기 송·수신 사이 ±100ms에 WAF 시작 시각이 들어와야 한다 | 서버 구간(WAF·backend)은 같은 EC2 호스트 시계, 브라우저 구간은 발생기 단조 시계로 계산 가능. 교차 시계 확인만 EC2용으로 재설계 |

### 준비 순서와 완료 기준

| 순서 | 작업 | 완료 기준 | 상태 |
| --- | --- | --- | --- |
| P0 | EC2 읽기 전용 현황 수집 | 배포 SHA·EC2 작업 트리 상태·이미지 digest, `.env.aws` 키 존재 여부(값 제외), 테이블·UNIQUE 구조, 데이터 규모, consumer group lag, chrony 오차, 인스턴스·크레딧 모드, 메모리·디스크, 로그 드라이버, 호스트 Nginx 헤더 설정을 비밀값 없는 증거 JSON으로 기록 | 접근 방식 미정 |
| P1 | 실행 조건 결정 | 접근 방식, 발생기 위치·공인 IP, 발생기 IP 차단 정책, 측정 시간대, 관리자 로그인 방식, 배포 일정 확정 | 사용자 결정 필요 |
| P2 | 배포 절차서 | 커밋 정리 → PR → develop → main → Actions, SQL 사전 적용·백업·env·WAF 재생성·검증·롤백 순서 문서화. 실행은 사용자 승인 후 | [절차서](deploy-runbook-outbox-trace.md) 작성(2026/11/05). 미실행. 배포 시간대·백업·trace 설정·운영 문서 반영은 미정 |
| P3 | 실행기 환경 분리 | `local`/`ec2` 프로필로 대상 URL 허용 목록·HTTPS 검증·보고서 경로·실험 ID 접두사 분리. 기존 로컬 모의 테스트 회귀 통과 | 미구현 |
| P4 | 원격 수집 어댑터 | 기존 lag·DB·DG_TRACE·컨테이너 파서를 원격 명령으로 재사용하고 EC2 쪽에서 로그를 필터링. 명령 시간·실패를 기록하고 부하 없이 수집만 성공 | 미구현 |
| P5 | 시계·가드 | 여러 보정 요청으로 발생기 시계 오프셋 구간을 기록. 발생기와 EC2 호스트 자원(메모리·CPU steal·가능하면 크레딧)을 따로 감시 | 미구현 |
| P6 | DB 관측 | 측정 전후 statement digest 차이, 전역 상태, 락 대기·장기 트랜잭션, outbox 상태·대기·발행 지연(DB 시계), 테이블 크기를 읽기 전용으로 수집하고 수집 비용 기록 | 미구현 |
| P7 | 인증·소량 연결 검증 | EC2 대시보드 직접 로그인 후 STOMP 준비, 정상 요청 헤더·로그 연결, probe 1건의 두 출처 수신·DOM 확인, 결정한 IP 정책대로 차단 상태 확인 | 미실행 |
| P8 | EC2 목표·중단 기준 확정 | 소량 결과로 부하 상한·반복·중단·복구 기준을 실행 전에 확정. 로컬 기준을 그대로 복사하지 않음 | 미정 |

## 병목·결함 개선과 재측정 연결

| 사례·시나리오 | EC2 기준선 보고서·ID | 관측 문제·원인 근거 | 개선 변경 SHA·설정 | 동일 조건 재측정 보고서·ID | 판정·비교 제한 |
| --- | --- | --- | --- | --- | --- |
| 관측 후 추가 | 미정 | 미확정 | 미적용 | 미실행 | 미평가 |

위 행의 문제명·대상·우선순위는 측정에서 확인한 증거에 따라 정한다. 특정 DB 개선이나 파이프라인 변경을 미리 성과로 확정하지 않는다.

로컬에서 개선한 코드가 EC2에 배포돼 있다면 그 상태로 EC2 첫 기준선을 측정한다. 로컬 결과를 EC2의 개선 전 값으로 대신 쓰지 않는다. 비교 기준선과 모델·정책·데이터·서버 자원 등이 다르면 차이를 기록하고 필요한 새 기준선을 정한다. EC2에서 추가 병목·결함이 관측되지 않았다면 해당 범위와 한계를 기록한다.

## 기록·재개 방법

1. 이 목차의 최근 기록과 [공통 가이드](../README.md)를 읽고 EC2 준비·측정 대상·실행 범위를 정한다.
2. 보고서는 `docs/testing/ec2/runs/<실험-ID>.md`, 공유 증거는 `docs/testing/ec2/evidence/`, 원본은 `build/test-runs/<실험-ID>/`를 사용한다. 새 실험 ID의 환경은 `ec2`로 구분한다. 현재 EC2 보고서·증거는 미생성이다.
3. 실행·분석 후 이 목차에 회차·판정·증거·관측 사실·원인 가설·다음 작업을 갱신한다. 개선·재측정이면 기준선과 변경 내용을 연결한다.
4. 실패·중단 기록도 보존한다. 로컬 자료를 이동하거나 복사해 EC2 실측 결과로 표시하지 않는다.
