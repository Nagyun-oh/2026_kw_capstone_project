# EC2 로그 수집 Flush 대기 · 핵심 요약

**2026/11/07 · EC2 Flush 0.1 적용 및 같은 부하 재측정 완료(PASS) · 운영 유지** · [상세 해결 과정](<트러블슈팅_4(상세본).md>)

## 문제 상황 흐름

```mermaid
flowchart LR
    A["공격 요청 → WAF"] --> B["access.log·감사 로그 기록"]
    B --> C["Fluent Bit tail 읽기"]
    C --> D["Flush 0.5초마다 묶어서 전달"]
    D --> E["Kafka → 백엔드 저장"]
    E --> F["AI 분석·알림 → 화면"]
```

## 문제 상황

- 트러블슈팅_1~3 이후에도 공격 → AI 알림 화면 표시는 p95 **1,268ms**(평균 1,000ms)였다. 목표는 1초 미만이다.
- 확인 요청 36건을 요청 단위로 나누니 가장 큰 구간은 **WAF 접수 → 로그 커밋**(평균 361ms, 36%)이었다. WAF 알림 경로에서도 같은 성격의 구간이 60%였다.
- 1,800건 분포가 최소 약 58ms부터 약 560ms까지 고르게 퍼져 있었다. 고정 비용 약 55ms에 0~500ms의 임의 대기가 더해진 모양으로, 수집기 `Flush 0.5`초 주기와 일치한다.

## 해결 과정

- Nginx 로그 쓰기 버퍼는 없고 HTTP 처리도 평균 20ms라 다른 원인은 작다고 판단했다.
- 대안 중 **Flush 0.5 → 0.1**을 선택했다. 설정 한 줄만 바꾸고 수집기만 다시 만들면 되며, 읽기 위치와 전송 대기 데이터가 볼륨에 남아 재시작해도 로그가 사라지지 않는다.
- 목표는 적용 전에 정했다. 주 지표인 WAF 접수 → 로그 커밋 p95를 521.8ms에서 300ms 이하로, 정합성·회귀는 기존 기준 유지다.

## 결과

- 분포 폭이 약 500ms에서 약 150ms로 줄었다. 확인 요청의 같은 구간 평균이 정확히 200ms 줄어, 주기 차이의 절반이라는 추정과 맞았다.
- p99도 같은 방향이다. WAF 접수 → 로그 커밋 p99는 553.8 → 206.8ms이고, 회차별 542~576 → 193~209ms로 겹치지 않는다. AI 알림 표시 p99는 1,311.4 → 1,204.4ms다(36표본 참고값). [단계별 p99 추이](runs/20261107-ec2-p99-trend-ts1-ts4.md)
- 세 회차 모두 600건 저장·AI 완료, 확인 요청 두 출처 알림, lag 0, 원복을 확인했다. 앱·실행기·부하·브라우저 조건은 기준선과 같았다.
- **AI 알림 p95 1초 미만 목표는 아직 미달이다(1,133ms).** 평균은 1초 아래로 내려왔다. 남은 요인은 AI 처리 경로, 알림 발행 대기, 요청 구간 꼬리, 팝업 갱신이다.
- EC2는 Flush 0.1을 유지한다. 저장소 설정도 0.1로 바꿨다(2026/11/07 커밋, 다음 배포에 포함). [적용 증거](evidence/20261107-fluentbit-flush-operating.json)

## 해결과정에 쓴 방법을 써야만 했던 이유

- 분포가 주기 대기의 모양이라, 주기 하나만 바꿔 원인을 확인하는 비교가 가장 직접적이다.
- 수집기를 거치지 않는 구조 변경은 원본 보존·재전송 설계가 필요해 이번 범위에서 제외했다.
