# P8 — EC2 기준 확정·전체 실행기 연결

기준 확정일: **2026/11/05**

[EC2 목차](README.md) · [P7 완료](P7.md) · [확정 계약](../../../scripts/testing/profiles/ec2-e2e-v1.json)

P8은 사용자가 동의한 EC2 목표를 고정하고, 발생·수집·감시·DB 관측·브라우저·원복을 한 회차로 연결한다. 실행 결과에 맞춰 기준을 소급 변경하지 않는다. 기준을 바꿔야 하면 새 버전과 이유를 남기고 비교 조건을 분리한다.

## 목표·합격 기준

| 대상 | 확정 기준·집계 |
| --- | --- |
| AI 서버 경로 | WAF 요청 시작 → AI 결과 커밋 후 계측 p95 ≤ 3,000ms. NORMAL 결과도 완료에 포함 |
| WAF 서버 경로 | WAF 요청 시작 → WAF 탐지 커밋 후 계측 p95 ≤ 3,000ms |
| 정합성 | run ID와 서버 requestId로 송신·DB·AI 완료를 대조. 중복 로그·탐지 결과·커밋 계측 0건 |
| 알림 | probe의 WAF/AI 두 출처 전송·실제 브라우저 수신·DOM 표시, 같은 alertId의 중복 팝업 방지 |
| 적체 해소 | 부하 종료 후 60초 내 모든 해당 요청 AI 완료·probe 두 출처 DOM·필수 4개 Kafka 경로 lag 0을 약 10초 이상 간격의 연속 2표본으로 확인 |
| 반복 | 같은 부하 단계 정식 3회가 모두 PASS여야 단계 PASS. pilot 회차는 합산하지 않음 |
| 통계 | 평균·p50·p95·p99·최대·표본·미확인 기록. 현재 표본 규모에서 p99는 참고 |
| 외부 지연 | PC HTTP·브라우저 시간은 별도 관측. 네트워크 시간을 추정해 빼거나 서버 지연으로 해석하지 않음 |

3초는 프로젝트의 수초 내 모니터링을 위한 공학적 목표이며 산업 표준·보장된 운영 SLA가 아니다. knee point와 목표 위반 지점은 구분한다. 5 RPS에서도 꺾이지 않으면 검증 범위를 기록하고 다음 상한을 별도로 정한다.

## 부하 조건과 EPS

- 정식: **1 → 3 → 5 입력 RPS**, 각 120초·3회. 회차마다 1 RPS·30초 워밍업은 판정에서 제외한다.
- 예비: **1 RPS·60초·1회**, 같은 30초 워밍업. 연결·수집 비용·판정·원복을 확인하며 정식 기준선으로 사용하지 않는다.
- 10초마다 probe 1건을 포함한다. 정상 요청은 10초당 9/29/49건이므로 **전체가 1/3/5 RPS**다. 예비 측정 60건은 정상 54건+probe 6건이다.
- 최초 IP 대조용 정상 요청 1건과 최종 복구 요청 1건은 측정 부하와 분리한다. 워밍업 30건도 별도로 집계한다.
- 유입 EPS는 실험에서 관측한 고유 서버 요청 수/계획 구간으로 표시한다. 실제 송신 RPS는 관측한 송신 구간도 함께 표기한다.
- 부하 중 로그 커밋·AI 완료 EPS는 `progress.jsonl`의 관측 간격별 완료 건수 차이로 기록한다. 최종 drain 완료 수를 부하 중 처리량으로 사용하지 않는다. WAF·AI 탐지 이벤트 합계는 고유 요청 처리량과 구분한다.

## 시작·중단·판정

| 조건 | 동작 |
| --- | --- |
| 시작 전 PC·EC2 각각 여유 메모리 ≥ 2GiB, NTP·서비스·초기 lag 확인 | 충족 후 시작. 입력값·계정 오류는 WAF 변경·부하 전에 확인 |
| 어느 호스트든 여유 메모리 < 1GiB가 관측상 15초 지속 | 소유 부하 중단, INCONCLUSIVE. PC·서버 원인을 구분해 조사 |
| 컨테이너 종료·OOM·unhealthy·재시작·교체, 서버 재부팅 | 중단, FAIL. 높은 CPU·steal만으로 중단하지 않음 |
| 자원 표본 15초 단절, 필수 관측 연속 2회 실패 | 중단, INCONCLUSIVE |
| 예상 밖 403, probe 전송 실패, 최근 10초 HTTP 오류율 ≥ 10%(최소 5표본) | 중단, FAIL. 전체 정상 처리 판정은 HTTP 200·요청 집합 대조 사용 |
| 실험 요청이 관측상 60초 넘게 AI 미완료 | 중단, FAIL. 고정 서버 목표 3초와 안전 중단 한계를 구분 |
| k6 미전송·실행 실패·표본 손상·송신 수 미달 | 부하 조건 또는 측정 불완전으로 INCONCLUSIVE. 이미 확인한 HTTP/서버 FAIL은 유지 |
| 대상 앱 SHA·이미지 변경 | 중단 또는 비교 불가, INCONCLUSIVE. 서로 다른 버전을 개선 효과로 합산하지 않음 |
| 시계 점프/모순·보정 구간 산출 실패·보정 유효 기간 초과 | 중단, INCONCLUSIVE. 오차를 임의 상수로 덮지 않음 |
| 시계 구간 폭 > 20ms | 교차 시계 정밀도 참고 정보에 표시. 서버·PC 독립 시계 구간 측정 자체를 중단하지 않음 |

**개정 2:** 최초 pilot r01은 부하·WAF 변경 전 시계 구간 폭 약 38ms로 중단됐다. 추가 읽기 전용 15회 교환에서도 약 34ms였다. 초기 20ms 전체 중단 조건은 동일 서버 시계끼리 계산하는 서버 지연과 같은 PC 단조 시계로 계산하는 요청→브라우저 지연에도 외부 네트워크 제약을 부과하므로 제거했다. 20ms는 교차 시계 정밀도 참고값으로 유지하고, 시계 점프·구간 모순·유효 기간 검사는 그대로 유지한다. 서버 p95 3초·정합성·적체 해소 기준은 변경하지 않는다. **r01 원본·INCONCLUSIVE 판정은 보존하며 개정 2는 새 회차에만 적용한다.**

**개정 3 (2026/11/07):** 부하 중 Kafka lag 조회(`kafka-consumer-groups` CLI)가 측정 구간의 30~35% 동안 vCPU 1개 가까이를 쓰는 측정 도구 부담으로 확인됐다([트러블슈팅_6](<트러블슈팅_6(상세본).md>)). 그래서 `lag_measurement_interval_seconds: 60`을 추가해 부하 중 lag 조회만 60초마다 실행한다. DG_TRACE·DB 수집 주기, 적체 해소 확인의 10초 lag 확인, 서버 p95 3초·정합성 기준은 그대로다. 개정 2 회차(r01~r29)의 원본·판정은 보존하고, 개정 3은 새 회차에만 적용한다.

P5 시계·자원 기본 프로필을 읽고 이 계약의 중단 기준을 명시적으로 결합한다. 보정은 각 회차의 워밍업·측정 직전에 갱신하며 정밀 Windows UTC API를 사용한다. EC2 epoch와 PC 시각을 직접 빼서 지연을 만들지 않는다.

CPU 크레딧은 기존 사용자 콘솔의 unlimited/잔량 자료가 과거 관측임을 기록한다. 이번 예비 실행에서 최신 잔량을 자동 수집했다고 주장하지 않는다. 정식 비교 전후에는 가능한 최신 콘솔 자료와 시각도 남긴다.

### 2026/11/06 — 응답 시각의 실제 표본 재확인

5 RPS 최초 회차에서 약 92초 후 응답 1건이 시작 시 보정 상한을 약 1.52ms 벗어나 중단됐다. 완료된 k6 일반 요청 450건은 HTTP 200이었고 뒤의 실제 보정 구간도 소폭 달라졌다. [중단 원본·진단](evidence/20261106-5rps-clock-interruption.json)은 INCONCLUSIVE로 보존한다.

EC2 실행기는 시각 구간 오류에 한해 실제 시계 교환 표본 5개를 다시 수집한다. 기존·새 보정 사이 **같은 교환 표본의 정밀 UTC(`generator_reference_ms`)·단조 시계** 경과 차이가 10ms를 넘거나 구간이 서로 불연속이면 중단한다. `calibrated_at`은 표시용이며 경과 시간 검증에 사용하지 않는다. 기존 보정의 300초 기한을 넘긴 경우도 재확인으로 우회하지 않는다. phase당 최대 3회만 재확인하고, 같은 응답을 새 보정으로도 확인할 수 없으면 계속 중단한다. HTTP 재전송은 하지 않는다.

각 입력의 실제 해상도도 구간으로 전파한다. Nginx 시작 값은 ms 시각의 차이이므로 ±1ms, k6 `Date.now()`의 정수 값은 [t,t+1ms] 구간으로 검증한다. Python 정밀 UTC의 클라이언트 구간에는 k6 해상도를 붙이지 않는다. 지원 해상도는 0/1ms뿐이고 임의로 큰 오차를 지정할 수 없다. 기존 표본의 보정과 각 보정의 유효 기간도 보존한다.

첫 보완 버전의 r02·r03은 PASS였지만 r04는 표시용 UTC의 약 11.13ms 양자화 차이를 실제 점프로 판단해 INCONCLUSIVE가 됐다. 정밀 UTC·단조 시각 차이는 약 0.003ms였다. 정밀 비교와 입력 해상도 전파를 보완한 뒤 전체 회귀 **262개(시계 회귀 10개 포함)**, 중단 원본 HTTP 875표본의 오프라인 재검증이 통과했다. 기존 r01/r04 판정과 r02/r03의 개별 PASS는 보존하며 새 버전의 세 회차에 섞지 않는다. [재검증 근거](evidence/20261106-5rps-precise-clock-replay.json).

서버 지연 계산·3초 SLO·송신 수·중복·원복 기준은 그대로다. 새 표본·재확인 횟수는 `clock-recheck-*.json`, `manifest.json`의 `clock_rechecks`에 남긴다. 계측 소스 해시가 이전 1·3 RPS와 달라지므로 비교 문서에 검증 방식·입력 해상도 처리·추가 SSH 수집 비용 차이를 기록한다. 기존 회차는 재판정하지 않는다.

## 실행·숨김 입력

전용 실행기는 `run_ec2_e2e.py`다. 기존 로컬 실행기 `run_e2e.py --environment ec2 --execute`는 준비 없이 원격 경로를 우회하지 못하도록 계속 차단한다. k6도 고정 계약 해시·허용 HTTPS 주소를 검증하고 TLS 검증을 유지한다.

계획 확인은 명령·HTTP·파일 생성·숨김 입력을 하지 않는다.

```powershell
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_e2e.py --dry-run --mode pilot --rate 1
```

직접 연 PowerShell에서 예비 측정을 실행한다. 검증된 기존 호스트 키 별칭이 필요하면 P4의 `--host-key-alias`를 추가한다.

```powershell
$ec2Host = '<현재 EC2 주소>'
$ec2Key = '<기존 개인 키 파일 경로>'
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_e2e.py --execute --mode pilot --rate 1 --round 1 --ssh-host $ec2Host --identity-file $ec2Key --prompt-credentials
```

관리자 ID·비밀번호와 기존 DB root 비밀번호를 같은 창에서 숨김 입력한다. 값은 실행 프로세스 메모리에서만 사용하고 파일·환경 변수·명령 인자·기록에 저장하지 않는다. 일반 터미널 입력으로 fallback하지 않는다. 실제 관리자 폼으로 로그인하며 허용된 HTTPS 관리자 origin 외에는 입력하지 않는다. Chrome 세션 파일·전체 화면·응답 토큰을 저장하지 않는다. 자동 로그인 후 관리자 비밀번호 참조를 해제하고, DB 비밀번호는 전후 관측 후 종료 시 해제한다. 메모리 덮어쓰기의 완전한 보장을 주장하지 않는다.

이번 진행에서는 Git 제외 `build/testing-validation/p8-prepared-r01/`의 선입력 대기 보조 프로세스와 `p8-prepared-r03/`의 임시 제어기를 사용했다. 후자는 현재 P8 작업 동안 최대 30분만 메모리에 입력값을 보관하고, 새 자식 프로세스 표준 입력으로 전달하며 성공·종료 시 참조를 해제한다. 재실행은 검토 후 marker로만 허용하고 성공 뒤 추가 실행하지 않는다. 준비 상태 파일·marker·명령 인자에는 비밀번호·계정이 없다. r03 성공 후 해당 Python 제어기 종료를 확인했다. 표준 실행은 위 명령이며 개인용 보조 파일은 커밋하지 않는다.

## 회차 자동 흐름·복구

```text
고유 ID·계약·실행기 해시 기록
→ 자원·서비스·앱/이미지·초기 lag·DB 통계 인증 확인
→ 관리자 폼 로그인·STOMP 준비
→ 정상 단건으로 HTTPS 실제 IP 대조
→ 발생기 IP 하나 임시 제외·WAF 상태 확인
→ 워밍업·처리 정리
→ DB 전 관측·측정용 시계 보정
→ 부하 발생 + pipeline/자원/브라우저 지속 관측
→ 60초 내 처리 완료·lag 해소 확인
→ DB 후 관측·대표 행·대상 SHA/이미지 대조
→ 이번 실험에서 발생한 등록만 삭제·원래 제외 목록 복구
→ 정상 HTTPS·적용 보고·보고서 저장
```

예외가 나도 소유한 부하를 먼저 종료하고 정리·복구를 시도한다. 뒤늦은 결과의 재등록 가능성을 배제할 수 없거나 등록 소유권이 불명확하면 임의 삭제·제외 해제를 강행하지 않고 미확인 상태와 복구 파일을 남긴다. 앱·DB·Kafka를 초기화하거나 중지하지 않는다.

## 결과·반복 집계

회차의 `manifest.json`, 고정 `measurement-contract.json`, `metrics.json`, 단계별 HTTP 원본, DB 전후·차이, trace·브라우저·progress·자원·원복 증거를 보존한다. DB 상세 관측은 원문 없이 전체 DB 구간의 통계이며 관리자·수집기 트래픽도 포함한다. 서버/발생기 메모리와 컨테이너 자원은 구분한다.

정식 회차는 `--mode formal --rate 1 --round N`으로 수행하고, 해당 단계가 끝나면 `summarize_ec2.py --runs <원본1> <원본2> <원본3> --output <EC2 문서 안의 새 .md 경로>`로 합산한다. pilot·다른 부하·다른 계약/코드/이미지는 섞지 않는다. p99 평균 대신 원본 지연 표본으로 합산 백분위를 계산한다.
