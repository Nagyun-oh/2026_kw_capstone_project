## 1. S — Situation: 실제로 어떤 문제가 보였는가

트러블슈팅_1~4를 거친 뒤 r21~r23에서 공격 → AI 알림 화면 표시는 평균 782.7ms·p95 1,133.3ms였다. 목표인 p95 1초 미만에 아직 못 미친다. 확인 요청 36건을 요청 단위로 나눈 구간 중 두 곳은 **처리할 것이 이미 DB에 커밋돼 있는데 발행기가 다음 조회 시각까지 기다리는 시간**이다.

| 구간 (r21~r23, 36건) | 평균 | p50 | p95 | 성격 |
| --- | ---: | ---: | ---: | --- |
| AI 결과 커밋 → 알림 전송 시작 | 121.4ms | 102.2ms | 226.5ms | 알림 발행기 250ms 조회 대기 |
| WAF 탐지 커밋 → 알림 전송 시작 | 127.5ms | 118.4ms | 232.0ms | 같은 대기 |

- 0~250ms 사이에 고르게 퍼진 대기라면 평균은 약 125ms, p95는 약 238ms가 된다. 관측값(평균 121~128ms, p95 227~232ms)이 이 모양과 맞는다.
- 트러블슈팅_1은 알림 조회를 1,000 → 250ms, 트러블슈팅_2는 AI outbox 조회를 500 → 250ms로 줄여 이 대기가 원인임을 이미 확인했다. 감소량도 주기 차이의 절반과 맞았다.
- 남은 문제는 **주기를 아무리 줄여도 평균적으로 주기의 절반은 기다린다**는 점이다. 주기를 더 줄이면 조회 쿼리가 비례해서 늘어난다. 현재 outbox 선점 조회 7.53회/초, 알림 대기 목록 조회 3.96회/초다.

## 3. A — Action: 구조를 따라가며 원인을 좁힌 과정

### 3-1. 변경 전 흐름: "적어 두고, 주기적으로 꺼내 보내기"

이 프로젝트는 Kafka 전송과 WebSocket 알림을 **트랜잭션 안에서 바로 보내지 않는다.** 먼저 DB에 "보낼 것"을 적고 커밋한 뒤, 별도 발행기가 그 기록을 읽어 보낸다. 이것을 transactional outbox 패턴이라고 한다(8-1 참고).

```text
[Kafka Consumer 스레드]                         [발행기 스레드 (단일)]
로그 저장 + outbox 행 INSERT ── 커밋 ──┐          @Scheduled(fixedDelay=250ms)
                                       │          ┌─▶ 대기 행 조회(SELECT … FOR UPDATE SKIP LOCKED)
                                       └ 기다림 ─▶ │    있으면 선점·Kafka 전송·완료 기록
                                         (최대 250ms)└── 없으면 끝, 250ms 뒤 다시
```

| 순서 | 실제 코드 | 역할 | 트랜잭션·스레드 |
| --- | --- | --- | --- |
| 1 | [`LogService`](../../../backend/src/main/java/com/example/security_log_system/service/LogService.java) → [`AiRequestOutboxService.enqueue`](../../../backend/src/main/java/com/example/security_log_system/service/AiRequestOutboxService.java#L34) | 로그 저장과 같은 트랜잭션에서 outbox 행 INSERT | Kafka Consumer 스레드, 로그 저장 트랜잭션 |
| 2 | [`AiRequestOutboxDispatcher.dispatch`](../../../backend/src/main/java/com/example/security_log_system/service/AiRequestOutboxDispatcher.java#L25) | `fixedDelay` 250ms마다 최대 20건 처리 | `aiRequestOutboxScheduler` 스레드 1개 |
| 3 | `AiRequestOutboxPublisher.publishNext` | 선점(커밋) → Kafka ACK 대기 → 완료 기록 | 선점·완료는 각각 별도 트랜잭션 |
| 4 | [`RequestAlertService.record`](../../../backend/src/main/java/com/example/security_log_system/service/RequestAlertService.java#L36) | WAF·AI 탐지 저장 트랜잭션에서 알림 행을 새 revision + `pending=TRUE`로 갱신 | 탐지 저장 트랜잭션 |
| 5 | [`RequestAlertDispatcher.dispatch`](../../../backend/src/main/java/com/example/security_log_system/service/RequestAlertDispatcher.java#L25) | 250ms마다 `pending` 목록 조회 → `RequestAlertPublisher.publish`(행 잠금·WebSocket 전송·완료 기록) | 기본 `taskScheduler` 스레드 1개 |

**`fixedDelay`의 의미:** 이전 실행이 끝난 시점부터 250ms를 센다. 실행 시작 시각 기준인 `fixedRate`와 다르다. 커밋 시각과 다음 조회 시각 사이에는 아무 관계가 없다. 그래서 커밋된 행은 0~250ms(+실행 시간)를 임의로 기다린다. 1절의 고른 분포가 이것이다.

| --- | --- | --- | --- |

### 3-3. 원인과 증상의 연결

```text
발행기가 "커밋됐다"는 사실을 모름 → 다음 주기까지 대기(평균 ≈ 주기/2)
```

## 4. A — Action: 대안을 비교하고 선택한 이유

| 대안 | 동작 | 장점 | 단점·위험 | 선택 |
| --- | --- | --- | --- | --- |
| A. 주기를 더 줄이기(예: 50ms) | 설정만 변경 | 코드 변경 없음 | 평균 대기 25ms가 여전히 남음. 행이 없어도 초당 20회씩 조회. 인스턴스를 늘리면 조회도 배로 늘어남 | 보류 |
| **B. 커밋 직후 깨우기 + 주기 조회는 복구용으로 유지** | 저장 트랜잭션이 커밋되면 발행기를 한 번 바로 실행 | 정상 경로의 대기가 사라짐. outbox 행·재시도·선점 만료 구조를 그대로 재사용 | 깨우기 신호 유실·중복·동시 실행을 설계해야 함 | **선택** |
| C. 트랜잭션 안에서 바로 Kafka·WebSocket 전송 | outbox 없이 즉시 전송 | 가장 빠름 | DB는 롤백됐는데 메시지는 나감, 또는 그 반대. outbox를 도입한 이유가 사라짐 | 제외 |
| D. DB 변경 감지(CDC, 예: Debezium) | binlog를 읽어 이벤트 발행 | 애플리케이션 조회 제거 | 인프라·운영 복잡도가 큼. 이 규모에 과함 | 제외 |
| E. `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` | 커밋 이벤트로 별도 스레드 풀에서 발행 | Spring 기본 기능 | 스레드 풀에서 발행기가 동시에 여러 개 돌 수 있음. 주기 실행과도 겹침. 잠금·중복 실행 제어가 추가로 필요 | B의 일부만 채택 |

**B를 고른 이유:** "보낼 것은 DB에 먼저 커밋한다"는 기존 안전장치를 그대로 두고, **언제 꺼내 보낼지**만 앞당긴다. 깨우기는 어디까지나 "빨리 확인해 보라"는 신호다. 실제로 무엇을 보낼지는 지금처럼 DB가 결정한다. 그래서 신호가 사라져도 주기 조회가 결국 보낸다. 신호가 여러 번 와도 이미 처리된 행은 다시 보내지 않는다.

E와의 차이는 실행 위치다. E는 별도 스레드 풀에서 실행되지만, 여기서는 **각 발행기가 원래 쓰던 단일 스레드 스케줄러에 작업을 넣는다.** 그래서 주기 실행과 깨우기 실행이 같은 스레드에서 차례로 돈다. 동시 실행 제어를 새로 만들 필요가 없다.

### 5-2. 핵심 변경을 순서대로 설명

#### ① 커밋 후 콜백 등록 — `requestAfterCommit()`

```java
public void requestAfterCommit() {
    if (!enabled) return;                                       // 플래그로 끔
    if (!TransactionSynchronizationManager.isSynchronizationActive()) return; // 트랜잭션 밖이면 주기 조회에 맡김
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { signal(); }       // 커밋이 끝난 뒤에만 호출됨
    });
}
```

- **누가 호출하나:** `AiRequestOutboxService.enqueue`가 outbox 행을 INSERT한 직후, `RequestAlertService.record`가 알림 행을 `pending=TRUE`로 바꾼 직후 호출한다. 둘 다 `Propagation.MANDATORY`라 호출 시점에 항상 바깥 트랜잭션(로그·탐지 저장)이 열려 있다.
- **왜 바로 실행하지 않나:** 이 시점에는 아직 커밋 전이다. 발행기는 다른 트랜잭션(READ COMMITTED)으로 조회하므로 커밋 전 행을 볼 수 없다. 그래서 "커밋이 끝나면 불러 달라"고 콜백만 등록한다.
- **`TransactionSynchronization`이란:** Spring이 트랜잭션 생명주기의 각 시점(`beforeCommit`, `afterCommit`, `afterCompletion`)에 호출해 주는 콜백이다. `afterCommit`은 **커밋이 성공했을 때만** 호출된다. 롤백되면 호출되지 않으므로 롤백된 행 때문에 헛되이 깨우는 일이 없다. 같은 패턴을 이미 [`PipelineTrace.afterCommit`](../../../backend/src/main/java/com/example/security_log_system/service/PipelineTrace.java)이 계측에 쓰고 있다.

#### ② 예약만 하고 바로 반환 — `signal()`

```java
void signal() {
    Runnable task = dispatch.get();
    if (task == null) return;                          // 발행기가 비활성화된 환경
    if (!queued.compareAndSet(false, true)) return;    // 이미 예약된 실행이 있음 → 그 실행이 처리
    try {
        executor.execute(() -> {
            queued.set(false);                         // 실행 "시작"에 표시를 먼저 지움
            try { task.run(); }                        // = dispatcher.dispatch()
            catch (RuntimeException e) { log.warn(...); }   // 실패를 스케줄러 스레드로 퍼뜨리지 않음
        });
    } catch (RuntimeException e) {                     // 종료 중 등 예약 거부
        queued.set(false);
        log.warn(...);
    }
}
```

- **왜 Consumer 스레드에서 발행하지 않나:** `afterCommit`은 커밋한 스레드, 곧 Kafka Consumer 스레드에서 실행된다. 여기서 Kafka ACK를 기다리거나 DB를 조회하면 다음 메시지 소비가 늦어진다. 그래서 발행기 스레드에 작업을 넣기만(`execute`) 하고 바로 돌아간다.
- **`afterCommit` 안에서 예외를 던지면 안 되는 이유:** 커밋은 이미 끝났는데 예외가 호출자(Kafka 리스너)로 전파된다. 그러면 오류 처리기가 같은 메시지를 다시 처리하려 할 수 있다. 그래서 모든 예외를 잡아 로그만 남긴다.
- **중복 예약 방지(`AtomicBoolean queued`):** 초당 수십 건이 커밋돼도 아직 시작하지 않은 실행이 있으면 새로 예약하지 않는다. 한 번 실행되는 `dispatch()`가 커밋된 행을 최대 20건(알림은 100건)까지 한꺼번에 처리하기 때문이다. `compareAndSet(false, true)`는 "false일 때만 true로 바꾸고 성공 여부를 돌려준다"는 원자적 연산이다. 여러 Consumer 스레드가 동시에 불러도 한 스레드만 예약에 성공한다.
- **신호 유실을 막는 순서:** 표시를 실행이 **끝날 때가 아니라 시작할 때** 지운다. 실행이 진행되는 동안 새 행이 커밋되면 새 신호가 표시를 다시 세우고 다음 실행을 예약한다. 끝날 때 지웠다면 다음 시간선처럼 놓칠 수 있다.

```text
(잘못된 순서) 실행 중 조회 끝(행 없음) → 그 사이 행 X 커밋·신호(표시가 아직 true라 무시) → 실행 종료·표시 해제
             → X는 다음 주기 조회까지 대기 ✗
(현재 순서)   실행 시작·표시 해제 → 행 X 커밋·신호(표시 false → 예약) → 다음 실행이 X 처리 ✓
```

- **같은 스레드라 동시 실행이 없다:** `executor`는 발행기의 `@Scheduled`가 쓰는 `ThreadPoolTaskScheduler`(스레드 1개)다. 그래서 깨우기 실행과 주기 실행이 겹치지 않고 차례로 돈다. 깨우기 실행이 이미 처리한 행은 주기 실행이 다시 조회해도 없다(완료 기록됨). [스케줄러 설정](../../../backend/src/main/java/com/example/security_log_system/config/OutboxSchedulingConfig.java#L11)

#### ③ 발행기 연결 — `AiRequestOutboxWakeup`·`RequestAlertWakeup`

```java
public AiRequestOutboxWakeup(
        @Qualifier("aiRequestOutboxScheduler") ThreadPoolTaskScheduler scheduler,   // 발행기와 같은 스레드
        ObjectProvider<AiRequestOutboxDispatcher> dispatcher,                       // 실행 시점에 찾기
        @Value("${app.ai-outbox.wakeup-enabled:true}") boolean enabled) {
    super("ai-outbox", scheduler, () -> {
        AiRequestOutboxDispatcher current = dispatcher.getIfAvailable();
        return current == null ? null : current::dispatch;
    }, enabled);
}
```

- **`ObjectProvider`를 쓴 이유(순환 참조):** outbox 서비스 → 깨우기 → 발행기 → 발행 처리(`AiRequestOutboxPublisher`) → outbox 서비스 순서로 서로를 필요로 한다. 생성자에서 발행기를 바로 받으면 Spring이 생성 순서를 정하지 못한다. `ObjectProvider`는 "필요할 때 찾아 달라"는 지연 조회라 생성 시점의 순환을 끊는다.
- **발행기가 없을 때:** `app.ai-outbox.enabled=false`면 발행기 빈이 만들어지지 않는다(`@ConditionalOnProperty`). 이때 `getIfAvailable()`이 `null`을 돌려주므로 깨우기도 아무것도 하지 않는다. 로그 저장은 이 설정과 무관하게 outbox에 쌓인다.
- **알림 쪽:** `RequestAlertDispatcher`의 `@Scheduled`는 스케줄러를 지정하지 않아 기본 `taskScheduler`(스레드 1개)를 쓴다. 그래서 깨우기도 `@Qualifier("taskScheduler")`로 같은 스케줄러를 받는다. 이 스레드는 분 단위 `ReportScheduler`와 공유되지만, 그 작업은 위협 건수 조회 한 번이라 짧다.

#### ⑥ 트레이드오프

- **줄어드는 것:** 정상 경로의 조회 대기(AI 경로 평균 약 240ms, WAF 경로 약 125ms 추정).
- **늘어나는 것:** 커밋마다 발행기가 한 번 더 돈다. outbox는 실행마다 "선점 성공 1회 + 빈 조회 1회" 정도의 선점 SELECT가 늘 수 있다. 알림은 대기 목록 조회가 는다. 5 RPS에서는 작다고 보지만, 실제 증가량은 재측정에서 기록한다.
- **그대로인 것:** 메시지 전달 보장 수준. 이전과 같이 "적어도 한 번" 시도한다. 발행 후 완료 기록 전에 장애가 나면 다시 보낼 수 있고, 브라우저 쪽은 revision으로 중복을 거른다. 종단 간 정확히 한 번이라고 주장하지 않는다.

## 8. 학습 정리·다음 작업

### 8-1. 이번에 쓴 핵심 개념

- **Transactional outbox:** 업무 데이터와 "보낼 메시지"를 같은 DB 트랜잭션에 저장한 뒤, 별도 발행기가 커밋된 기록만 보낸다. DB와 메시지 브로커 사이에서 "저장은 됐는데 메시지는 안 나감"이나 "메시지는 나갔는데 저장은 롤백됨"을 막는다. 대가로 발행이 한 박자 늦다. 이번 개선은 그 늦음을 줄이는 작업이다.
- **Polling vs push(깨우기):** 폴링은 단순하고 복구에 강하지만 평균 주기/2만큼 늦다. push는 빠르지만 신호가 사라질 수 있다. 그래서 **push로 빠르게 + polling으로 안전하게** 둘을 겹쳐 쓰는 것이 흔한 방식이다.
- **`fixedDelay` vs `fixedRate`:** `fixedDelay`는 이전 실행이 끝난 뒤부터 센다. 실행이 길어져도 겹치지 않는다. `fixedRate`는 시작 시각 기준이다.
- **`TransactionSynchronization.afterCommit`:** 커밋 성공 후에만 불리는 콜백이다. 여기서 무거운 작업이나 예외를 내지 말고, 다른 스레드로 넘겨야 한다.
- **신호 합치기(coalescing)와 유실 방지:** "예약 표시"를 원자적으로 세우고, 실행 **시작 시** 지운다. 그러면 신호 폭주를 막으면서 실행 중 신호도 놓치지 않는다.
- **단일 스레드 실행기 = 상호 배제:** 같은 작업을 한 스레드에만 넣으면 별도 잠금 없이 동시 실행이 사라진다. 대신 처리량은 스레드 하나로 제한된다. 현재 부하에서는 충분하다.
- **`ObjectProvider`:** 빈을 실행 시점에 찾는 지연 조회다. 생성자 순환 참조를 끊거나 선택적 빈(조건부로 없을 수 있음)을 다룰 때 쓴다.

### 8-2. 직접 따라가 보기

1. `AiRequestOutboxService.enqueue`(로그 저장 트랜잭션) → `AiRequestOutboxWakeup` → `AfterCommitDispatchTrigger.requestAfterCommit` 순서로 읽는다.
2. `signal()`의 `compareAndSet`·`queued.set(false)` 위치를 보고 5-2 ②의 시간선을 그려 본다.
3. `AfterCommitDispatchTriggerTest.commitDuringRunSchedulesAnotherRun`이 그 시간선을 어떻게 흉내 내는지 본다.
4. 테스트 실행(`backend/`): `.\gradlew.bat test --tests "*AfterCommit*"`
5. 배포 후 확인: 구간 분해에서 "커밋 → 전송 시작"이 수 ms로 줄었는지, DB 관측에서 선점 조회 횟수가 얼마나 늘었는지 본다.

### 8-3. 면접에서 설명할 포인트

- 왜 트랜잭션 안에서 바로 보내지 않았나 → outbox의 정합성(4절 C).
- 왜 폴링을 없애지 않았나 → 신호 유실·재시도·재시작 복구(5-2 ⑤).
- 동시 실행은 어떻게 막았나 → 발행기 전용 단일 스레드 스케줄러에 넣음. DB 선점은 `FOR UPDATE SKIP LOCKED`·임대 토큰을 그대로 사용.
- 신호가 몰리면 → 예약 하나로 합치고, 한 번 실행에 여러 건 처리.
- 인스턴스를 늘리면 → 깨우기는 자기 인스턴스의 발행기만 깨운다. 다른 인스턴스의 행은 그쪽 주기 조회와 `SKIP LOCKED`가 처리한다. 확장 시에는 주기를 늘려 조회 비용을 줄이는 조정이 가능하다.
