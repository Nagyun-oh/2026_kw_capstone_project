## 1. S — Situation · 기준선

알림 발행 지연을 줄인 유효 세 회차 r10·r12·r13을 AI outbox 비교의 기준선으로 삼는다. 이 회차의 알림 발행 조회 대기는 250ms였고 AI 요청 outbox 조회 대기는 500ms였다. EC2에서 5 RPS·120초·3회, 회차별 600건 중 탐지 확인 요청 12건을 사용했다. [기존 설정·회차 증거](evidence/20261107-alert-poll-250ms-comparison.json)

| 지표 | 기준선 |
| --- | ---: |
| outbox 생성 → 발행 완료 기록 가중 평균 | **300.9ms** · 1,800건 |
| 로그 커밋 → AI 결과 커밋 p95 | 754.8ms |
| 요청 → AI 결과 커밋 p95 | 1,172.7ms |
| 요청 → AI 알림 화면 표시 p95 | 1,814.3ms |
| 요청 → WAF 알림 화면 표시 p95 | 946.5ms |

DB 관측 창의 outbox 통계는 r10 318.294ms, r12 291.637ms, r13 292.911ms였다. 각 600건의 발행 완료 증분을 확인했다. 이 평균은 `published_at - created_at`의 합계 증분을 발행 건수 증분으로 나눈 값이다. DB 관측 범위는 서버 전체 창이며, 개별 요청의 지연 분포는 별도 계측이 필요하다. [DB 집계 정의](../../../scripts/testing/ec2_db.py#L167)

## 2. T — Task / Target · 비교 기준

- 기존 앱 SHA·이미지, 부하 실행기·요청 구성·워밍업과 알림 발행 250ms를 맞춘다. AI outbox의 `app.ai-outbox.poll-delay-ms`만 500ms와 250ms로 비교한다. 환경이 달라지면 차이를 기록하고 필요하면 같은 세션에서 500ms 기준선을 다시 잰다.
- 주 지표는 outbox 생성 → 발행 완료 기록의 회차별 평균과 3회 가중 평균이다. 반복 측정에서 평균 감소가 재현되는지 확인한다.
- AI 결과 커밋·브라우저 표시 p95를 따로 비교한다. WAF 결과와 화면 표시도 함께 기록해 공통 경로 변동을 확인한다.
- 기존 P8 합격 기준을 적용한다. 회차별 600건 저장·AI 완료, 확인 요청 12건의 양쪽 알림, 누락·중복 0건, 종료 후 필수 Kafka lag 0과 WAF 원복을 대조한다. 선점 SELECT의 호출 빈도와 실행 시간, outbox 적체·발행 오류·재시도도 기록한다. [기존 측정 계약](P8.md)

## 3. A — Action · 원인 가설

원본 로그 트랜잭션에서 outbox 행을 저장한다. 발행 스케줄러는 한 번 실행할 때 최대 20개를 순서대로 처리한다. 대기 작업이 없거나 발행이 실패하면 현재 실행을 끝내고, `fixedDelay`가 지나면 다시 시작한다. 각 작업은 DB에서 선점·커밋한 뒤 Kafka 전송 ACK를 기다리고, 성공하면 별도 트랜잭션으로 발행 완료를 기록한다. [Dispatcher](../../../backend/src/main/java/com/example/security_log_system/service/AiRequestOutboxDispatcher.java#L25) · [선점·완료 처리](../../../backend/src/main/java/com/example/security_log_system/service/AiRequestOutboxService.java#L51) · [Kafka 발행](../../../backend/src/main/java/com/example/security_log_system/service/AiRequestOutboxPublisher.java#L20)

관련 SQL의 문장별 평균이 1ms 미만이고 outbox 생성 → 발행 완료 기록 평균이 약 301ms여서, 주기적 조회 대기를 첫 가설로 잡았다. 500ms → 250ms 비교는 이 주기가 전체 발행 지연에 기여하는지 검증한다. 정확히 나누려면 같은 `logId`의 **outbox 생성·선점 완료·Kafka ACK·발행 완료 기록**을 연결해야 한다. 기존 계측으로는 조회 대기와 ACK의 개별 지연을 확정할 수 없다.

## 4. A — Action · EC2 적용 및 원복

현재 EC2는 운영 오버라이드로 알림 발행 250ms를 적용한다. 실험에서는 해당 파일을 계속 포함하고 AI outbox만 별도 오버라이드로 전달한다. Spring Boot 환경 변수 `APP_AIOUTBOX_POLLDELAYMS`가 `app.ai-outbox.poll-delay-ms`에 해당한다. [알림 운영 적용](evidence/20261107-alert-poll-250ms-operating.json) · [Spring Boot 환경 변수 변환 규칙](https://docs.spring.io/spring-boot/3.5/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.relaxed-binding.environment-variables)

아래는 실행 전에 정한 수동 절차다. 백엔드 재생성 전에 현재 이미지가 Compose에 해석된 이미지와 일치하는지 확인한다.

```bash
cd ~/2026_kw_capstone_project
alerts=/home/ubuntu/.config/dualguard/compose.alerts.override.yaml
dc_alerts() {
  sudo docker compose --env-file .env.aws -f compose.aws.yaml -f "$alerts" "$@"
}

backend_id=$(dc_alerts ps -q backend)
backend_ref=$(sudo docker inspect -f '{{.Config.Image}}' "$backend_id")
backend_image=$(sudo docker inspect -f '{{.Image}}' "$backend_id")
dc_alerts config --images backend | grep -Fx -- "$backend_ref" &&
  test "$(sudo docker image inspect -f '{{.Id}}' "$backend_ref")" = "$backend_image" &&
  dc_alerts exec -T backend sh -c 'test "$AI_OUTBOX_ENABLED" = true && test "$APP_ALERTS_POLLDELAYMS" = 250 && test -z "${APP_AIOUTBOX_POLLDELAYMS:-}"' &&
  echo '기존 이미지와 기준 설정 확인'
```

이미지 확인이 통과하면 실험용 오버라이드를 추가한다.

```bash
outbox=$(mktemp /tmp/dualguard-outbox-250.XXXXXX)
cat > "$outbox" <<'YAML'
services:
  backend:
    environment:
      APP_AIOUTBOX_POLLDELAYMS: "250"
YAML

dc_alerts -f "$outbox" config --quiet &&
  dc_alerts -f "$outbox" up -d --no-build --pull never --no-deps --force-recreate backend &&
  curl -fsS --retry 25 --retry-delay 2 --retry-all-errors \
    --retry-max-time 60 --max-time 4 http://127.0.0.1:8080/actuator/health &&
  test "$(sudo docker inspect -f '{{.Image}}' "$(dc_alerts ps -q backend)")" = "$backend_image" &&
  dc_alerts exec -T backend sh -c 'test "$APP_ALERTS_POLLDELAYMS" = 250 && test "$APP_AIOUTBOX_POLLDELAYMS" = 250' &&
  echo '동일 이미지와 두 설정 확인'
```

측정 종료 뒤 알림 운영 오버라이드만 포함해 원복한다.

```bash
dc_alerts up -d --no-build --pull never --no-deps --force-recreate backend

curl -fsS --retry 25 --retry-delay 2 --retry-all-errors \
  --retry-max-time 60 --max-time 4 http://127.0.0.1:8080/actuator/health

dc_alerts exec -T backend sh -c 'test "$APP_ALERTS_POLLDELAYMS" = 250 && test -z "${APP_AIOUTBOX_POLLDELAYMS:-}"' &&
  echo '알림 250ms 유지, AI outbox 500ms 기본값 복구'
```

- **가설은 지지됐다.** outbox 발행 평균은 회차별 291.6~318.3ms에서 157.1~171.3ms로, 세 회차 모두 기준선 범위보다 낮았다. 로그 커밋 → AI 결과 커밋 p95와 요청 → AI 결과 커밋 p95도 250ms 세 회차가 모두 기준선 세 회차보다 낮았다. 이 두 지표는 조건별 1,800표본이다.
- 감소폭은 평균 137.2ms다. 작업이 주기와 무관하게 생성된다고 가정하면 평균 조회 대기는 주기의 절반에 가까우므로, 500ms → 250ms에서 약 125ms 감소를 예상할 수 있다. 관측값은 이 추정과 같은 규모다. 남은 약 164ms에는 250ms 주기의 대기, 선점·커밋, Kafka ACK, 완료 기록이 섞여 있다. 개별 구간은 계측하지 않았으므로 이 분해는 추정이다.
- 화면 표시 p95는 36표본이고 회차별 범위가 겹친다. 기준선 r13 1,502.9ms가 250ms r14 1,692.7ms보다 낮다. AI outbox와 무관한 WAF 결과 커밋 p95도 18.9%, WAF 화면 표시 p95도 7.5% 줄었다. 따라서 AI 화면 표시 감소분 253.8ms 전체를 outbox 설정 효과로 보지 않는다. 서버 쪽 1,800표본 지표를 주 근거로 쓴다.
- 비용: 선점 SELECT 고정 digest는 500ms에서 2,570회 / 455.3초, 250ms에서 3,324회 / 450.7초였다. 문장 평균은 0.774ms → 0.707ms, 오류는 두 조건 모두 0건이었다. 회차 종료 후 outbox 행은 모두 `SENT`였고 최대 시도 횟수는 1이어서 재시도가 없었다.
- 정합성: 250ms 세 회차 모두 600건 저장·AI 완료, `requestId`·`logId` 각 600개 고유, 확인 요청 12건의 고유 알림과 두 출처 화면 표시를 확인했다. 종료 후 필수 lag 0과 WAF 원복도 회차별로 확인했다.
- 적체: 부하 중 관측된 `ai-request-topic` 최대 lag는 500ms 17~27, 250ms 22~28이었다. 측정 후 최종 처리 대기는 500ms 22.1~38.7초, 250ms 21.5~37.2초였다. 발행 주기를 줄여도 AI 서비스 소비 적체는 크게 달라지지 않았다.

- AI 알림 화면 표시 p99는 거의 변하지 않았다. 36표본 참고값이다. 전체 단계의 추이는 [단계별 p99 추이](runs/20261107-ec2-p99-trend-ts1-ts4.md)에 모았다.

## 6. T — Trouble · 비교 제한

- 같은 날 약 30~50분 간격으로 측정했다. 기준선 r10은 13:56 호스트 Nginx 재시작 전, r12·r13은 재시작 후다. r10을 빼도 로그 → AI 결과 커밋 p95는 680.3·694.0ms 대 520.1~531.0ms로 같은 방향이다. [Nginx 재시작 기록](<트러블슈팅_1(상세본).md#8-진행-기록>)
- 알림 250ms의 전달 방식이 다르다. 기준선은 임시 `SPRING_APPLICATION_JSON`, 재측정은 14:20:56에 적용한 운영 오버라이드 `APP_ALERTS_POLLDELAYMS`다. 실행 중 값은 둘 다 250ms였다.
- r14는 백엔드 재생성 32초 뒤 시작했다. 30초 워밍업은 집계에서 제외했지만 r14의 백엔드 CPU 최대치는 95.9%로, 기준선 47.3~51.8%와 r15·r16의 52.8%·36.4%보다 높았다. JVM 초기화 영향일 수 있으나 원인은 확인하지 않았다. 기준선 백엔드는 r10 시작 약 13분 전에 생성됐다.
- DB 규모는 회차마다 누적 증가했다. 최신 CPU 크레딧은 수집하지 않았다. p99는 참고값이다.
- outbox 지표는 DB 관측 창 전체의 합계 증분이다. 개별 요청의 발행 지연 분포·p95는 아직 없다.
