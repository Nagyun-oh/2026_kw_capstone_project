## S — Situation

1 RPS·60초 예비 측정은 PASS했지만 정식 반복 기준선이 없다. 측정된 AI·WAF 서버 지연의 반복성을 확인하고 이후 부하 증가·개선 전 비교에 사용할 기준선을 확보한다.

## T — Task·Target

- 동일 앱 SHA·이미지·실행기·계약에서 **1 RPS·120초·3회**, 회차마다 1 RPS·30초 워밍업 제외.
- 측정 요청은 회차마다 정상 108건+probe 12건=120건. 초기 IP 확인 1건·워밍업 30건·복구 1건은 분리한다.
- 서버 요청→AI/WAF 커밋 p95 각 3초 이내, 요청·저장·AI 완료 대조와 중복 0건.
- probe의 두 출처 알림 수신·DOM 표시·대표 행 확인. 종료 60초 안에 업무 완료·필수 lag 0 연속 확인.
- 세 회차 모두 PASS해야 단계 PASS. 평균·p50·p95·p99·최대·표본 수를 기록하며 p99는 참고값.
- 현재 기준·구현을 유지하며 지연 개선이나 3·5 RPS 실행은 이번 범위에 포함하지 않는다.

## T — Trouble·해석·다음 작업

- 세 회차 모두 확정 계약 개정 2와 같은 앱·이미지·모델 이미지·실행기 버전으로 수행했다. 앱/실행기 로직이나 수집·발행 주기를 변경하지 않았으며 이 결과를 성능 개선 효과로 표현하지 않는다.
- 1 RPS에서 서버 AI p95 약 1초·WAF 약 0.61초로 3초 목표를 충족했다. 이는 해당 부하의 기준선이며 최대 처리량·knee point·장시간 안정성 증거는 아니다.
- WAF는 회차당 12표본·합산 36표본이다. p99는 참고값이며 탐지율·오탐률은 이번 판정 대상이 아니다. 총 부하 안에서 probe는 0.1 RPS로 고정하므로 탐지 이벤트 전용 처리량 한계를 측정한 실험으로 해석하지 않는다.
- DB 통계의 테이블 행수는 추정값이며 회차 진행에 따라 데이터가 늘었다. DB 초기화 없이 원본 로그·탐지·실험 증거를 보존했다. 상세 통계에는 관리자 화면·관측기 조회도 포함된다.
- 컨테이너 자원 최대값에는 수집 CLI·healthcheck 비용도 포함된다. 최대 CPU 하나나 순간 lag만으로 병목을 확정하지 않는다. 부하 중 완료 EPS·lag 추이는 각 회차 progress.jsonl에 보존했다.
- 최신 CPU 크레딧 잔량은 미수집이다. P0의 과거 unlimited/잔량 관측을 이번 최신값으로 대체하지 않는다.
- 숨김 입력은 이번 세 회차에만 메모리에서 재사용했으며 완료 시 참조를 해제했다. 계정·비밀번호·토큰·발생기 IP는 이 보고서와 공유 증거에 기록하지 않았다.
- **다음:** 개선 전 3 RPS·120초·3회 → 5 RPS·120초·3회를 먼저 측정한다. 저부하 대기와 부하에 따른 적체를 구분한 뒤 원인 하나를 개선하고 같은 단계에서 재측정한다. 10 RPS 이상은 앞 단계 결과와 새 실행 상한·중단 기준을 확인한 뒤 별도로 진행한다.
