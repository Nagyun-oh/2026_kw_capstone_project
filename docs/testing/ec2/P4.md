# EC2 P4 원격 수집 어댑터

완료일: **2026/11/05**

[EC2 진행표](README.md) · [P1 실행 조건](P1.md) · [P3 환경 분리](P3.md) · [최종 연결 보고서](runs/20261105T182244+0900-ec2-collection-r02.md) · [공유 증거](evidence/20261105-p4-remote-collection.json)

P4는 Windows PC에서 SSH로 EC2의 측정 자료를 읽는 연결이다. **구현·모의 회귀·실제 읽기 전용 수집을 완료했다.** 앱 요청·부하·브라우저 로그인·DB 변경·컨테이너 재시작·차단 제외 변경은 하지 않았다. E2E 부하 실행은 P5~P8 준비 전까지 계속 차단한다.

후속 [P5 시계·자원 감시](P5.md)도 완료했다. 아래 결과는 P4 완료 시점의 기록이며 현재 다음 단계는 P6 DB 관측이다.

## 연결 구조

```text
Windows 수집 전용 CLI 또는 E2E 수집 지점
  → SSHCollection
  → 검증된 호스트 키를 사용하는 SSH
  → 표준 입력으로 전달한 Python 수집기
  → 기존 EC2 컨테이너·DB·Kafka·backend 로그 읽기
  → 필터링한 자료·조회 시간·실패 코드만 반환
  → 기존 DB·trace·lag·자원 파서로 해석·저장
```

서버 저장소에 파일을 설치하지 않는다. P4 수집기를 사용하려고 앱을 새로 배포할 필요는 없다. 기존 배포 앱의 계측·테이블이 준비돼 있어야 하며, P0 확인 결과만으로 미래 실행 상태를 단정하지 않는다.

## 수집 범위

| 대상 | 수집 내용 | 해석·제한 |
| --- | --- | --- |
| Kafka | 필수 4개 group·topic의 partition·lag | 실패·빈 출력·알 수 없는 offset을 lag 0으로 처리하지 않음. 이전 표본의 partition 누락도 불완전 |
| DB | run ID가 같은 요청의 requestId·logId·실험 표식·alertId·탐지 행 수 | 기존 `database_sql`·`parse_database` 재사용. 본문·IP·쿠키 제외 |
| DG_TRACE | 해당 run의 DB 요청 ID 또는 명시한 관측용 requestId의 커밋·알림 계측 | EC2에서 먼저 필터링하고 허용 필드만 전송. `parse_traces` 재사용 |
| 컨테이너 자원 | 서비스별 CPU%·Mem%·메모리 사용량 | `resource_peaks` 재사용. 호스트 전체 사용률과 다르며 CPU 100% 초과도 보존 |
| 컨테이너 상태 | 실행 상태·health·재시작 횟수·시작 시각·이미지 ID | healthcheck가 없으면 null 유지. 서버 자원에 따른 자동 중단은 P5 |
| 실행 근거 | 수집 전용 check의 EC2 HEAD, 명령별 시작·종료·소요 시간·종료 코드·실패·읽은 바이트·행 수 | SSH 주소·키 경로·명령 stderr를 기록하지 않음. checkout HEAD와 이미지 ID는 구분 |

DB는 컨테이너에 이미 설정된 앱 계정으로 접속한다. 비밀번호를 로컬로 가져오지 않고 argv에 펼치지 않는다. `START TRANSACTION READ ONLY`와 SELECT당 3초 제한, DB 조회 프로세스 12초 제한을 사용한다. 인증 실패 시 계정·환경을 바꾸거나 root로 자동 전환하지 않는다.

SSH 연결은 기존 known_hosts·`StrictHostKeyChecking=yes`를 유지한다. IP 변경 때문에 기존 검증 별칭을 사용한다면 **같은 서버 키임을 확인한 별칭만** 지정한다. 호스트 키 검증을 끄지 않는다.

일반 명령은 12초, Kafka 조회는 20초, SSH 전체 호출은 80초 제한이다. 실패 시 고정 코드만 보존한다. 로그는 `--since`·최근 20,000행·입력 16MiB·개별 행 제한을 적용하며 상한에 도달하면 불완전으로 표시한다. timeout에서 종료하는 대상은 자신이 시작한 조회 프로세스이며 앱 컨테이너는 중단하지 않는다. SSH 연결이 끊겨도 서버의 개별 조회 제한이 별도로 남는다.

## 수집 전용 실행

프로젝트 루트의 Windows PowerShell에서 먼저 계획을 확인한다. 이 명령은 파일·SSH·HTTP를 생성하지 않는다.

```powershell
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_collection.py --dry-run --since 2026-11-05T09:00:00Z --samples 2
```

실제 읽기 전용 수집은 기존 SSH 주소·키를 변수로 지정한다. 보고서에는 별칭만 남는다.

```powershell
$ec2Host = '<현재 EC2 주소>'
$ec2Key = '<기존 개인 키 파일 경로>'
$sinceUtc = [DateTime]::UtcNow.AddMinutes(-5).ToString('yyyy-MM-ddTHH:mm:ssZ')
.\build\e2e-venv\Scripts\python.exe -X utf8 scripts/testing/run_ec2_collection.py --collect-only --ssh-host $ec2Host --identity-file $ec2Key --since $sinceUtc --samples 2 --round 3
```

기본적으로 새 수집 ID로 DB를 대조하므로 앱 요청을 보내지 않았다면 DB·trace가 비어 있는 것이 정상이다. 기존 실험을 확인하려면 `--run-id <기존 실험 ID>`를 지정한다. 기존 계측 필터만 확인할 때는 `--request-id <WAF 생성 ID>`를 지정할 수 있다. 새 요청을 만들거나 ID를 위조하는 기능이 아니다. 표본 수는 1~3개이며, `--interval`은 **앞 표본 수집 완료 후 다음 표본까지의 대기**다. 고정 5초 표본 주기라고 해석하지 않는다.

## 다음 단계와 남은 한계

- **P5:** 발생기·서버 시계와 자원을 각각 관측하고 수집 주기·자동 중단을 연결한다. 두 호스트의 절대 시각을 그대로 빼지 않는다. 이번 소요 시간은 각 호스트의 단조 시계로 측정했다.
- **P6:** SQL 실행 계획·statement digest·락·outbox 지연 등 상세 DB 관측과 비용을 검토한다. 이번 DB 시간은 Docker 실행·접속까지 포함한 조회 프로세스 시간이며 순수 SQL 지연이 아니다.
- **P7:** 실제 신규 요청의 양수 DB 표본·WAF 탐지·브라우저 알림 수신·DOM 연결 확인. 이번 양수 DB 결과의 파싱은 모의 검증이며 실제 DB 조회는 빈 결과였다.
- **P8:** EC2 목표·중단·반복·부하 상한 확정. 현재 1→3→5 RPS 제안이나 수집 성공을 성능 PASS로 표시하지 않는다.
