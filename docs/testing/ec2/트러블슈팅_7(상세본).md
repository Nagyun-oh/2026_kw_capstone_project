## 1. S — Situation: 실제로 어떤 문제가 보였는가

트러블슈팅_6에서 측정 실행기의 lag 조회를 줄였는데도 Kafka 컨테이너 CPU가 기대만큼 줄지 않았다. lag 조회가 없는 시점에도 Kafka CPU가 26~78% 튀었다. 원인을 따라가 보니 Kafka의 Docker healthcheck가 15초마다 `kafka-topics --bootstrap-server kafka:29092 --list`를 실행하고 있었다. 이 명령도 실행할 때마다 JVM을 새로 띄우는 Java CLI다.

2026/11/08 10:12~10:15 +09:00에 부하 없이 3분 동안 읽기 전용으로 쟀다. 그동안 WAF 접근 로그 증가가 0바이트라 외부 트래픽은 없었다. CPU는 `docker stats` 순간 표본 대신 컨테이너별 cgroup `cpu.stat` 누적값을 1초마다 읽어 구했다.

| 관측 사실 | 값 | 자료 |
| --- | --- | --- |
| 유휴 호스트 CPU | 평균 21.2%(약 0.42 vCPU) | `/proc/stat` |
| Kafka 컨테이너 CPU | 평균 23.75%, 그중 브로커 자체 1.94% | cgroup 누적값 |
| healthcheck 실행 | 3분간 12회, 회당 평균 2.85초·최대 4.15초, 회당 약 3.8 CPU초, 실패 0 | `docker inspect` health 기록 |
| 다른 healthcheck | AI 0.57초, DB 0.10초, WAF 0.10초 | 같음 |

- **영향:** healthcheck 하나가 운영 중 평균 약 0.22 vCPU를 상시 쓴다. 2 vCPU 서버 용량의 약 11%이고, 유휴 CPU의 절반이다.
- **처리 한계에 주는 영향:** 단계 부하 추정에서 CPU 포화는 지금 약 8.7 RPS, 이 부담이 없으면 약 9.9 RPS다(선형 가정).

## 3. A — Action: 구조를 따라가며 원인을 좁힌 과정

### 3-1. 변경 전 흐름

```text
dockerd: 15초마다 kafka 컨테이너 안에서 kafka-topics --list 실행
  → JVM 기동(약 2.9초, 약 1.3코어) → AdminClient로 브로커 메타데이터 조회 → 종료
  → 성공 12회 연속 실패 전까지 healthy 유지
compose: backend·ai·fluent-bit은 depends_on kafka: service_healthy (기동 시 한 번 대기)
```

| 위치 | 설정 | 역할 |
| --- | --- | --- |
| [`compose.aws.yaml` kafka healthcheck](../../../compose.aws.yaml) | interval 15s, timeout 10s, retries 12, start_period 40s | 브로커가 실제 요청에 응답하는지 확인 |
| 같은 파일 backend·ai·fluent-bit `depends_on` | `condition: service_healthy` | 기동 순서 보장. 운영 중 재시작 판단에는 쓰지 않음 |

### 3-2. 가설과 검증

| 가설 | 근거 | 상태 |
| --- | --- | --- |
| lag 조회 외 Kafka CPU 급등은 healthcheck CLI 때문 | 급등 시점과 lag 조회가 겹치지 않음(트러블슈팅_6). 유휴 측정에서 healthcheck 실행 구간마다 회당 약 3.8 CPU초 증가, 브로커 자체는 1.94% | 확인 |
| unhealthy 상태로 자동 재시작이 일어나 확인 간격이 중요하다 | 자동 재시작 장치(autoheal 등)가 없음. healthy는 기동 시 의존 서비스 대기에만 쓰임 | 기각 |

## 4. A — Action: 대안을 비교하고 선택한 이유

| 대안 | 예상 CPU | 장점 | 단점 | 선택 |
| --- | ---: | --- | --- | --- |
| A. 간격 15 → 60초, 기동 중에만 5초 간격(`start_interval`) | 약 0.05 vCPU | 확인 방식(브로커 응답) 유지. 기동 대기 시간은 거의 그대로 | 운영 중 이상 감지가 최대 60초 늦어짐(상태 표시만 영향) | **선택** |
| B. 포트 확인(`nc -z`, `/dev/tcp`) | 거의 0 | 가장 가벼움 | 포트가 열린 것과 요청을 처리할 수 있는 것은 다를 수 있음. backend의 DLT 토픽 생성 등이 너무 일찍 시작될 위험 | 보류 |
| C. 처음 한 번 `kafka-topics`, 이후 포트 확인 | 거의 0 | 정확한 준비 확인과 가벼운 상시 확인 | 스크립트가 복잡하고 같은 컨테이너 재시작 때 동작 검증이 필요 | 보류 |
| D. 같은 명령에 JVM 경량 옵션 | 30~50% 감소(추정) | 의미 변화 없음 | 감소 폭이 불확실하고 여전히 15초마다 JVM | 보류 |

**선택 이유:** A는 healthcheck가 확인하는 내용을 바꾸지 않고 실행 횟수만 1/4로 줄인다. 확인 결과가 쓰이는 곳(기동 시 대기)에도 영향이 거의 없다. 효과가 부족하면 B·C를 다음 단계로 검토한다.

## 5. A — Action: 코드 수준에서 어떻게 바꿨는가

### 5-1. 변경 후 흐름

```text
기동 후 120초(start_period) 동안: 5초 간격(start_interval)으로 kafka-topics 확인 → healthy가 되면 의존 서비스 기동
이후: 60초 간격으로 kafka-topics 확인
연속 3회 실패(약 3분)하면 unhealthy (이전 15초 × 12회와 같은 시간)
```

| 설정 | 변경 전 | 변경 후 | 이유 |
| --- | --- | --- | --- |
| `interval` | 15s | 60s | 상시 실행 횟수 1/4 |
| `start_interval` | 없음 | 5s | 기동 직후에는 짧게 확인해 의존 서비스 대기 시간 유지 |
| `start_period` | 40s | 120s | 기동이 40초를 넘어도 60초 간격으로 넘어가기 전에 5초 간격으로 확인 |
| `retries` | 12 | 3 | unhealthy 판정까지 시간을 약 3분으로 유지 |
| `test`, `timeout` | `kafka-topics --list`, 10s | 그대로 | 확인 의미 유지 |

### 5-2. 핵심 변경

- **`start_interval`:** Docker 25 이상과 Compose spec에서 지원한다. EC2는 Docker 29.8.1, Compose 5.5.1이다. 로컬 Compose 5.4.0으로 `config` 해석을 확인했다.
- **배포 영향:** healthcheck도 컨테이너 설정이라, 이 변경이 처음 배포될 때 `compose up -d`가 Kafka 컨테이너를 한 번 재생성한다. 데이터는 `kafka-data` 볼륨에 남는다. backend·ai·fluent-bit은 Kafka가 다시 healthy가 될 때까지 기다린다. [배포 문서](../../06_aws_deployment.md)에 적었다.
- **범위:** 로컬용 `compose.yaml`은 바꾸지 않았다. 로컬 실험 조건을 유지하기 위해서다.
- **트레이드오프:** 운영 중 Kafka 이상을 healthcheck로 감지하는 시간이 최대 60초 늦어진다. 하지만 이 상태로 자동 조치하는 장치가 없어 영향은 상태 표시에 그친다.

## 8. 학습 정리·다음 작업

- **healthcheck도 부하다:** 컨테이너 안에서 실행되는 healthcheck의 CPU는 그 컨테이너 몫으로 잡힌다. JVM CLI 같은 무거운 명령은 짧은 간격으로 돌리면 서버 용량을 상시 잡아먹는다.
- **확인 간격과 용도:** healthcheck 결과가 어디에 쓰이는지(기동 순서, 자동 재시작, 모니터링)에 따라 적절한 간격이 다르다. 이 시스템은 기동 순서에만 쓰므로, 기동 중에는 짧게, 이후에는 길게 확인하는 구성이 맞다.
- **다음 작업:** 배포 후 유휴 재측정과 5 RPS 기준선 재측정. 그 결과로 [단계 부하 계획](step-load-plan.md)의 예상 한계를 갱신하고 knee point 측정으로 넘어간다.
