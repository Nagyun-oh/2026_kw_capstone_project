## 1. S — Situation · 관측한 문제

5 RPS에서 요청 → AI 결과 저장 p95는 1,049.3ms였고, 요청 → AI 알림 화면 표시 p95는 1,992.0ms였다. WAF 쪽은 각각 541.0ms와 1,496.4ms였다. 서버 저장은 EC2 시계로, 요청 → 화면 표시는 발생기 단조 시계로 집계했다. 구간별 p95의 차로 후속 구간을 추정하면 서로 다른 요청을 비교할 수 있어, 같은 요청을 연결해서 실제 전송 전 대기를 구했다. [5 RPS 구간별 지연](runs/20261106-ec2-5rps-baseline-review.md#원본-표본-합산-지연)

## 2. T — Task / Target · 확인할 질문과 판정

- 탐지 커밋 후 대기, 전송 호출 자체, 브라우저 수신 후 화면 표시 중 어느 구간에 시간이 집중되는가?
- 발행 조회 주기를 줄이면 전송 시작 전 지연이 줄고, 기존의 발행 복구와 동일 알림 갱신이 유지되는가?
- 후속 A/B 비교의 제안 기준은 5 RPS·120초·3회와 동일 요청 구성·워밍업을 사용해 AI·WAF 각각의 전송 시작 전 p95가 **400ms 이하**인지 보는 것이다. 서버 3초 SLO와 기존 중단·원복 기준을 함께 적용한다. [정식 측정 기준](P8.md)

## 3. A — Action · 지연 구간을 좁힌 과정

### 3-1. 발행 경로를 코드에서 따라갔다

1. WAF와 AI는 탐지 저장 트랜잭션에서 같은 요청의 알림을 생성하거나 갱신한다. 저장소가 새 revision과 `pending = TRUE`를 기록한다. [WAF 저장](../../../backend/src/main/java/com/example/security_log_system/service/WafDetectionWriter.java#L117) · [AI 저장](../../../backend/src/main/java/com/example/security_log_system/service/ThreatService.java#L135) · [알림 저장](../../../backend/src/main/java/com/example/security_log_system/repository/RequestAlertRepository.java#L81)
2. `RequestAlertDispatcher`는 `fixedDelay`로 동작한다. 직전 실행이 끝나고 기본 1,000ms 뒤에 `pending` 행을 다시 조회하고, 최대 100건을 순차적으로 발행한다. 기본 스케줄러 스레드 하나를 분 단위 리포트 작업과 공유한다. [Dispatcher](../../../backend/src/main/java/com/example/security_log_system/service/RequestAlertDispatcher.java#L25) · [조회 SQL](../../../backend/src/main/java/com/example/security_log_system/repository/RequestAlertRepository.java#L104) · [스케줄러](../../../backend/src/main/java/com/example/security_log_system/config/OutboxSchedulingConfig.java#L10) · [리포트 작업](../../../backend/src/main/java/com/example/security_log_system/scheduler/ReportScheduler.java#L15)
3. `RequestAlertPublisher`가 행을 잠그고 여전히 발행 대기인지 확인한다. 전송 직전 `ALERT_SEND_BEGIN`, 호출 반환 직후 `ALERT_SEND_RETURNED`를 남기고 해당 revision을 발행 완료로 기록한다. 예외는 dispatcher가 기록하고 다음 조회에서 대기 행을 다시 처리한다. [Publisher](../../../backend/src/main/java/com/example/security_log_system/service/RequestAlertPublisher.java#L21)

### 3-3. 현재 판단

두 출처 모두 지연이 전송 호출 전에 집중됐고 상위 지연이 기본 1초 주기에 가깝다. 발행 대기 행이 조회 직후 커밋되면 다음 조회까지 대기하는 구조와 일치한다. **유력 원인은 주기적 조회 대기다.** 실행 중 설정값과 조회 시각은 후속 비교에서 확인한다. 현재 원본에는 개별 폴링 시각이 없어 스케줄러 공유 작업과 락의 기여도를 분리할 수 없다.

## 4. A — Action · 해결 대안과 첫 비교 후보

| 대안 | 기대 효과 | 비교할 비용과 동작 |
| --- | --- | --- |
| 발행 조회 지연 1,000ms → 250ms | 한 변수로 조회 대기의 영향을 비교 | 유휴 조회 빈도가 이론상 초당 약 1회에서 4회로 증가. 실제 조회량과 알림 revision 수를 확인 |
| 커밋 후 발행기 깨우기 + 주기적 복구 | 커밋 직후 발행 기회를 앞당김 | 동시 실행 제한, 트리거 유실·재시작 시 복구, 같은 요청의 후속 revision을 별도로 검증 |
| 알림 전용 스케줄러 | 리포트 작업과 스레드 공유 제거 | 공유 작업과 지연이 겹친다는 계측이 필요. 폴링 간격은 별도 변수로 유지 |

첫 비교 변수로 **발행 조회 지연 250ms**를 선택했다. 5 RPS 기준선에서 36건 중 23건은 한 번의 전송으로 두 출처가 전달됐고, 13건은 같은 `alertId`의 여러 전송으로 전달됐다. AI 탐지 커밋은 WAF 커밋 뒤 중앙값 약 538ms에 발생했다. 조회가 잦아질 때 WAF 선발행 후 AI 갱신 비율, 같은 알림의 최신 revision, 팝업 개수와 두 출처 표시를 확인했다. [브라우저 알림 갱신 코드](../../../frontend/src/hooks/useWebSocket.js#L69)

## 5. A — Action · 적용과 복구 계획

1. 실행 중 적용값을 확인한다. 기존 속성 `app.alerts.poll-delay-ms`를 사용해 진단 설정을 250ms로 바꾸고, 발행 대기 저장·행 잠금·실패 시 재처리·revision 동작을 확인한다.
2. 같은 5 RPS 조건으로 새 회차를 실행한다. 전송 전 지연, 호출 지연, 화면 표시 지연, 대기 조회 횟수, 알림별 전송 횟수와 기존 정합성 지표를 함께 기록한다. 지연이 남으면 조회 시작·완료와 행 잠금 획득 시각을 따로 확인한다.
3. 진단이 끝나면 원래 설정과 서비스 상태로 복구하고, 대기 알림 처리와 임시 차단 제외 원복을 확인한다.

EC2에서 임시 Compose 오버라이드의 SPRING_APPLICATION_JSON에 app.alerts.poll-delay-ms=250을 전달하고 같은 이미지로 백엔드를 재생성했다. 각 유효 회차 전후로 설정, health, 앱 SHA·이미지 및 백엔드 시작 시각을 대조했다. 원복 시 기본 Compose로 백엔드를 다시 생성했다. [집계·설정·원복 증거](evidence/20261107-alert-poll-250ms-comparison.json)

## 7. T — Trouble · 계측 한계

- 1·3 RPS 원본 교차 확인에서 AI 전송 시작 로그가 커밋 후 기록보다 0.1~1.1ms 앞선 표본이 4건 있었다. DB 커밋 완료 후 콜백에서 타임스탬프를 찍는 동안 다른 스레드가 이미 커밋된 행을 읽을 수 있다. 이는 기록 순서에 대한 설명 가설이다. 5 RPS 본 분석의 36건에는 이런 역전이 없었다. [커밋 후 계측](../../../backend/src/main/java/com/example/security_log_system/service/PipelineTrace.java#L49)
- 1·3·5 RPS 사이의 계측·브라우저 버전 차이와 DB 규모 변동은 기존 비교 문서에 기록했다. 개선 전후 평가는 5 RPS 기준선과 같은 조건의 새 회차로 수행한다. [비교 조건](runs/20261106-ec2-1-3-5rps-comparison.md)
