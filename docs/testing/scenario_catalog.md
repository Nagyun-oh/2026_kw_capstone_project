# 시나리오 카탈로그

로컬 JuiceShop(WAF 뒤)을 대상으로 6대 웹 공격, 곧 SQL Injection, XSS, Command Injection, Path Traversal, SSRF, XXE를 유형마다 세 가지씩 다룬다. 각 시나리오는 어디서 무엇을 어떻게 입력하고 그 결과와 탐지가 어땠는지 순서로 적었다.

> 이 문서는 Notion "시나리오 카탈로그" 페이지의 **이미지 없는 사본**이다. 단계별 화면 캡처는 Notion/PDF 버전에 있다. 모든 수치는 2026-11-02 로컬 스택에서 실제 Chromium 브라우저로 측정했다.

## 0. 시작 전 준비

### 0.1 접속 주소

- 공격 대상(JuiceShop, WAF 경유): `http://localhost/`
- 탐지 확인(대시보드): `http://localhost:3000/` → 관리자 로그인 → 왼쪽 메뉴 `위협 탐지`

### 0.2 로그인이 필요한 시나리오

5번(SSRF)과 6번(XXE)은 JuiceShop 로그인이 필요하다. 로그인 화면에서 `admin@juice-sh.op` / `admin123`(JuiceShop 공개 기본 계정)으로 로그인하거나, 1.1 공격으로 로그인한 상태를 그대로 이어서 써도 된다.

### 0.3 탐지 확인 방법

1. 공격 후 10초쯤 기다린다(로그가 Kafka를 거쳐 저장되는 시간).
2. 대시보드 `위협 탐지`에서 맨 위 행을 보거나, `위협 번호` 칸에 번호를 넣고 검색한다.
3. `탐지 유형`이 `WAF Detection, AI Detection`이면 둘 다 탐지, `WAF Detection`이면 WAF만 탐지다. 위협 탐지 목록에 없으면 `전체 로그`에서 요청 기록만 확인한다.

### 0.4 알아둘 점

- 공격 규칙은 탐지 전용(DetectionOnly)이라 공격 요청은 막히지 않고 **기록만** 된다.
- 브라우저 요청은 게이트웨이 IP(`172.20.0.1`)로 들어온다. 이 IP는 차단 제외 대상이라 WAF·AI가 둘 다 탐지해도 **403 차단은 걸리지 않는다**.
- 화면 위쪽 검색창(돋보기)은 입력값을 서버로 보내지 않는다(서버에는 빈 `q=`만 감). 그래서 검색 API를 쓰는 시나리오는 **주소창에 API 주소를 직접 입력**한다.
- 주소창에 `../`를 그대로 쓰면 브라우저가 주소를 정리하면서 지운다. `..%2f`로 웹 루트보다 위까지 올라가면 Nginx가 400으로 먼저 거부해 WAF·AI 로그에 남지 않는다(실측). 그래서 4번은 한 단계만 올라가는 형태를 쓴다.

# 공격 시나리오 (1~7)

## 1. SQL Injection

입력값에 SQL 구문을 섞어 데이터베이스 쿼리의 의미를 바꾸는 공격이다. JuiceShop의 로그인과 상품 검색 API가 취약하다.

### 1.1 로그인 우회 (항상 참 조건)

**어디서**: 로그인 화면 `http://localhost/#/login` › Email 칸

**어떻게**

1. 오른쪽 위 `Account` → `Login`을 눌러 로그인 화면을 연다.
2. Email 칸에 아래 입력값을 넣고, Password에는 아무 값이나 넣는다.
3. `Log in`을 누른다.

**입력값**

```text
' OR 1=1--
```

**결과**: 비밀번호 없이 첫 번째 계정인 관리자(admin@juice-sh.op)로 로그인된다. (응답 200)

**탐지**: WAF 탐지, 규칙 5건(942100 등) · AI 탐지, `[규칙] SQL 논리우회(OR/AND 토톨로지)` — 위협 #10524

### 1.2 관리자 계정 지정 로그인

**어디서**: 로그인 화면 › Email 칸

**어떻게**: 1.1과 같고 Email 값만 바꾼다.

**입력값**

```text
admin@juice-sh.op'--
```

**결과**: `--` 뒤의 비밀번호 검사 부분이 주석 처리되어, 비밀번호 없이 관리자 계정으로 로그인된다. (응답 200)

**탐지**: WAF 탐지, 규칙 4건(942100·942300·942440·942520) · AI 탐지, `[규칙] 따옴표 뒤 주석/구문종결(SQLi)` — 위협 #10526

### 1.3 UNION으로 회원 정보 빼내기

**어디서**: 브라우저 주소창 › 상품 검색 API

**어떻게**: 아래 주소를 주소창에 그대로 붙여 넣고 Enter를 누른다.

**입력값**

```text
http://localhost/rest/products/search?q=qwert')) UNION SELECT id,email,password,'4','5','6','7','8','9' FROM Users--
```

**결과**: 상품 목록 대신 전체 회원 24명의 이메일과 비밀번호 해시(MD5)가 응답에 그대로 나온다. (응답 200)

**탐지**: WAF 탐지, 규칙 9건(942 계열) · AI 탐지, `[규칙] UNION SELECT 구문` — 위협 #10528

**1번 정리**: 세 가지 모두 WAF와 AI가 함께 탐지했다. 1.1·1.2는 관리자 로그인에, 1.3은 회원 정보 유출에 실제로 성공한 공격이다. AI가 놓치는 SQLi 변형(`/**/` 주석 끼우기, 이중 인코딩)과 그때도 WAF가 잡는 결과는 별도 우회 측정 페이지(Notion: "실제 공격·우회 패턴 탐지 시나리오")에 있다.

## 2. Cross-Site Scripting (XSS)

입력한 HTML·스크립트가 다른 사용자의 화면에서 실행되게 만드는 공격이다. 피드백처럼 저장된 뒤 다시 보여지는 입력란이 대상이다.

### 2.1 script 태그 삽입

**어디서**: 고객 피드백 화면 `http://localhost/#/contact` › Comment 칸

**어떻게**

1. 왼쪽 위 메뉴(≡) → `Customer Feedback`을 연다.
2. Comment 칸에 아래 입력값을 넣는다.
3. Rating에서 별점을 아무거나 고르고, CAPTCHA 문제(예: `7*9+2`)의 답을 Result 칸에 넣는다.
4. `Submit`을 누른다.

**입력값**

```text
<script>alert(1)</script>
```

**결과**: "Thank you for your feedback." 메시지가 뜨고 입력이 그대로 저장된다. (응답 201)

**탐지**: WAF 탐지, 규칙 7건(941100 등) · AI 탐지, `[규칙] XSS 태그/함수 다중 검출 [<script, alert(, </script]` — 위협 #10531

### 2.2 이미지 오류 이벤트 삽입

**어디서**: 고객 피드백 화면 › Comment 칸

**어떻게**: 2.1과 같고 Comment 값만 바꾼다.

**입력값**

```text
<img src=x onerror=alert(1)>
```

**결과**: 피드백이 저장된다. (응답 201)

**탐지**: WAF 탐지, 규칙 8건(941100·941120 등) · AI 탐지, `[규칙] XSS 이벤트 핸들러 [onerror=] · XSS 태그/함수 다중 검출` — 위협 #10535

### 2.3 javascript: 주소 iframe 삽입

**어디서**: 고객 피드백 화면 › Comment 칸

**어떻게**: 2.1과 같고 Comment 값만 바꾼다.

**입력값**

```text
<iframe src="javascript:alert(`xss`)">
```

**결과**: 피드백이 저장된다. (응답 201)

**탐지**: WAF 탐지, 규칙 13건(941170·941210 등) · AI 탐지, `[규칙] XSS 태그/함수 다중 검출 [<iframe, javascript:, alert(]` — 위협 #10539

**2번 정리**: 세 가지 모두 WAF와 AI가 함께 탐지했다. 6개 유형 중 탐지가 가장 고르다.

## 3. Command Injection

입력값에 쉘 기호(`;`, `|`, 백틱)를 섞어 서버가 운영체제 명령을 실행하게 만드는 공격이다. JuiceShop에는 명령을 실행하는 입력란이 없어서, 공격자가 입력 파라미터에 명령을 섞어 보내는 상황을 상품 검색 API로 재현한다. 앱이 실제로 명령을 실행하지는 않으므로 이 항목은 **공격 시도를 탐지하는지**를 확인한다.

### 3.1 세미콜론으로 명령 이어 붙이기

**어디서**: 브라우저 주소창 › 상품 검색 API

**어떻게**: 아래 주소를 주소창에 붙여 넣고 Enter를 누른다.

**입력값**

```text
http://localhost/rest/products/search?q=test;cat /etc/passwd
```

**결과**: 응답 200, 검색 결과 없음 (명령은 실행되지 않음).

**탐지**: WAF 탐지, 규칙 3건(930120·932160·932236) · AI 탐지, `[규칙] 쉘 메타문자 + 시스템 명령 [cat /, ;cat ]` — 위협 #10542

### 3.2 파이프로 명령 연결

**어디서**: 브라우저 주소창 › 상품 검색 API

**어떻게**: 3.1과 같고 주소만 바꾼다.

**입력값**

```text
http://localhost/rest/products/search?q=test|cat /etc/passwd
```

**결과**: 응답 200, 검색 결과 없음.

**탐지**: WAF 탐지, 규칙 4건(930120·932160·932220·932236) · AI 탐지, `[규칙] 쉘 메타문자 + 시스템 명령 [cat /, |cat]` — 위협 #10544

### 3.3 백틱 명령 치환

**어디서**: 브라우저 주소창 › 상품 검색 API

**어떻게**: 3.1과 같고 주소만 바꾼다.

**입력값**

```text
http://localhost/rest/products/search?q=test`id`
```

**결과**: 응답 200, 검색 결과 없음.

**탐지**: WAF 탐지, 규칙 1건(942510) · AI 미탐 — 위협 #10546

**3번 정리**: 3.1·3.2는 둘 다 탐지했다. 3.3 백틱 치환은 `cat` 같은 명령 키워드가 없어 AI 규칙에 걸리지 않았고 WAF만 탐지했다. AI의 빈틈을 WAF가 메운 사례다. 다만 WAF도 명령 실행 규칙(932)이 아니라 SQL 규칙(942510)으로 잡았다(PL1 기준).

## 4. Path Traversal

경로에 `../`를 넣어 허용된 폴더 밖의 파일을 읽으려는 공격이다. JuiceShop의 파일 서버 `/ftp`가 대상이다. `http://localhost/ftp`에 들어가면 공개된 파일 목록을 먼저 볼 수 있다.

### 4.1 인코딩한 ../ 로 상위 폴더 파일 요청

**어디서**: 브라우저 주소창 › `/ftp` 파일 서버

**어떻게**: 아래 주소를 주소창에 붙여 넣고 Enter를 누른다. (`/`를 `%2f`로 바꿔 써야 브라우저가 지우지 않는다.)

**입력값**

```text
http://localhost/ftp/..%2fpackage.json
```

**결과**: 응답 403 — 앱이 상위 폴더 파일 요청을 거부한다.

**탐지**: WAF 탐지, 규칙 3건(930100·930110·930130) · AI 미탐 — 위협 #10547

### 4.2 이중 인코딩으로 필터 우회

**어디서**: 브라우저 주소창 › `/ftp` 파일 서버

**어떻게**: 4.1과 같고 주소만 바꾼다. (`%25`는 `%` 자체를 인코딩한 것이라, 서버에서 두 번 풀어야 `../`가 된다.)

**입력값**

```text
http://localhost/ftp/%252e%252e%252f%252e%252e%252fetc%252fpasswd
```

**결과**: 응답 403 — `Only .md and .pdf files are allowed!`

**탐지**: WAF 탐지, 규칙 1건(930100) · AI 탐지, `[규칙] 디렉터리 탈출 패턴 [%2e%2e×2]` — 위협 #10548

### 4.3 널 바이트로 확장자 검사 우회

**어디서**: 브라우저 주소창 › `/ftp` 파일 서버

**어떻게**: 4.1과 같고 주소만 바꾼다. (`/ftp`는 `.md`·`.pdf`만 허용하는데, 파일 이름 뒤에 `%00`(널 바이트)과 `.md`를 붙여 검사를 속인다.)

**입력값**

```text
http://localhost/ftp/package.json.bak%2500.md
```

**결과**: 응답 200 — 원래 받을 수 없는 개발자 백업 파일 `package.json.bak`이 다운로드된다(공격 성공).

**탐지**: WAF 탐지, 규칙 1건(930130) · AI 탐지, `[모델] 처음 보는 경로·파라미터 조합 … 검토 권장` (규칙이 아니라 모델이 구조 이상으로 판정) — 위협 #10550

**4번 정리**: WAF는 세 가지 모두 탐지했다. AI는 4.1(`..%2f`)을 놓쳤고, 4.3은 규칙이 아니라 모델의 구조 판정으로 잡았다. 4.1도 WAF가 메워 요청 단위 미탐은 없다.

## 5. Server-Side Request Forgery (SSRF)

서버가 공격자가 지정한 주소로 대신 요청하게 만드는 공격이다. 외부에서 닿지 않는 내부망·클라우드 메타데이터에 접근하는 데 악용된다. JuiceShop 프로필 사진의 "URL로 가져오기" 기능이 대상이다.

### 5.1 클라우드 메타데이터 주소 요청

**어디서**: 프로필 화면 `http://localhost/profile` › Image URL 칸 (로그인 필요)

**어떻게**

1. JuiceShop에 로그인한다(0.2 참고).
2. 오른쪽 위 `Account` → 이메일(admin@juice-sh.op)을 누르거나, 주소창에 `http://localhost/profile`을 입력해 프로필 화면을 연다.
3. Image URL 칸에 아래 입력값을 넣는다.
4. `Link Image`를 누른다.

**입력값**

```text
http://169.254.169.254/latest/meta-data/
```

**결과**: 서버가 이 주소로 요청을 시도한다. 로컬에는 메타데이터 서버가 없어 요청은 실패하고, 앱은 주소만 프로필 이미지 주소로 저장한다. (응답 302) 클라우드(EC2)라면 인스턴스 정보·자격 증명이 노출될 수 있는 경로다.

**탐지**: WAF 탐지, 규칙 3건(931100·931130·934110) · AI 미탐 — 위협 #10552

### 5.2 내부 관리 API(루프백) 요청

**어디서**: 프로필 화면 › Image URL 칸 (로그인 필요)

**어떻게**: 5.1과 같고 Image URL 값만 바꾼다.

**입력값**

```text
http://127.0.0.1:3000/rest/admin/application-configuration
```

**결과**: 서버가 자기 내부의 관리 API를 대신 호출하고, 그 응답(앱 설정 JSON)을 프로필 이미지 파일(`/assets/public/images/uploads/1.jpg`)로 저장한다. 외부 사용자가 그 파일을 열면 내부 데이터를 볼 수 있다(공격 성공).

**탐지**: WAF 탐지, 규칙 3건(931100·931130·934110) · AI 미탐 — 위협 #10553

### 5.3 16진수 IP로 루프백 우회

**어디서**: 프로필 화면 › Image URL 칸 (로그인 필요)

**어떻게**: 5.1과 같고 Image URL 값만 바꾼다. (`0x7f000001`은 `127.0.0.1`을 16진수로 쓴 것이라, `127.0.0.1`·`localhost` 문자열만 막는 필터를 피한다.)

**입력값**

```text
http://0x7f000001:3000/
```

**결과**: 서버가 내부 페이지를 가져와 이미지 파일로 저장한다(공격 성공).

**탐지**: WAF 탐지, 규칙 3건(931130·934120·942450) · AI 미탐 — 위협 #10554

**5번 정리**: AI에는 SSRF 규칙이 없어 세 가지 모두 놓쳤고 WAF가 전부 탐지했다. AI가 통째로 비는 영역을 WAF가 메우는 대표 사례다.

## 6. XML External Entity (XXE)

XML 파서가 외부 엔티티를 처리하게 만들어 서버 파일 읽기·내부 요청·자원 고갈을 일으키는 공격이다. JuiceShop 민원 화면의 송장(Invoice) 파일 첨부가 대상이다.

**공통 어디서**: 민원 화면 `http://localhost/#/complain` › Invoice 파일 첨부 (로그인 필요)

**공통 어떻게**

1. 아래 입력값(XML)을 메모장에 붙여 넣고 `invoice.xml`로 저장한다.
2. JuiceShop에 로그인한 뒤 왼쪽 위 메뉴(≡) → `Complaint`를 연다.
3. Message 칸에 아무 문장이나 쓴다.
4. Invoice의 `Choose File`로 `invoice.xml`을 첨부한다. (파일 선택 창은 기본으로 `.pdf`·`.zip`만 보여주므로 형식을 "모든 파일"로 바꿔서 고른다.)
5. `Submit`을 누른다.

### 6.1 외부 엔티티로 서버 파일 읽기

**입력값** (`invoice.xml`)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE order [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<order><item>&xxe;</item></order>
```

**결과**: 응답 410 — `B2B customer complaints via file upload have been deprecated for security reasons`

**탐지**: WAF·AI 모두 미탐 — 위협 탐지 목록에 없고, 전체 로그에만 `POST /file-upload 410`으로 기록된다.

### 6.2 외부 엔티티로 내부 주소 요청

**입력값** (`invoice.xml`)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE order [<!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/">]>
<order><item>&xxe;</item></order>
```

**결과**: 응답 410 (6.1과 같음).

**탐지**: WAF·AI 모두 미탐

### 6.3 엔티티 폭탄(Billion Laughs)

**입력값** (`invoice.xml`)

```xml
<?xml version="1.0"?>
<!DOCTYPE lolz [<!ENTITY lol "lol"><!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;"><!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">]>
<lolz>&lol3;</lolz>
```

**결과**: 응답 410 (6.1과 같음).

**탐지**: WAF·AI 모두 미탐

**6번 정리**: **WAF와 AI가 모두 놓치는 사각지대**다. ModSecurity가 요청 본문 자체는 검사하지만, **기본 CRS 룰셋은 multipart로 업로드된 파일의 내용을 규칙 대상(ARGS 등)에 넣지 않아** 그 안의 XML을 스캔하지 않는다(모든 업로드 바이트를 규칙에 돌리면 비용·오탐이 커서 택한 의도된 기본값). AI에도 XXE 규칙이 없고, 파일 내용이 분석 입력에 들어가지도 않는다. JuiceShop v20은 XML 업로드 기능을 폐기(410)해서 공격 자체는 동작하지 않지만, 탐지 공백은 실제 한계다. **대응(향후 과제)**: 기본 룰셋만으로는 못 잡으므로 업로드 본문을 검사하는 커스텀 규칙을 추가한다 — 예: 본문에서 `<!DOCTYPE`·`<!ENTITY`·`SYSTEM`·`file://`를 탐지(`SecRule REQUEST_BODY "@rx (?i)<!(DOCTYPE|ENTITY)\b|SYSTEM\s+["']|file://" ...`). 단 현재 엔진이 libmodsecurity v3(nginx 커넥터)라 파일 내용 정밀 검사(`@inspectFile` 등) 지원이 제한적이고, 공격 규칙은 DetectionOnly라 이 규칙도 인라인 차단이 아니라 탐지에 그친다. WAF·AI·IP가 모두 맞으면 블랙리스트에 올라 다음 요청부터 403이 된다.

## 7. 종합

18개 시나리오의 탐지 결과를 커버리지별로 묶으면 다음과 같다.

1. **WAF·AI 둘 다 탐지 — 10건**: 1.1, 1.2, 1.3, 2.1, 2.2, 2.3, 3.1, 3.2, 4.2, 4.3
2. **WAF만 탐지(AI 미탐) — 5건**: 3.3(백틱), 4.1(`..%2f`), 5.1, 5.2, 5.3(SSRF 전체)
3. **둘 다 미탐 — 3건**: 6.1, 6.2, 6.3(XXE 전체)
4. **AI만 탐지 — 0건** (정식 18건 기준; 추가 측정에서 AI 이상탐지만 반응한 경로-세그먼트 probe는 아래 7.1 — 깨끗한 AI-only 공격은 아님)

정리하면 어느 한 계층도 단독으로 완전하지 않다. WAF와 AI는 서로의 빈칸을 메우지만, XXE처럼 두 계층이 함께 비는 사각지대는 과제로 남는다.

한 가지 덧붙이면, 위에서 "AI만 탐지"가 0건인 것은 고정된 공격에 대해서는 CRS가 워낙 넓게 잡기 때문이다. CRS를 실제로 우회하는 적대적 변종에서는 AI가 그 일부를 회수한다. WAF-A-MoLE로 찾은 CRS 우회 SQLi의 50%(3/6), 공개 우회 payload의 29%(2/7)를 AI가 잡았고, WAF 단독이면 0%다. 즉 깨끗한 AI-only는 고정 공격이 아니라 우회(회수) 맥락에서 나온다. 상세는 우회 강건성 측정(Notion: "우회 강건성 (AI 침투 테스트)")에 있다.

## 7.1 AI 이상탐지만 반응한 경로-세그먼트 probe

위 18개 정식 시나리오에는 "AI만 탐지"가 0건이다. 추가 탐색에서 **WAF 시그니처는 못 보고 AI만 반응한** 경우를 하나 확인했는데(2026-11-02 실측), **깨끗한 "AI만 잡은 공격"은 아니다** — 아래처럼 성격이 애매한 사례다. 그래도 WAF·AI 커버리지 차이를 보여주므로 남긴다. 공격 문자열을 쿼리 파라미터가 아니라 **URL 경로(path) 세그먼트**에 심은 경우다.

**어디서**: 브라우저 주소창 › JuiceShop REST 경로의 id 세그먼트 (예: `/rest/products/:id/reviews`)

**입력값**: `http://localhost/rest/products/test&sleep 15&/reviews` (실제 전송 `/rest/products/test%26sleep+15%26/reviews`). `&sleep 15&`는 시간 기반 블라인드 명령어 주입 probe의 전형 — 스캐너가 "응답이 15초 늦나?"로 취약 여부를 떠보는 형태다.

**결과**: 응답 200. JuiceShop은 Node라 셸을 실행하지 않아 `sleep`은 동작하지 않고 잘못된 상품 id로 처리된다 → **동작하는 공격이 아니라 공격 "시도(probe)"**다.

**탐지**: WAF 미탐(waf_detections 없음) · AI 탐지, `[모델] URL 인코딩 문자 2개 [%26×2] · 처음 보는 경로·파라미터 조합 … 검토 권장`

**이 사례의 성격**: AI는 이걸 "명령어 주입이다"라고 **의미로** 판정한 게 아니라, `[모델]`이 **"URL 구조가 이상하다 → 검토 권장"**이라고 **구조로** 플래그한 것이다(낮은 확신의 이상 탐지). 그래서 같은 모델은 깨진 링크·봇 트래픽·이상하게 인코딩된 정상 요청에도 같은 플래그를 낼 수 있다 — 즉 **"공격 탐지"보다 "이상 요청 탐지"에 가깝고, 오탐과 종이 한 장 차이**다.

**왜 WAF가 놓치나**: CRS의 SQLi(942)·명령어(932) 룰은 주로 **ARGS(쿼리 파라미터·본문)**를 검사한다. 같은 payload를 `…/search?q=test;cat /etc/passwd`처럼 쿼리에 넣으면 CRS가 932로 잡지만(3번 시나리오), 경로 세그먼트에 심으면 흘린다.

정리하면 JuiceShop에서 AI만 잡는 깨끗한 동작 공격은 사실상 없다. 실제 주입점이 전부 쿼리나 본문(ARGS)이라 CRS가 커버하기 때문이다. AI-only처럼 보이는 것은 이런 구조 이상 플래그이고, AI의 실질적 가치는 탐지 개수가 아니라 오탐을 줄이고 처음 보는 변종에 일반화하는 데 있다.

# 정상 시나리오 (8)

앞의 1~6번은 공격을 탐지하는 쪽을 봤다. 반대로 정상 사용자의 평범한 입력에서 WAF가 오탐하고 AI가 그 오탐을 걸러내는 경우를 모았다. 정상 입력 10건 중 7건에서 WAF가 오탐했지만, AI는 10건 모두 정상으로 판정했다. T1에서 측정한 WAF 오탐 19.7%와 AI 오탐 4.4%를 화면으로 재현한 것이다.

## 8.1 정상 입력 — 오탐 없음 (대조군)

특수문자가 없는 평범한 입력이다. WAF·AI 모두 조용하고, 대시보드 위협 탐지 목록에 뜨지 않는다(전체 로그에만 기록). 오탐 사례와 비교할 기준선이다.

- **상품 리뷰 작성** — 입력 `Very fresh and tasty, will buy again!` → WAF·AI 모두 정상.
- **회원가입** — 이메일·비밀번호·보안 질문 답변 입력 → 정상.
- **배송지 추가** — `서울시 강남구 테헤란로 123, 4층` → 정상.

## 8.2 SQL 구문으로 오인 — CRS 942 계열

평범한 문장에 들어간 `--`(하이픈 강조)나 `order by` 같은 일상 단어를 WAF가 SQL 공격으로 오인한다. 셋 다 앱에는 정상 저장되고, AI는 모두 정상으로 판정한다.

**리뷰에 하이픈 두 개로 강조**

WAF 오탐. 규칙 942440(SQL 주석 `--` 탐지)이 걸렸고, 매칭된 문자열은 `-- `였다.

**피드백에 하이픈 두 개로 강조**

WAF 오탐. 규칙 942440이 걸렸고, 매칭된 문자열은 `-- `였다.

**SQL 단어가 섞인 문의**

WAF 오탐. 규칙 942380(SQL Injection)이 걸렸고, 매칭된 문자열은 `order by`였다. 일상어 "order by 가격 정렬"을 공격으로 오인한 것이다.

## 8.3 명령어 실행으로 오인 — CRS 932 계열

음식·회사 이름, 윈도우 폴더 경로, 심지어 앱이 자동으로 보내는 요청까지 WAF가 OS 명령 실행 공격으로 오인한다. AI는 모두 정상으로 판정한다.

**화면을 열기만 해도 생기는 오탐**

고객 피드백 화면을 열면 앱이 로그인 사용자 정보를 확인하려고 `GET /rest/user/whoami?fields=id,email`을 자동으로 보낸다. WAF는 파라미터의 `id,`를 리눅스 `id` 명령으로 오인한다(규칙 932236). 사용자가 아무것도 입력하지 않아도 생기는 오탐이다.

**음식 이름 fish & chips**

WAF 오탐. 규칙 932236(Unix 명령 삽입)이 걸렸는데, 매칭된 문자열은 `&`가 아니라 `fish`였다(리눅스 셸 이름으로 오인).

**윈도우 폴더 경로 언급**

WAF 오탐. 규칙 932240(명령 삽입 우회 시도)이 걸렸고, 매칭된 문자열은 `Users\me`였다(경로의 `\`를 명령어 우회 기호로 오인).

## 8.4 서버 500 오류로 오인 — CRS 950100

**이름에 아포스트로피가 있는 사용자의 로그인**

`o'brien@example.com`으로는 회원가입은 정상으로 되지만(탐지 없음), 같은 계정으로 로그인하면 아포스트로피가 앱의 SQL을 깨뜨려 서버가 500을 낸다. WAF는 이 500 응답을 보고 정보 노출 시도로 기록한다(규칙 950100). 공격이 아니라 앱의 입력 처리 버그가 만든 오탐이다. AI는 정상으로 판정한다.

## 8.5 종합 (정상 시나리오)

정상 입력 10건 중 7건에서 WAF가 오탐했지만, AI는 10건 모두 정상으로 판정했다.

| 구분 | 시나리오 | WAF | AI |
| --- | --- | --- | --- |
| 대조군 | 1.1~1.3 | 정상 | 정상 |
| SQL 오인 | 2.1~2.3 | **오탐** (942440·942380) | 정상 |
| 명령어 오인 | 3.1~3.3 | **오탐** (932236·932240) | 정상 |
| 500 오인 | 4.1 | **오탐** (950100) | 정상 |

**논리**

- 자동 차단은 WAF와 AI가 함께 탐지할 때만 걸린다. 그래서 이 7건의 WAF 오탐은 자동 차단으로 이어지지 않는다. AI가 정상이라고 판정해 걸러내기 때문이다.
- 오탐은 특이한 입력이 아니라 `--`, `&`, `\`, `'`, `order by`처럼 평범한 입력에 흔한 토큰에서 나온다. 3.1처럼 사용자가 입력하지 않아도 앱의 자동 요청에서 생기기도 한다.
- 이것이 T1 측정의 WAF 오탐 19.7%와 AI 오탐 4.4%를 화면에서 재현한 것이다. 공격 쪽이 AI가 WAF를 보완한다는 점을 보였다면, 이 쪽은 그 보완의 핵심이 탐지 개수가 아니라 오탐 감소임을 보여준다.

정리하면, WAF 단독 운영은 정상 사용자를 공격자로 오인해 차단할 위험이 있다. AI가 오탐을 걸러 주기 때문에 WAF와 AI를 함께 쓰는 이중 방어가 안전하게 자동 차단을 할 수 있다.
